## Vue 2 之 `ref` 在 `v-for` 內一律是陣列(2026-09-14)

- **事件**: `PageUser.vue` 變更密碼表單之 `ref="rfChangePwForm"` 位於 `v-for="(v,k) in displayUser"` 內, `vo.$refs.rfChangePwForm` 為 `[el]`(即使只命中一個), `el.scrollIntoView` 為 undefined → `if (el && el.scrollIntoView)` 靜默跳過, 捲入自 09-07 起從未執行, e2e 全綠(斷言不驗捲動).

## Vue 2.7.16 之靜態 style 會蓋掉 v-show(2026-09-24, ADR-067)

- **事件**: 標題列漢堡容器寫成 `style="...; display:flex; ..." v-show="isNarrow"`, 寬版初載漢堡鈕即可見; 窄→寬切換當下正確隱藏, 下一次重繪(改版寬)又出現. 逐步印 `style.display` 才看出在 `none` / `flex` 間翻.
- **成因**: Vue 2.7.16 `updateStyle`(`node_modules/vue/dist/vue.runtime.esm.js` 之 `function updateStyle`)對新 style 每個屬性**無條件** `setProp`(舊版有 `cur !== oldStyle[name]` 比對才寫), 靜態 style 之 `display` 每次重繪都被寫回, 蓋掉 v-show 設的 `display:none`. v-show 只在值變動時才改 display, 救不回來.
- **教訓**: v-show 之元素其靜態 style 不放 `display`(移至內層), 或改用 v-if; 規則與盤點指令見 `sgud/rule/rulebook.md`「程式碼規則」. 同理, 任何被程式改寫之 inline style 屬性(非 display)若也寫在靜態 style, 下次重繪同樣會被還原.

## 真實點擊時, 同一 click 之各監聽器之間會先跑 microtask(2026-09-24, ADR-067)

- **事件**: 漢堡按鈕(`WButtonCircle`, click 以 `$nextTick` emit)經 `toggleMenu` 把 v-model 設 false 關閉選單, 但同一 click 冒泡到外層 `WPopup` 觸發區(`@click="evShow('popup','click')"`)時選單已關(`valueTrans=false`), evShow 於是又把它打開 → 「再點一次關不掉」. 以 `$watch(..., {sync:true})` 印堆疊才看到 `setMenuOpen(true)` 來自 `buildPopper.mjs` 之 `triggerEvent`.
- **成因**: 瀏覽器對 trusted event(使用者真實操作 / Playwright `locator.click` / `mouse.click`)在每個監聽器回呼返回後執行 microtask checkpoint, 子層 `$nextTick`(Promise)與其觸發之重繪都在父層監聽器之前完成. `el.click()` / `dispatchEvent` 之合成事件則整段同步派送, 中間不跑 microtask——用合成事件測不出此問題.
- **教訓**: 父子兩層處理同一 click 時, 不可假設子層 nextTick 晚於父層監聽器; 以 `@click.stop` 截斷, 開關改由單一來源(v-model)控制. 驗證一律用真滑鼠. 規則見 `sgud/rule/rulebook.md`「程式碼規則」.

## 探測時同一頁混用滑鼠與觸控, tap 後會多出 mouseleave(2026-09-24, ADR-067 姊妹專案驗收)

- **事件**: perm 觸控探測中 cht 輪「tap 截斷之說明出提示」穩定失敗, eng 輪通過. 在觸發區掛事件記錄: cht 輪 tap 後依序為 `…mouseup, click, mouseleave, mouseleave`, 提示一出現即被關; eng 輪沒有 mouseleave.
- **成因**: cht 輪在同一頁先以滑鼠(`locator.click`)點寬版語系下拉切語系, 之後才 tap; Chrome 在 tap 之相容滑鼠事件後把 hover 還給先前的滑鼠位置, 對 tap 點之元素送出 mouseleave. 真實手機沒有另一個滑鼠指標, 屬探測手段造成之假象.
- **教訓**: 觸控情境(`hasTouch`)之探測, 所有前置操作也一律用 `tap()`/`touchscreen.tap`, 不混用 `click()`; 遇「只有某語系/某順序失敗」先比對兩輪前置操作之差, 再掛事件記錄看實際事件序, 不先懷疑產品.

## 契約測試把外洩凍結成規格; 權杖類別要以「輸出通道」展開(2026-09-24, ADR-068)

- **事件一(2026-09-07 → 09-24)**:
  - 為對外 helper 建契約測試時, 把「含已代入權杖之完整網址」之 reject 字串逐字斷言為契約, 沒有任何「不得含權杖」之負向斷言;
  - 部署方實測: 任何人送無效權杖即可從消費端回應取得 app token.
- **事件二(方案 v1)**:
  - 輸入空間表以變數名 grep(`token|query|authorization`)與投訴句長出軸, 漏了:
    - 以標頭流動之權杖: referer 每請求寫入 srLog、整包 headers 印 console;
    - 參數型別(Hapi 重複參數 → 陣列, `maskToken` 對非字串原樣回傳);
    - 另兩個注入函數;
    - 本家範本(perm helper 早已 key-only);
    - 第四個兄弟系統(task);
  - 兩個獨立複審才補齊. 實作中又以規則 grep 找到方案與複審都漏的 kpfun `getUserInfor` valueLog(與 HTTP 路由同規則之第二處).
- **教訓**:
  1. 契約測試寫「對外字串」時, 同時寫它**不得**含什麼(權杖、網址、錯誤原文), 且先對舊碼跑紅;
  2. 權杖類別之軸取「會輸出到哪」: 回應、reject 值、srLog 各欄(含 referer)、console、下游 error 事件、瀏覽器、反向代理 access log、介接端資料庫. 站點以規則 grep, 不以投訴路徑推;
  3. 回報方問題必 grep 姊妹專案同機制(`sgud/proc/process.md` 已明訂), 先找本家範本再對標外部標準;
  4. `String.prototype.replaceAll(字串, 字串)` 之取代字串會解讀 `$&` `` $` `` `$'`: 代入請求端可控值一律 split / join;
  5. Node 內建 fetch 之錯誤 message 可能含完整網址(`Failed to parse URL from …`、`Request cannot be constructed from a URL that includes credentials: …`), `util.inspect` 錯誤物件時 `cause.input` 亦含全文: 只輸出 name / code.
- **連帶**: `api-httpendpoints` 之 `restartBackend` 會換掉 11007 上之任何後端(含手動啟動者); 跑該檔後若需手動後端須重啟並回驗.

## 陣列欄經 w-orm-lmdb `save` 無法縮短; 權限要測「撤銷」不只測「授予」(2026-09-25, ADR-069)

- **事件**: app token 權限矩陣全綠後, 另寫「授予後再撤銷」案例: 授予 `readTokens` 立即生效, 撤銷為 `[]` 後 app 仍可讀金鑰清單. DB 內 perms 仍為 `['readTokens']`.
- **成因**: `node_modules/w-orm-lmdb/src/WOrmLmdb.mjs` 之 `save` 以 `merge({}, 舊列, 新列)` 寫入; lodash `merge` 對陣列逐索引合併, 空陣列或較短陣列蓋不掉舊尾端元素(`['a','b']` 存成 `['c']` 會得 `['c','b']`). 授予(變長)恰好正確, 所以只測授予抓不到.
- **教訓**:
  1. 任何陣列欄之寫入都要有「由長改短、元素不同」之案例(PERM-A-007); 權限類功能以「授予 → 撤銷 → 立即失效」為完整單位.
  2. 修法在 `updateTabItems`(陣列欄變短之列先存 `null` 再存整列), 不改他套件; 直接以 `woItems.<表>.save` 寫陣列欄之路徑同樣要處理(`sgud/proc/process.md`「應用系統金鑰之權限」).

## 寫入驗證只驗「本批有變動」之列(2026-09-25, ADR-069)

- **事件**: perms 寫入驗證先寫成「每列都驗」, 矩陣中 admin 之整批存回金鑰清單全被 `tokenPermsInvalid` 擋下——fixture 有一列 DB 內之 perms 為毀損值(字串), 前端原樣送回.
- **教訓**: 後台「整批存回」型 API 若對每列做格式驗證, DB 內一筆既有壞資料就會讓所有存檔永遠失敗且無從在 UI 修正. 只驗與 DB 不同之列; 未變動之列依讀取端之 fail closed 規則正規化(有效結果相同).

## 後台清單儲存格內之彈出層: 重繪會銷毀, 銷毀不送關閉事件(2026-09-25, ADR-069)

- **事件**: 應用系統權限清單(WPopup, 在 ag-grid 儲存格內)若每勾一次就寫回列並 `refresh()`(`redrawRows`), 儲存格重建使清單當場關閉; 改為「草稿 + 關閉清單時寫回」後, 又發現切換編輯模式時清單隨表格重建被銷毀, 而銷毀後 `hide` 事件因元件已 `$off` 收不到, 草稿殘留顯示於該列.
- **教訓**: 儲存格內之多選編輯採草稿, 以彈出層之 `@show` / `@hide` 載入與寫回, 並在重建表格處(`genOpt`)清除草稿; 勾選當下即標記已修改讓儲存鈕出現, 按儲存時先寫回草稿. 儲存格之顯示可讀父層草稿(scoped slot 會追蹤父層響應式資料), 不需重繪.

## `--names` 給多階段圖鍵時整案靜默略過; 重產是否真寫檔以 mtime 與 `[skip]` 行判斷(2026-09-27)

- **事件**: 重產標準圖後做重現性驗證, `--names eng-E2E-001-list-loaded,cht-E2E-005-2-perms-list,eng-E2E-007-4-perms-list-readonly` 結束碼 0、log 印「標準圖產生完成」, 實際只重產了 E2E-001; 後兩張所屬 case 根本沒執行, log 連 `[skip]` 都沒有.
- **成因**: e2e-tokens 之 `shouldGen` 以 `${lang}-${case 名}-` 前綴比對階段圖鍵, 但階段圖鍵格式為 `E2E-NNN-<序>-<名>`(不含 case 名), 永不命中; 其他 6 個有多階段案例之流程則是 `shouldGen` 只認 case 名、`writeBaseline` 只認階段圖鍵, 兩者須同時給.
- **教訓**:
  1. 手術式重產後, 以「目標檔 mtime 是否落在本輪」與「log 中該 case 是否出現、其他階段是否印 `[skip]`」確認真的寫了, 不看結束碼與完成字樣.
  2. tokens 已改為以 `${lang}-E2E-NNN-` 比對(給 case 名寫全部階段, 給階段圖鍵只寫該張); 其他流程之同類缺口見 `sgud/rule/rulebook.md` 已知缺口.

## 截圖實作之等價測試: 同一頁先後截兩次會「搭便車」, 須每次重新載入並有反向對照(2026-09-27, srcPack)

## 頁面捲動後, 以視窗座標遮 `<img>` 動畫會落錯位置, 且截圖「穩定」在不固定影格(2026-09-27, srcPack)

- **教訓**: ①改框的「對象」後要回頭驗框的「留白」, 兩者是不同維度; ②以 display 判斷「是否自帶框」是近似(無底色的 inline-flex 開關會被誤判), 要以視覺事實(可見邊界)判斷; ③掃描器旗標多為元素邊界貼框(彈窗、晶片、按鈕), 需逐類裁框目視才定性.

## 「框線不蓋框外內容」同日連修三輪: 每一輪都只量了一側(2026-09-28, 四專案)

- **事件**: 業主指示「亂框亂壓導致遮蔽有效資訊或使用者誤解就是問題」後, 依序改了三版, 每版審圖都抓到上一版自己造成的新貼線: ①鄰項夾邊以**元素框**取中點 → 圖示鈕之透明內距把框線拉回「Edit mode／編輯模式」字上(1–2px); ②浮層一律**畫在內側** → 內距 6–7px 之時間清單、模式清單、權限浮層框線貼字(1–2px); ③外擴只給文字、**子元素框不外擴** → 權限列之勾選框、開關軌道貼框線 0–1px, 四邊留白不一致; 另 WPopperFix 為「透明 fixed 外層 + 內層面板」, 只認 fixed 元素本身, 語系清單框線壓觸發區 2px.
- **處置**: 框線一律置於「兩側可見內容之間隙正中」——可見範圍取有邊界者之元素框、無邊界者之子元素與文字聯集; 浮層外之內容以命中測試找(透明攔截層可穿透、遮罩後不算), 目標涵蓋整個浮層時以面板內容計; 無邊界目標之可見內容一律外擴 4px, 恰為單一有邊界元素者視同框該元素. srcPack 每一版都補了能重現該失敗之單元測試.
- **教訓**: 「不壓」有兩側——框外的鄰項與框內的自身內容; 任何單向規則(一律外擴 / 一律內縮 / 只外擴某類)都會在某類版面失敗. 每改一版, 審圖時量框線兩側到最近內容之距離(`tmp/ink-gaps.mjs` 類量測 + 3 倍放大), 不只看被投訴的那一側.

## 程式一致已證明, 仍四專案全套重跑——驗證範圍要由差異決定(2026-09-29, ADR-073)

- **經過**: w-package-tools-e2e 1.0.2 發布後切換四專案. 切換前已解 tarball 逐檔比對: srcPack 之 52 檔中 48 檔逐位元相同、3 檔只差 JSDoc / 引號寫法、`launchChromium` 所轉呼叫之實作與已裝 1.0.1 相同——行為無差異已證明. 我仍機械式啟動四專案全套(本專案 e2e 約 100 分鐘), 業主指正「你確認程式碼是否一致不就好了」「若無差異就是能保證不用重跑 e2e, 若有差異應該是針對差異之處去跑」.
- **成因(我的流程)**: 把「測試全綠」當成唯一可信的完成證據, 沒有把已完成之比對結果轉成驗證範圍; 沒估算成本就選了最重的驗證.
- **判準**: 驗證前先寫「差異清單」(程式 diff、依賴版本、解析路徑), 每項對到會觸及它的最少測試: 本次唯一實際變動是模組解析路徑與依賴解析位置 → 橋接檔載入檢查(52 個匯出)＋依賴版本比對＋每專案抽查數檔即足. 程式有行為差異時, 只跑用到該模組之測試.
- **中止長鏈之假象**: 以 TaskStop 中止 `run-e2e-isolated` 後, runner 會繼續生後續各檔之子行程, 全部以 0xC0000142(`3221225794`, 無法初始化)結束並印「✘ N 個 e2e 檔失敗」——這是中止假象, 不是測試失敗; 另有一個 npx 孫行程(mocha)存活, 須以命令列確認為本輪所起後樹狀結束, 並清 `test/_tmp` 之殘留.

## 雙擊防護實測: 全頁 loading 只擋滑鼠; 請求數要數後端日誌(2026-09-29)

- **事件**: 盤點「按鈕雙擊防護」時以探測腳本量「連按送出幾次」. 滑鼠雙擊各「儲存」鈕只送 1 次(全頁 loading 之 WDialog 蓋住第 2 下), 但**鍵盤**(焦點在按鈕或輸入框連按 Enter)可送 2 次: WDialog 不搶焦點, 事件照送到原元素; 已套 `promiseUnlock` 者因 handler 第一行 `pm.resolve()` 使元件鎖立即解除, 第 2 次 `keyup.enter` 亦不被擋. 使用者清單新增後連按 → 新帳號被第 2 次當「修改」覆寫(timeVerified 清空、建立者寫成前端佔位字), 無法登入. 細節與站點見 `sgud/rule/rulebook.md` 已知缺口.
- **量測教訓**: ①前端 `$fapi` 之請求 body 不是 `obj2u8arr({ func })`(`api-doubleclick` 直打用之格式), 在瀏覽器端解 func 名全為 null——請求數一律以後端 srLog 之 `kpfun-*` 事件、依時間過濾計數; ②使用者頁「Log out」在卡片捲動區下方, 不先捲入就以座標點會點到卡片背景, 看似「沒送出」; ③連按間隔 80ms 時, 本機後端在第 1 次已處理完、儲存鈕隨 `isModified=false` 隱藏, 第 2 下無對象——「沒重現」不等於有擋, 要縮到 5ms 才看得到; 判定有無防護先看程式有無機制, 再以最短間隔實測.
- **修正時連帶找到的兩件(ADR-074 / ADR-075)**: ①單例訊息框(CheckYes / CheckYesNo)之 `show()` 會覆寫前一個等待者之 pm, 被覆寫之流程永久等待——前端流程狀態以「結果訊息框關閉」為結束點後, 這會使該 key 永遠不釋放, 按鈕永遠無反應; 以單例服務呈現結果者, 改流程結束點前先確認前一個等待者會被結束. ②驗收新帳號時清單顯示「未驗證」: 追到 verifyEmail 與後台建帳以秒級 `now2str()` 寫 timeVerified, 而共用判斷 `getIsVerified` 要 `istimemsTZ`——既有測試只驗「有值」不驗格式, 所以一直綠; 測試斷言須對到判斷函式實際採用之格式(以同一個判斷函式斷言, 不自寫正則).
- **harness 註解把缺陷背書成「可接受狀態」**: 四專案之 `e2e-setup.mjs` 都寫著「按鈕點擊後立即彈 dialog 者, 遮罩擋住 mouseleave, 截圖含 tooltip 視為可接受」, PERM 據此凍結了 11 案之殘留提示框標準圖(蓋住表格標頭). 最小重現推翻其前提: 單純遮罩仍會派發 mouseleave, 殘留只發生於 WButtonCircle 以 `v-if` 換掉游標下之圖示後再出現遮罩(元件缺陷). 處置: 不改元件(他 repo, 須授權)、不重產把殘留凍結, 改在 `captureStable` 之 `beforeShots` 偵測「游標已移開仍可見 `saveChanges` 提示」即拋 knownDefect, 比對端 `onKnownDefect: () => this.skip()` 標 pending; 只認特定提示文字, 因 `.WPopperFix` 亦用於下拉浮層; `visibility:hidden`(popper 之 reference-hidden)不算可見. 讀到「視為可接受」「使用者也只能看到此態」這類註解時, 先以最小重現驗其前提再決定是否繼承. **(2026-09-30 更正)** 「只認特定提示文字」是把類別縮成撞到的那一個: PERM 所屬對話框標題列 Save 鈕(WDialog 內建, 提示「Save」／「儲存」)之同型殘留因此沒被偵測, 已凍結進 6 張標準圖; 且當時說「四專案都寫著」, 實則 API 那份漏改. 區分提示框與下拉浮層應依元件設定(WTooltip `mode`), 不依文字(見下節).
- **定向重跑之假綠**: `mocha --grep` 對不到任何案例時 0 passing 且離開碼 0, 看起來像「全過」; 定向重跑一律加 `--fail-zero`, 且 grep 字樣取自 `it()` 標題原文(本專案部分 e2e 標題不含 E2E 編號).

## w-package-tools-e2e 1.0.3 升版: 會改像素之改動怎麼只重產受影響者(2026-09-30, ADR-078)

## w-serv-orm 1.1.8 適配: 上游把「寫入時拒絕」的一類輸入前移, 要連「寫入時改寫」的同根因一起前移(2026-10-12, ADR-081)

## 透傳之上游選項: 先確認本套件之呼叫路徑滿足其前提; 參數之每種用途都要列(2026-10-12, ADR-083 / ADR-084)
