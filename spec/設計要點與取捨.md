## ADR-001: Multi-session 接受 (同帳號多 active token 並存)

**Status**: Accepted (2026-06-08)

**Context**:
- 業主需求為「同一使用者可在多裝置 / 多瀏覽器同時保有登入態」(辦公桌 PC + 手機 + 平板情境). 若每次新登入就 invalidate 既有 token, 跨裝置體驗會被打斷, 與業主期待不符.
- Audit F-046 指出 `loginByAccountAndPassword` 並行調用時, 若同時走「先查既有 token 是否仍有效→無則新發」邏輯, 存在 check-then-act race condition, 可能同瞬間發出 2 張 token. 若強行修補此 race, 需引入 per-user lock / 序列化, 換來的卻是與業主多裝置需求衝突的「單 active token」語意.
- 不解決層面: race 修補的工程代價遠大於踩到的代價 (同帳號同一瞬間發 2 張 token, 兩張皆合法、皆可用, 並不造成資料污染或權限越界).

**Decision**:
- 採「同帳號多 active token 並存」模型: 每次 `loginByAccountAndPassword` 成功皆發新 token, **不 reuse 既有 token、不 invalidate 既有 token**.
- 同一裝置同一瀏覽器內已快取 token 時, 前端 `autoLogin` (mUI.mjs) 於 App 啟動階段 short-circuit, 直接以快取 token 入站, 不會重打 `loginByAccountAndPassword`. 故「重複登入打 API」場景僅出現於跨裝置 / 跨瀏覽器 / 清空 localStorage 後再登入.
- `logoutByToken` 只 invalidate **當下這張** token (清 localStorage + 後端刪除該 token record), 不影響同帳號其他裝置 active session.
- F-046 race 標為 **Accepted by design**, 不修.

**Consequences**:
- ✅ 跨裝置 / 跨瀏覽器多 active session 流暢, 對齊業主需求.
- ✅ 同瀏覽器內 reload 由 frontend autoLogin short-circuit, 不會反覆觸發後端發 token, 後端負載合理.
- ✅ 省去 per-user lock 工程複雜度與其衍生的死結 / 效能風險.
- ⚠️ 同一瞬間並行登入仍可能發出 2 張 token, 兩張皆合法可用 (無實質危害, 但 audit log 會看到 2 筆相鄰 token 簽發).
- ⚠️ 使用者懷疑帳號被盜時, 自助登出僅清掉「當下這張」token, 其他裝置 session 不受影響; 須走 admin 手動清 (或變更密碼後等既有 token 自然到期, 見 ADR-009 multi-device session 獨立).
- ⚠️ Admin 後台金鑰清單會出現同帳號多筆 active token, 屬預期行為, 不視為異常.

**Affected**:
- spec/流程_使用者一般登入.md
- spec/流程_使用者登出.md
- spec/流程_後台金鑰清單.md
- spec/流程_自動封鎖機制.md
- server/procCore.mjs (loginByAccountAndPassword / logoutByToken)
- src/plugins/mUI.mjs (autoLogin short-circuit)

## ADR-002: 訊息呈現分流 (modal / toast / inline)

**Status**: Accepted (2026-06-08)

**Context**:
- 早期程式碼混用 `alert()` / `$alert` / 自訂 modal 三種呈現方式, 一個流程結果有時走 modal、有時走 toast、有時走 inline 紅字, 體驗割裂.
- 全域 §5.1 已禁用瀏覽器內建 `alert()` (e2e 截不到圖、無法 pixel baseline). 但即使全面改成 DOM 模態, 仍須訂出**何時用哪一種**的契約, 否則「成功 modal / 失敗 modal / 例外 toast」混淆會讓使用者誤判操作是否成功.
- 不解決會踩到: e2e 視覺回歸缺口 (toast 4s 自動消失難 baseline)、使用者對「無感操作」與「失敗操作」分辨不清、跨流程體驗不一致.

**Decision**:
- **操作結果 (成功 / 可預期失敗)** → `vo.$dg.showCheckYes` 持久 modal, 須點 OK 才消失. 含: 註冊成功、變更密碼成功、admin 儲存 Users/IPs/Tokens 成功、重設密碼成功等.
- **非預期例外** (catch 區內無從預期之 throw / network down / 後端 500) → `vo.$alert(vo.$t('anUnexpectedErrorOccurred'), { type: 'error' })` 低調 toast, 4s 自動消失. 設計意圖: 非預期錯誤應低調, 用 modal 反而過度放大、傷感受可靠度.
- **欄位驗證** (帳號為空 / 密碼過短 / email 格式錯) → inline 紅字 (reactive error var), 不彈窗.
- **Yes/No 確認** (刪除前確認 / 解除權限前確認) → `vo.$dg.showCheckYesNo` modal.
- **載入失敗 fallback 區塊**: 初次 mount 之 getAndRelaData (LayoutContentUserInfor 用 `v-if="!firstLoading && !errMsg"`; LayoutContentStaInfor 自 ADR-051 P2 起改 `v-if="!errMsg"` + 各區塊自帶 loading 旗標/轉圈, 先到先畫) 控制主內容渲染, errMsg 有值時走 v-else 顯示 i18n 載入失敗訊息. 與其他 3 類訊息不同: (a) 阻塞性質介於 modal 與 inline 之間 (主內容隱藏, 但無 OK 按鈕需點); (b) 通常為「token 失效 / 後端不通」之系統性錯誤, 非單欄位驗證.
- 對齊 §5.1 「非同步提交的 core() + finally 統一寫法」: inline 錯誤於進 core() 第一步清空, 同步檢測階段填 inline 錯誤並 early-return, 確定要打 API 才開 loading, 外層 catch 才走 $alert 收非預期例外.

**Consequences**:
- ✅ 三種訊息類型一目了然, 使用者立刻分辨「我做的事成功了 / 我輸入的東西錯了 / 系統出了意料外的問題」.
- ✅ 持久 modal 與 inline 紅字皆可 pixel baseline e2e 回歸守護, 取代原本 alert / toast 的 e2e 盲區.
- ✅ 非預期錯誤的 toast 不放大警訊, 對偶發網路抖動友善, 不打斷使用者主流程.
- ⚠️ 新增流程時須在「結果 / 例外 / 驗證 / 確認」四種之間正確分類, 分錯會體驗錯位 (例如把可預期失敗丟去 toast 反而會被忽略).
- ⚠️ toast 4s 自動消失無法 pixel baseline, 故 e2e 對「非預期例外」case 僅做語意斷言 (text contains), 不做整頁 pixel 比對 — 此為設計取捨, 不視為測試缺口.

**Affected**:
- src/components/PageLogin.vue (register / login error handling)
- src/components/PageUser.vue (changePassword / forceChangePw)
- src/components/LayoutContentUsers.vue
- src/components/LayoutContentTokens.vue
- src/components/LayoutContentIps.vue
- src/components/LayoutContentStaInfor.vue
- src/components/LayoutContentUserInfor.vue
- spec/流程_使用者創建帳密.md
- spec/流程_使用者變更密碼.md
- spec/流程_後台新增使用者.md
- spec/流程_後台IP清單.md
- spec/流程_後台金鑰清單.md

## ADR-003: 防帳號列舉 — 失敗訊息統一化

**Status**: Accepted (2026-06-08)

**Context**:
- 登入 / 自助註冊 / 重寄驗證信流程皆面臨「帳號不存在 / 密碼錯誤 / 帳號停用 / 帳號未驗證 / 帳號過期」等多種失敗原因.
- 若前端直接呈現具體原因, 攻擊者可逐筆試帳號清單以推斷哪些帳號已存在 (account enumeration), 大幅降低後續鎖定攻擊 / 釣魚攻擊的成本.
- 不解決會踩到: 帳號列舉、admin 帳號被識別後遭針對性攻擊、與 `getSsoUserInfor` 限制 (ADR-004) 對齊原則受損.

**Decision**:
- 後端 `loginByAccountAndPassword` 之**主路徑 (base case)** 對外回傳統一字串 (`'incorrect user account or password'`) 涵蓋: 帳號不存在 (`_getGenUserByKV` 過濾 `isActive='y'` 後找不到, 含「真不存在」與「被停用」) + 密碼錯誤. 兩者共用同訊息防列舉.
- **例外**: 帳號狀態為「未驗證 (`timeVerified=''`)」或「已過期 (`timeExpired<now`)」之 user 仍走 distinct reject 字串 (`'account not verified'` / `'account expired'`), 前端對應 distinct UI (未驗證顯示重寄連結 / 過期顯示提示). 此處放鬆統一訊息原則, 以保留**未驗證 user 自助 resend 路徑** 與**過期 user 之明確說明** 為 UX 必要 trade-off — 見 Consequences ⚠️.
- 後端內部 log 對主路徑與例外路徑皆保留具體 reject 原因, 供 audit / 維運追溯.
- 前端 PageLogin 登入失敗 handler 將後端回傳訊息對應映射 (統一 → `failedLoginForCatch` / 未驗證 → `userRegistrationNotVerified` + resend 連結 / 過期 → `loginAccountExpired`), 不嘗試解析或補充細節.
- 自助註冊 (createUser) 之「帳號重複 / email 重複」訊息對外仍 distinct (`'account already exists'` / `'email already exists'`), 屬 ADR-003 例外, 由 R2L1-001 cacheSt 兩段獨立 key 機制守住並發 race 後仍須回明確訊息 (註冊 UX 需要使用者知道是 account 還是 email 已被占用).
- 重寄驗證信 (resendVerifyEmail) 之「帳號不存在 / email 不符」走統一 `'invalid account or email'` (不洩露存在性); 「已驗證」走 distinct `'account already verified'` (UX 取捨); 「30s throttle」走 distinct `'resend throttled'` (僅成功路徑後才寫入 throttle, 故第二次 distinct 訊息實際不洩額外列舉 bit — 第一次成功之 modal 已揭露帳號存在且未驗證, 屬可接受).

**Consequences**:
- ✅ 主路徑 (帳號不存在 / 密碼錯誤 / inactive routed via 過濾鏈) 統一訊息, 攻擊者無法以登入失敗訊息辨識帳號是否存在.
- ✅ 後端內部 log 保留 audit 細節, 不影響維運追查.
- ✅ 前端 PageLogin / register 共用同套呈現邏輯, 降低維護負擔.
- ⚠️ **未驗證 / 已過期 distinct reject 為 UX 必要保留 — 已知接受 trade-off**: 攻擊者於已猜中正確密碼之撞庫情境可額外獲得「該帳號狀態為未驗證 / 已過期」之 1 bit 資訊, 換取「未驗證 user 能從登入頁進入 resend 流程」與「過期 user 知道為何無法登入」之 UX. 業主 (2026-06-11 Round-3 audit) 決議走此取捨, 對應 spec/流程_使用者一般登入.md i18n 粒度表保留 distinct 訊息為設計契約. 替代方案 (嚴守 + 另開獨立 resend 頁) 工程成本過高, E2E-003~007 流程鏈須整體重設計; 替代方案 (嚴守 + 砍 resend UI) UX 損失過大.
- ⚠️ 真實使用者輸錯帳號時, 看不到「您打錯帳號」或「您的密碼錯了」的差異, 排查體驗略差 — 屬安全與 UX 的取捨.
- ⚠️ inactive 路徑走 `'can not find the user by account'` (procProtect 階段 reject, 不會走到 procCore line 307 之 `'account inactive'` — 該 reject 為 dead branch, 已於 Round-3 audit Phase 2 清除).
- ✅ db_query 之 NoSQL operator injection (account / email / password 缺 type check 可送 mongo operator 物件) 已於 Round-3 audit Phase 5 修復 (commit fd31c8c): kpfun 入口 `_strictStr` type guard (server/WWebSso.mjs) + procCore 內層 isestr 防呆 + updateXxxList array deep check. 原本即被 `_getGenUserByKV` duplicate check + `verifyPassword` 之型別/長度 guard 守住無 auth bypass, 此修復為深度防禦補強, 並杜絕 mingo 全表 scan DoS 與 log 噪音.

**Affected**:
- server/procCore.mjs (loginByAccountAndPassword line 290-356 / resendVerifyEmail line 879-989 之 reject 路徑分流)
- src/components/PageLogin.vue (line 783-814 login error mapping / line 694-715 resend error mapping)
- spec/流程_使用者一般登入.md (i18n 粒度表 + 執行流程)
- spec/流程_使用者創建帳密.md (resend i18n 粒度表)
- spec/流程_查詢使用者資訊.md
- server/WWebSso.mjs (`_strictStr` kpfun 入口 NoSQL operator injection type guard) + server/procCore.mjs (isestr 內層防呆) — Round-3 Phase 5 已修 (commit fd31c8c)

## ADR-004: `getSsoUserInfor` 收緊 IDOR — 限 admin / app caller

**Status**: Accepted (2026-06-08)

**Context**:
- `/api/getSsoUserInfor` 原開放給任何持有有效 token 的使用者呼叫, 可以「給定 userId / account / email」查詢任一使用者資訊.
- 結果: 任一登入使用者可窮舉所有 userId, 列舉系統內所有帳號 (含 admin 帳號) 並取得其基本資料 (姓名 / email / 角色), 屬 IDOR (Insecure Direct Object Reference) 漏洞.
- 不解決會踩到: 一般使用者可偵察到 admin 帳號, 接著針對 admin 做密碼噴灑 / 釣魚, 大幅降低系統整體安全性.

**Decision**:
- 收緊 `getSsoUserInfor` 為 caller mode (a): `{ fun: funCheckAdmin }`, 僅 admin 使用者或 app token 可呼叫.
- 利用 app token 的 `isApp='y'` 自動 bypass `fun` 檢查的語意 (見 ADR-005), `funCheckAdmin` 一個檢查同時涵蓋「admin 使用者」與「app token」兩種合法 caller, 不需新增 `funCheckAdminOrApp`.
- 一般使用者欲查自己資訊改走 `getUserByToken` (token 即身份, 無 IDOR 風險).

**Consequences**:
- ✅ 阻擋一般使用者列舉系統帳號, 消除 IDOR 漏洞.
- ✅ app token 仍可正常呼叫此 API 做 server-to-server 查詢, 不影響系統整合場景.
- ✅ 利用 ADR-005 `isApp` bypass 機制, 程式碼簡潔, 無新增權限分類.
- ⚠️ 若系統未來新增「使用者可查其他使用者」之需求 (例如 user directory), 須另開 endpoint 並重新設計權限. 此 API 不可再放寬.

**Affected**:
- server/WWebSso.mjs:1135, 1114, 1341 (getSsoUserInfor 路由與 RPC 入口)
- server/procCore.mjs:397 (isApp bypass 語意)
- spec/流程_查詢使用者資訊.md

## ADR-005: App token (`isApp='y'`) 跳過 `fun` 驗證

**Status**: Accepted (2026-06-08)

**Context**:
- 系統需要兩類 caller 身份: (1) 經 `loginByAccountAndPassword` 取得 token 的使用者; (2) 內部系統 / 第三方整合服務以預配 app token 直接呼叫 API.
- 若每個受保護 endpoint 都要寫「先試 user `fun` 檢查 → 失敗再試 app token 檢查」雙路徑, 程式碼會大幅重複, 且易遺漏其中一條.
- 不解決會踩到: 維運須為每個 endpoint 分別維護 user / app 兩套權限檢查, 一不慎就漏寫導致 app 整合失敗或權限放寬.

**Decision**:
- App token (建立時 `isApp='y'`) 於 `_checkTokenByObj` (procCore.mjs:409) 階段自動 bypass `fun` 檢查 — 不論 handler 傳入的 `opt.fun` 是 `funCheckAdmin` / `funCheckUser` / 其他, 一律視為通過, 由此 token 持有人 (app) 被視為 admin 等級身份.
- App token 僅供「內部簽發」, 不對外開放使用者自助建立 (註冊流程無從產生 `isApp='y'` token). 信任邊界由「token 簽發過程」守住, 而非「驗證過程」.
- Handler 端只需寫一個 `fun` (通常為 `funCheckAdmin`) 即可同時授權「admin 使用者」與「app token」.

**Consequences**:
- ✅ 每個受保護 endpoint 只寫一個 `fun` 檢查, 同時涵蓋兩類合法 caller, 程式碼簡潔.
- ✅ 信任邊界集中於「token 簽發」, 不分散於各 endpoint, 易於 audit.
- ✅ 與 ADR-004 `getSsoUserInfor` 收緊機制無縫對齊, 同一個 `funCheckAdmin` 服務兩類合法 caller.
- ⚠️ 一旦 app token 外洩, 等同 admin 帳號外洩, 後果嚴重. 須將 app token 視為高敏資料, 限制傳遞通路與儲存方式.
- ⚠️ 未來若需新增「app token 不應做 X 但 admin 可以」之差異化權限, 此設計無法直接表達, 須擴充驗證機制.

**Affected**:
- server/procCore.mjs:397, 412 (`_checkTokenByObj` `isApp` bypass)
- server/WWebSso.mjs (所有 `{ fun: funCheckAdmin }` 之 handler)
- spec/流程_查詢使用者資訊.md

## ADR-006: `checkToken` 對外統一 `'token expired'`

**Status**: Accepted (2026-06-08)

**Context**:
- Token 驗證可能因多種原因失敗: token 不存在 (從未簽發或已被刪)、token 過期、token 對應 user 已被停用、token 對應 user 不符 `fun` 要求 (例如非 admin 卻打 admin 限定 API).
- 若 API 對外回傳不同 reject 訊息, 攻擊者可透過試探不同 token 值反推出 (a) 哪些 token 字串「曾存在過」(token 不存在 vs token 過期訊息不同)、(b) 哪些帳號被停用、(c) 哪些帳號是 admin.
- 不解決會踩到: token / 帳號狀態 / 角色之 information leakage, 削弱 ADR-003 防列舉與 ADR-004 IDOR 收緊的成效.

**Decision**:
- `checkToken` (procCore.mjs:521) 對外一律回傳 `'token expired'` 字串, 不論真實 reject 原因為何 (不存在 / 過期 / user 停用 / 不符 fun).
- 後端內部 `_checkToken` 仍保留具體布林與字串分流, 供 log 與內部呼叫者判斷.
- 此原則同樣套用於 `getSsoUserInfor` / stats endpoints / 其他經 `funCheckAdmin` 的 API: 不符權限的 caller 一律看到 `'token expired'`, 不暴露「你的 token 有效但你不是 admin」之差別.

**Consequences**:
- ✅ 攻擊者無法從 reject 訊息推斷 token / 帳號 / 角色狀態, 全面對齊 defense-in-depth.
- ✅ 內部 log 仍保留 audit 細節, 不影響維運.
- ✅ 與 ADR-003 防帳號列舉、ADR-004 IDOR 收緊形成一致的「對外不洩露細節」契約.
- ⚠️ 真實 token 過期的使用者與「token 仍有效但權限不足」的使用者看到同訊息, 客服排查時須以後端 log 為主, 不能單靠使用者回報的訊息判別.
- ⚠️ 前端見到 `'token expired'` 一律走「清 LS token + 跳回登入頁」流程, 若使用者實際是權限不足 (例如非 admin 誤入 admin 頁面), 也會被登出 — 屬可接受的副作用, 與權限模型對齊.

**Affected**:
- server/procCore.mjs:483, 524 (checkToken / `_checkToken` 統一 reject 訊息)
- spec/流程_查詢使用者資訊.md (E2E-002 描述 unified 'token expired' 行為)
- spec/流程_使用者自動登入.md

## ADR-007: Password hash 比對採 `crypto.timingSafeEqual`; token 比對使用 `===`

**Status**: Accepted (2026-06-08)

**Context**:
- 密碼比對若使用 `===` 短路比對, 理論上字串前綴匹配長度愈長、比對時間愈長, 攻擊者可透過遠端計時推測 hash 內容 (timing side-channel).
- 實務上: 帳號自動封鎖 (ADR-013) 已大幅限制可探測次數, 遠端 timing 攻擊在本系統環境下不切實際. 但 defense-in-depth 原則仍應採時間恆定比對.
- Token 比對則為另一情境: token 為 UUIDv7 (128-bit entropy), 純隨機, 無前綴規律可言; 加上 LMDB in-memory 儲存, 比對快至毫秒以下, timing 訊號被網路抖動完全淹沒, 攻擊不可行.
- 不解決會踩到: 密碼若採 `===` 雖實質安全, 但無法回應 audit 對 best-practice 的要求; token 若強行套 timing-safe 比對, 徒增複雜度無實質防禦.

**Decision**:
- **Password hash 比對**: 走 `verifyPassword` helper (`server/hashPassword.mjs:53`), 其內部以 `crypto.timingSafeEqual` (`hashPassword.mjs:97`) 做固定時間比對, 並先做長度檢查 (防 DB corruption / 空字串造成 throw). 用於 `loginByAccountAndPassword` (procCore.mjs:321) 與 `changeUserPassword` (procCore.mjs:1093) 之密碼驗證.
- **Token 比對**: 保留 `===` (procCore.mjs:458), 標註設計意圖 — UUIDv7 entropy + LMDB in-memory 已足夠, timing-safe 無實質收益.
- 兩種比對在程式碼中明確區隔, 不可後續一視同仁套同一種比對.

**Consequences**:
- ✅ Password 比對達 best-practice timing-safe, 回應 audit defense-in-depth 要求.
- ✅ Token 比對保留簡潔 `===`, 不引入無意義的複雜度.
- ✅ 兩種比對的設計意圖明示於 code comment (procCore.mjs:43, :461), 後續維護者不會誤判.
- ⚠️ 若未來改用其他 token 簽發機制 (例如可預測短字串 token), 須重新評估是否要切換為 timing-safe 比對 — 此 ADR 之決策建立在 UUIDv7 假設上.

**Affected**:
- server/hashPassword.mjs:53 (verifyPassword helper, 內含 crypto.timingSafeEqual @ :97)
- server/procCore.mjs:305 (loginByAccountAndPassword)
- server/procCore.mjs:458 (token `===` 比對, 設計註記)
- server/procCore.mjs:1041 (changeUserPassword 舊密碼驗證)
- spec/流程_使用者一般登入.md
- spec/流程_使用者變更密碼.md

## ADR-008: Admin 寫入後即時 invalidate 30s cache

**Status**: Accepted (2026-06-08)

**Context**:
- 後台 Users / Tokens / IPs 三份清單與其 stats 查詢 (procStaInfor) 套用 30s read-through cache (wsemi cache), 大幅降低高頻外部讀取對 DB 的負載.
- 但 admin 在後台對清單做寫入 (新增 user / 修改 IP 白名單 / 撤銷 token) 後, 若必須等 30s cache 自然過期才看到變更, 體驗很差 — admin 會以為「儲存沒成功」並重複點擊, 引發 ADR-012 寫入後 race / 重複 commit.
- 不解決會踩到: admin 寫完看不到結果、重複送、UX 與資料一致性兩頭損.

**Decision**:
- 每個 admin 寫入路徑 (`checkTokenAndUpdateUsersList` / `checkTokenAndUpdateTokensList` / `checkTokenAndUpdateIpsList`) 於**成功寫入後**立即呼叫 `cache.clear('fun')` 對應 key, 清掉相關 list 的 cache.
- Cache invalidation 必須放在「寫入成功後」, 不放在 reject 路徑 — 寫入失敗時 DB 未變、cache 不應清, 反而會增加無謂的 DB 重抓.
- 採 wsemi cache `needExec=true` 機制: 清空後保留 TTL 設定不變, 下次讀取觸發重新計算並重設 30s TTL.
- 外部高頻讀取 (例如 stats summary 被多前端 polling) 仍享 30s cache 加速; 只有「admin 剛寫入」這條時序窗口會繞過 cache.

**Consequences**:
- ✅ Admin 寫入後 dashboard 立刻同步, 無 30s 等待延遲.
- ✅ 外部高頻讀取仍享 cache 加速, 系統整體負載不受 invalidation 影響.
- ✅ Cache 與 DB 一致性由「寫入即清」契約保證, 不會出現「DB 已更新但 cache 仍舊」之窗口 (對 admin 視角而言).
- ⚠️ 多 admin 並發寫入時, 兩次 invalidation 可能相鄰但仍正確 — 每次 invalidation 後緊接的下一次讀取都會 trigger 重抓, 不會殘留舊資料.
- ⚠️ 若未來新增「非 admin 路徑」的寫入 (例如使用者自助更新某欄位), 須同步加上對應 cache invalidation, 否則會出現「使用者寫了但 stats 仍舊」.

**Affected**:
- server/procCore.mjs:1669, 1733, 1791 (checkTokenAndUpdate*List 之 cache 清除)
- server/procStaInfor.mjs:46 (cache read 端)
- spec/流程_後台新增使用者.md
- spec/流程_後台變更使用者資訊.md
- spec/流程_後台刪除使用者.md
- spec/流程_後台IP清單.md
- spec/流程_後台金鑰清單.md
- spec/流程_後台統計資訊.md

## ADR-009: Multi-device session 獨立 (變更 / 重設密碼後不清除既有 token)

**Status**: Accepted (2026-06-08)

**Context**:
- 使用者變更密碼 (主動) 或 admin 重設使用者密碼 (被動) 後, 既有的多裝置 active token 是否要全部 invalidate?
- 若強制 invalidate: 安全性較好 (假設密碼被盜, 重設後立刻趕走所有 session), 但與 ADR-001 multi-session 接受相衝突 — 使用者只是定期變更密碼也會被踢下所有裝置, 體驗極差.
- 若不 invalidate: 既有 token 持續可用至自然到期, 多裝置體驗順暢, 但若密碼真的被盜, 攻擊者持有的 token 仍可繼續使用至到期.
- 不解決會踩到: 安全性與 UX 兩頭擺盪, 無清楚契約.

**Decision**:
- 採「不清除既有 token」策略: 變更密碼 (流程_使用者變更密碼) 與重設密碼 (流程_後台重設使用者密碼) 後, 既有 token 不被 invalidate, 多裝置可繼續使用至自然到期 (見 ADR-010 token 效期).
- 使用者若疑似帳號被盜, 須額外由 admin 走「後台金鑰清單」手動撤銷該帳號所有 token, 或等既有 token 自然到期 (預設 `minExpired` 分鐘, 通常數小時).
- 此決策對齊 ADR-001 multi-session 接受 — 同一信念: 「session 生命週期由 token 自身控制, 不被密碼操作牽動」.

**Consequences**:
- ✅ 變更密碼為日常維運操作, 不打斷多裝置體驗, 對齊業主需求.
- ✅ 與 ADR-001 multi-session 接受形成一致的 session 模型, 不出現「multi-session 但密碼變更就清空」的不一致.
- ✅ 對齊「token 即身份」原則 — token 一旦簽發, 其有效性由自身 `timeEnd` 控制, 不受其他欄位影響.
- ⚠️ 密碼真的外洩時, 攻擊者持有的 token 不會立即失效, 仍可用至到期; 此為已知 trade-off, 對應的緊急應變方案為「admin 手動撤銷所有 token」.
- ⚠️ Spec 明確記載此為設計取捨, 不視為 audit finding.
- ✅ **v3 re-audit D-β 重新確認**: critic 質疑 adminResetPassword 之典型情境(帳號疑似被盜)下舊 session 不失效與 ADR-037(停用即時撤 token)不對稱. 業主拍板維持現狀(D39): 本 ADR 之 Decision 段已明列此情境之緊急應變路徑(admin 手動撤銷所有 token), 與 ADR-037「明確禁止意圖才即時撤」之區分原則一致, 非遺漏, 不追加程式碼變更.

**Affected**:
- server/procCore.mjs (changeUserPassword / adminResetUserPassword 不觸及 token table)
- spec/流程_使用者變更密碼.md
- spec/流程_後台重設使用者密碼.md
- spec/流程_使用者自動登入.md

## ADR-010: Token 效期與 session 管理約定 (`minExpired`, localStorage 清空慣例)

**Status**: Accepted (2026-06-08)

**Context**:
- Token 簽發、自動登入、登出三條流程須共用同一套 token 生命週期定義, 否則前端與後端會對「token 何時失效」「LS 何時清空」做不同假設.
- 不解決會踩到: 登出後 LS 殘留舊 token 字串、自動登入誤判失效 token 為有效、token 自然到期前後行為不一致.

**Decision**:
- Token 建立時 `timeEnd = now + minExpired` 分鐘 (`minExpired` 由 settings.json 設定, 預設數小時等級).
- 登出時前端將 LS token **設為空字串** (`localStorage.setItem('token', '')`), 非 `removeItem`. 此慣例讓「未曾登入」與「登出後」皆呈現空字串, 自動登入端統一以 `isestr(token)` 判 falsy.
- 自動登入啟動時讀 LS token, 若 `isestr` 為 falsy 則直接視為未登入, 不打後端 API; 若 truthy 則送後端 `checkToken` 驗證, 後端依 `timeEnd` 判斷.
- Token 自然到期不主動清 LS — 由下一次自動登入呼叫 `checkToken` 時被後端拒, 前端再清 LS + 跳登入頁.

**Consequences**:
- ✅ 三條流程共用同一 token 生命週期定義, 前後端假設一致.
- ✅ LS 空字串慣例讓「未登入」與「登出」狀態統一, 簡化 autoLogin 入口判斷.
- ✅ Token 自然到期由後端權威判斷, 前端不做時鐘比對, 避免前端時鐘漂移造成的不一致.
- ⚠️ 使用者登出後 LS 仍留 token key (值為空字串), 在某些 LS 偵測工具看來會被誤判為「有此 key」. 屬已知慣例.
- ⚠️ Token 自然到期前 (例如剩 1 分鐘) 使用者仍可進行操作, 中途突然失效 — 前端須對所有受保護 API 的 `'token expired'` reject 統一處理 (清 LS + 跳登入頁).

**Affected**:
- server/procCore.mjs (loginByAccountAndPassword / logoutByToken / checkToken)
- src/plugins/mUI.mjs (autoLogin / setToken / clearToken)
- src/App.vue (initialization)
- spec/流程_使用者一般登入.md
- spec/流程_使用者自動登入.md
- spec/流程_使用者登出.md
- spec/流程_使用者變更密碼.md

## ADR-011: cleanTokens timer disabled (token 不主動清掃)

**Status**: Accepted (2026-06-08)

**Context**:
- 早期設計考慮過「定期 timer 掃描 tokens table, 把已過 `timeEnd` 的 token 自動刪除」以節省 DB 空間.
- 但實作後發現: timer 觸發時若該 token 對應之 user 仍在使用 (browser tab 開著未關), 即便 token 已過 `timeEnd` 也可能仍持有 — 自動清除等於把使用者強制踢下線, 與 ADR-001 multi-session 接受 / ADR-009 多裝置獨立精神衝突.
- 不解決會踩到: 使用者 SSO session 在莫名時間被踢、無預警跳回登入頁、體驗破裂.

**Decision**:
- cleanTokens timer **disabled**, 不主動清掃過期 token.
- 過期 token 改由「下次被 checkToken 驗證時」自然判定為失效 (見 ADR-010), 此時前端會清 LS 並跳登入頁, 對使用者而言是「我打開頁面才看到要重新登入」, 而非「我正在用就突然被踢」.
- 已過期但未被驗證的 token 仍留在 DB, 由 admin 後台金鑰清單檢視 (此清單不過濾過期, 見 ADR-012).
- DB 空間影響微乎其微 (token record 小、UUIDv7 + 少數欄位), 不需主動回收.

**Consequences**:
- ✅ 使用者 session 體驗一致 — 只有「自己嘗試操作」時才會看到要重新登入, 永不被無預警踢線.
- ✅ 對齊 ADR-001 / ADR-009 的 session 獨立精神, 系統不主動操弄 session 生命週期.
- ✅ 省去 timer 邏輯與其潛在 race condition (例如清掃時剛好有 refresh / login 寫入).
- ⚠️ 過期 token 累積於 DB, 長期看 token table 會持續增長. 預計每年增長量可接受 — 若未來需空間回收, 須另開 admin 手動 / 批次清掃機制, 不可重新啟用定期 timer.
- ⚠️ Admin 後台看到大量過期 token, 須以 `timeEnd` 欄位自行判讀, 對應 ADR-012.

**Affected**:
- server/procCore.mjs (cleanTokens 函式或對應 timer 註冊處)
- server/procProtect.mjs
- spec/流程_後台金鑰清單.md
- spec/流程_使用者自動登入.md

## ADR-013: 帳號自動封鎖採「隱性解除」(比對當前時間, 不主動清 `timeBlocked`)

**Status**: Accepted (2026-06-08)

**Context**:
- 連續登入失敗超過閾值時, 系統將 `users.timeBlocked` 寫為「現在 + 封鎖分鐘數」, 之後比對來判斷該帳號是否仍被封鎖.
- 封鎖時間到期後如何「解除」? 兩種選項: (a) 顯性 — 用 timer 定期掃描, 把已到期的 `timeBlocked` 清空; (b) 隱性 — 不主動清, 只在每次查詢時用「現在 vs timeBlocked」比對判定.
- (a) 涉及額外 timer 邏輯、可能與寫入操作 race; (b) 簡單但須保證所有查詢點皆採同樣比對邏輯.
- 不解決會踩到: 封鎖到期後行為不一致、timer 與寫入 race、額外維運負擔.

**Decision**:
- 採 (b) 隱性解除: 不主動清 `timeBlocked` 欄位, 解除完全靠「當前時間 vs timeBlocked」比對.
- 所有判定封鎖狀態的位置統一走 `procCore.getBlockedByUser` (account 自動封鎖) 與 `procCore.getBlockedByOip` (IP 自動封鎖), 兩函式內部統一比對邏輯, 不在各 caller 自行比對.
- `timeBlocked` 欄位永久保留歷史封鎖時間, 同時作為 audit 紀錄 (admin 可看到該帳號何時曾被封鎖).
- 對應 IP 封鎖機制同此原則, 見 spec/流程_自動封鎖機制.md.

**Consequences**:
- ✅ 省去 timer 邏輯與 race condition.
- ✅ `timeBlocked` 同時兼任 audit 欄位, 不需額外封鎖歷史 table.
- ✅ 所有判定點統一函式入口, 比對邏輯一致, 不會出現「某處判到期、某處沒判」的差異.
- ⚠️ 須保證**所有**查詢封鎖狀態之處都走 `getBlockedByUser` / `getBlockedByOip`, 不可有 caller 自己讀 `timeBlocked` 後做比對 — 否則容易遺漏隱性解除邏輯造成永久封鎖.
- ⚠️ 過期 `timeBlocked` 累積於使用者欄位 (每次新封鎖會 overwrite), 不會無限增長, 屬可接受.
- ✅ 2026-07-06: 程式碼已對齊本決策 — 移除早於本 ADR 之 procCore cleanUsers/cleanIps 每 2 秒清空 timer (該 timer 為 2025-07 舊實作, 與本決策矛盾且會抹除 audit 欄位值).

**Affected**:
- server/procCore.mjs:getBlockedByUser, getBlockedByOip
- server/procProtect.mjs
- spec/流程_自動封鎖機制.md
- spec/流程_使用者一般登入.md (登入時封鎖檢查)

## ADR-014: API 回傳前剝除 `password` 欄位

**Status**: Accepted (2026-06-08)

**Context**:
- `users` table 之 `password` 欄位儲存 hash 值. 即便為 hash 而非明文, 仍不應隨任何 API 回傳暴露於外 — 一旦外洩, 攻擊者可離線暴力比對.
- 多個 API 回傳 user 物件 (後台 Users 編輯、新增、查詢使用者資訊), 若任一條漏寫剝除邏輯就會洩露 hash.
- 不解決會踩到: hash 隨 API 回傳洩露、攻擊者離線比對風險、相關 audit 不通過.

**Decision**:
- 所有回傳 user 物件之 API 統一在回傳前剝除 `password` 欄位.
- 統一在 `procCore.getGenUserByKV` (或其衍生) 回傳路徑做剝除, 而非各 handler 自行處理 — 集中於一處降低遺漏風險.
- 此原則延伸至: `checkTokenAndUpdateUsersList` (新增 / 修改回傳)、`checkTokenAndDeleteUsers`、`getSsoUserInfor`、`getUserByToken` 等所有暴露 user 物件之 endpoint.

**Consequences**:
- ✅ Hash 值不隨任何 API 洩露, 攻擊者無法離線比對.
- ✅ 集中剝除於一處, 不會因某 handler 漏寫而洩露.
- ✅ 與 ADR-003 / ADR-004 / ADR-006 對外不洩露細節的整體契約對齊.
- ⚠️ 內部 RPC 若需要 password (例如登入時驗證) 須走另一條路徑 (`procCore` 內部函式, 不經 API), 不可圖方便直接讀剝除後的物件.
- ⚠️ 未來新增「回傳 user 物件」之 endpoint 時, 須確認走過統一剝除路徑, 不可自行 query DB 後直接回傳.

**Affected**:

## ADR-015: Stats 頁 e2e baseline 截 cards 區 (y:0..330) 排除動態 chart

**Status**: Accepted (2026-06-08)

**Context**:

- 對應全域 §6.2 「測試是規格的翻譯」: cards 區的語意斷言 (具體數值文字) 為主, baseline 補強視覺整體回歸.

**Consequences**:
- ✅ Stats 頁 e2e baseline 穩定可重現, 不再受 chart 動態渲染影響.
- ✅ Cards 區的視覺回歸 (i18n / layout / icon) 仍受守護.
- ✅ 維護成本降低, 不需反覆 regen 因 chart 微差導致的 flake.
- ⚠️ Chart 視覺改動 (例如 chart 換 library / 配色) 不被 e2e baseline 抓到, 須額外做人工 UAT.
- ⚠️ 若未來業主新增 cards 至 `y > 330` 之區域, 須調整截圖範圍.

**Affected**:

- test/pics/stainfor/ (baseline 圖檔)
- spec/流程_後台統計資訊.md

## ADR-016: E2E hermetic seed lifecycle (resetToBaseSeed + insertTestUsers + deleteNonBaseSeed)

**Status**: Accepted (2026-06-08)

**Context**:
- E2E 測試彼此並行 / 順序執行時, 若共用 DB 而無清楚邊界, 一條測試殘留的 user / token / IP 會污染下一條測試的初始狀態, 造成 pixel baseline flake (對應全域 §6.3 「pixel 不一致 5 類成因」之第 1 類 DB 內容不同).
- 但若每條測試「整個 DB 清空再 seed」, e2e 啟動時間爆炸, 跑全套套件耗時不可接受.
- 不解決會踩到: e2e 跨測試污染、baseline flake、測試彼此耦合難 debug.

**Decision**:
- 採「base seed + 特化 seed」雙層: base seed (admin user + 必要基礎資料) 為所有 e2e 共用初始狀態, 測試啟動前由 `resetToBaseSeed` 重置至此.
- 個別 e2e 於 `before()` / 自己的 setup 階段以 `insertTestUsers` (或同類 helper) 插入本檔特化資料 (例如 `id-login-ok` user).
- 個別 e2e 於 `after()` / cleanup 階段以 `deleteNonBaseSeed` 移除本檔特化資料, 不動 base seed.
- 此契約使每條 e2e 「進場時 DB 等於 base seed」「出場時 DB 等於 base seed」, 順序 / 並行皆 hermetic.
- 對應全域 §6.3 rubric §5「Cleanup 完整」.

**Consequences**:
- ✅ E2E 彼此 hermetic, 不互相污染, baseline pixel 比對可靠.
- ✅ 不需「整個 DB 清空」, base seed 為共用基礎, 啟動成本可接受.
- ✅ Setup 與 cleanup 對稱, 防止測試殘留累積.
- ⚠️ Base seed 內容變動 (例如新增 admin 帳號 / 新增基礎 IP 白名單) 須同步更新所有 e2e 的預期, 屬統一變更負擔.
- ⚠️ 若 e2e 測試本身就是「驗證 admin 自我鎖死」(ADR 外的 spec 規則, 但相關), 須留意 base seed admin 不能被該測試刪除, 否則破壞 hermetic 契約.

**Affected**:
- test/e2e-setup.mjs (resetToBaseSeed / insertTestUsersAndTokens / deleteNonBaseSeed helpers)
- test/e2e-*.test.mjs (所有 e2e 檔)
- server/g_initialData.mjs (base seed 定義)

## ADR-018: 寄信失敗不阻擋流程結果 (SMTP fail 僅 log, 不 reject)

**Status**: Accepted (2026-06-08)

**Context**:
- 自助註冊 (寄驗證信)、重寄驗證信、變更密碼 (寄通知信)、後台重設密碼 (寄通知信) 等流程皆涉及寄信. SMTP 服務可能因外部因素失敗 (郵件供應商 down / 暫時 throttle / DNS 抖動).
- 若 SMTP 失敗就 reject 整個流程, 使用者註冊不成功、admin 重設密碼失敗 — 對「主操作」之 UX 影響大且非使用者本身的錯.
- 不解決會踩到: 寄信偶發失敗導致主流程整批失敗, 使用者反覆嘗試、admin 操作體驗破裂.

**Decision**:
- 寄信統一採 fire-and-forget 模式: 主流程 (例如 `createUser` / `changeUserPassword` / `adminResetUserPassword`) 完成 DB 寫入後觸發寄信, 寄信失敗僅記 console / log, **不 reject** 主流程.
- 使用者 / admin 視角為主操作成功 (帳號已建立 / 密碼已變更); 寄信若失敗, 使用者可主動走「重寄驗證信」流程補救, 或 admin 走 audit log 追查.
- 此契約由 `procCore.mjs` 寄信呼叫點之 `.catch(err => console.log(...))` 模式統一表達.

**Consequences**:
- ✅ 主流程不被外部 SMTP 抖動拖累, UX 穩定.
- ✅ 主操作成功之 DB 狀態與使用者視角一致, 不出現「使用者以為失敗但 DB 已寫入」之矛盾.
- ✅ 提供補救機制 (重寄驗證信 / audit log), 寄信失敗有可挽回路徑.
- ⚠️ 使用者可能完成註冊但收不到驗證信, 須自行察覺並走重寄 — 屬已知 UX 代價.
- ⚠️ 寄信失敗的 log 須有人定期檢視 (或上 alerting), 否則大量失敗會無聲累積. 屬維運責任, 不在程式碼契約內.

**Affected**:
- server/procCore.mjs (createUser / changeUserPassword / adminResetUserPassword 寄信呼叫點)
- server/template/*.html (email template)
- spec/流程_使用者創建帳密.md
- spec/流程_使用者變更密碼.md
- spec/流程_後台重設使用者密碼.md

## ADR-019: 強制變更密碼不可繞過 (`isForceChangePw` 旗標 + UI 鎖死)

**Status**: Accepted (2026-06-08)

**Context**:
- Admin 重設使用者密碼後, 使用者下次登入時須被強制變更密碼 (不可使用 admin 給的隨機密碼一直登入). 若使用者可繞過 (例如 close modal 後繼續使用), 安全強制流程失去意義.
- 不解決會踩到: 隨機密碼長期可用、admin 重設意圖被繞過、與 ADR-001 multi-session 對齊的「token 不被牽動」精神反而成為漏洞 (重設後 token 不失效 + 不強制變更 = 完全繞過).

**Decision**:
- Admin 重設後寫入 `users.isForceChangePw = 'y'`.
- 使用者下次登入後 (或自動登入後), 前端偵測該旗標, 自動展開變更密碼表單.
- 表單**取消按鈕隱藏** (只剩送出), 不可關閉 / 不可 close modal.
- 使用者唯一離開路徑為**登出**; 登出後重新登入仍會被拉回強制變更表單 (旗標未清).
- 變更密碼成功後, 後端清 `isForceChangePw` 旗標, 使用者恢復正常流程.

**Consequences**:
- ✅ 安全強制流程不可繞過, admin 重設意圖確實落地.
- ✅ 與 ADR-009 multi-device session 獨立並存 — token 不被 invalidate, 但使用者拿 token 進來後仍被強制變更.
- ✅ 使用者體驗清楚 — 只有兩條路: 改密碼 or 登出.
- ⚠️ 使用者若拒絕變更密碼, 等同放棄此帳號 (登出即等於無法回到後台). 屬安全前提.
- ⚠️ 強制流程的 UI 須與一般變更密碼共用 component 但動態隱藏取消鈕, 須謹慎處理 component 重用避免漏隱藏.

**Affected**:
- server/procCore.mjs (adminResetUserPassword 寫入旗標, changeUserPassword 清除旗標)
- src/components/PageUser.vue (偵測 `isForceChangePw` 展開表單, 隱藏取消鈕)
- spec/流程_後台重設使用者密碼.md
- spec/流程_使用者變更密碼.md

## ADR-021: 後台批次 upsert 契約 (`ltdtDiffByKey` add/diff/del 三分支, 整批 atomicity)

**Status**: Accepted (2026-06-08)

**Context**:
- 後台 Users / IPs / Tokens 三份清單採「整張表編輯」模式 — admin 在前端表格中任意新增 / 修改 / 刪除多列, 按「儲存」一次送出整張表的最新狀態.
- 後端須判斷哪些列是新增 / 修改 / 刪除, 並對每類各自驗證. 若任一列驗證失敗該如何處理?
- 不解決會踩到: 部分列成功部分失敗導致 DB 半邊資料, 或前端表格與 DB 狀態不一致.

**Decision**:
- 後端統一以 `ltdtDiffByKey` 比對前端送來的整張表 vs DB 現狀, 拆為 add / diff / del 三組.
- 對每組分別走對應驗證 (`ckKey` 檢查整表唯一性、欄位格式檢查、自我鎖死檢查 ADR-020 等).
- **任一驗證失敗整批 reject 不落地** — atomicity 由「全部驗證完才寫」契約守住.
- 寫入成功後立即 invalidate cache (見 ADR-008).

**Consequences**:
- ✅ DB atomicity 保證, 不會出現部分列成功部分失敗的中間狀態.
- ✅ Add / diff / del 三組分別處理, 各自的驗證邏輯不混淆.
- ✅ 與 ADR-008 cache invalidate-on-write 對齊, 寫入後 dashboard 立刻同步.
- ⚠️ Admin 一次編輯整張表時, 任一列錯誤導致整批 reject, 須回前端修正後重送; 若表很大且只錯一列, 重送的網路成本較高 — 屬可接受.
- ⚠️ 並發兩 admin 同時編輯同一張表, 後送者會以「自己看到的版本」覆蓋前送者的變更 (last-write-wins). 多 admin 並發編輯非設計重點, 屬已知限制.

**Affected**:
- server/procCore.mjs (checkTokenAndUpdateUsersList / TokensList / IpsList, updateTabItems)
- src/components/LayoutContentUsers.vue
- src/components/LayoutContentTokens.vue
- src/components/LayoutContentIps.vue

## ADR-022: 自助註冊驗證信採 server-rendered 結果頁 (非 SPA redirect)

- ⚠️ 結果頁無 i18n runtime 切換 — 使用者一進此頁就是當初註冊時的語系, 中途無切換鈕. 屬合理範疇.

## ADR-023: 多裝置 cleanKp endpoint 採 IP 白名單 (不信 X-Forwarded-For)

**Status**: Accepted (2026-06-08)

**Context**:
- `cleanKpIpCallApi` 與 `cleanKpAccountLoginFailed` 為 e2e 測試 cleanup 用 endpoint, 可重置 in-memory rate-limit / 自動封鎖計數器.
- 若這兩 endpoint 接受任意 caller, 攻擊者可外部觸發以繞過自動封鎖機制 (ADR-013).
- IP 限制若依 X-Forwarded-For header 判斷, 攻擊者可偽造 header. 須直接以 socket 層級 client IP 判斷.
- 不解決會踩到: 自動封鎖機制被外部 reset, 無法守住暴力試密碼閘.

**Decision**:
- `cleanKpIpCallApi` 與 `cleanKpAccountLoginFailed` 入口檢查 `socket.remoteAddress` (真實 TCP 連線來源), 不採 X-Forwarded-For.
- 來源 IP 須在 settings 中明確白名單清單內 (預設僅 127.0.0.1), 不在則 reject.
- E2E 測試於 localhost 跑, 天然滿足白名單; production 環境無此 endpoint 對外使用案例.

**Consequences**:
- ✅ 即使部署於 reverse proxy 後方 (proxy 帶 X-Forwarded-For), 此 endpoint 仍只信實際 TCP 連線來源, 無法被外部偽造繞過.
- ✅ 自動封鎖機制不會被外部 reset, defense-in-depth 完整.
- ✅ E2E cleanup 場景仍可用, 不影響測試可達性.
- ⚠️ 若未來部署架構變動 (例如真的需要從 proxy 後方某 trusted host 呼叫), 須擴充白名單機制 (例如允許多個白名單 IP / 子網), 不可改為信 X-Forwarded-For.
- ⚠️ Reverse proxy 配置不當時 (proxy 把 client IP 直接當 socket.remoteAddress 而非 X-Forwarded-For) 可能整套錯位, 屬部署層責任.

**Affected**:
- server/WWebSso.mjs:849, 879 (cleanKp* handlers IP 檢查)
- server/procProtect.mjs (getIpByHeaders 一般使用者流程, 與此契約對照)
- spec/流程_自動封鎖機制.md

## ADR-024: 前端 autoLogin cache-priority (LS token 優於 URL `?token`)

**Status**: Accepted (2026-06-08)

**Context**:
- 系統支援兩種 token 進入路徑: (a) localStorage 已快取的 token (上次登入留下); (b) URL `?token=...` 帶入 (例如其他系統 redirect 過來).
- 若兩者同時存在, 採用哪個? 若採用 URL token, 攻擊者可構造帶 token 的 URL 騙使用者點擊, 使用者瀏覽器原有 LS token 被覆寫, 等於被劫持 session.
- 若採用 LS token, 已有合法 session 的使用者不會被 URL 帶來的 token 偷換掉; 但需注意「使用者主動清 LS 後從別處 redirect 過來」之合法場景仍能進.
- 不解決會踩到: URL token 劫持風險.

**Decision**:
- `autoLogin` (mUI.mjs:520 區段) 優先使用 LS cached token; 若 LS 存在 truthy token, 即使 URL 帶 `?token=` 也忽略.
- 若 LS 為空 (`isestr` falsy), 才採用 URL `?token=`. 採用後寫入 LS, 後續一切以 LS 為準.
- 此契約使「single trusted session source = LS」成立, URL token 僅為「初次進入」之引導.

**Consequences**:
- ✅ 已登入使用者不會被 URL 帶來的 token 劫持, session 安全性提升.
- ✅ 仍支援「從外部系統 redirect 帶 token 進來」之合法場景 (LS 空時自動採用 URL token).
- ✅ 與 ADR-010 「localStorage 空字串慣例」對齊, `isestr` 判 falsy 為單一判定入口.
- ⚠️ 使用者若想「強制切換到 URL 帶來的新 token」, 須先手動登出 (清 LS), 再從 URL 進; 屬合理流程.
- ⚠️ 開發 / debug 時若想以 URL token 覆蓋當下 session, 須先清 LS, 體驗略繁瑣 — 屬可接受工程代價.

**Affected**:
- src/plugins/mUI.mjs:520 (autoLogin cache priority)
- src/App.vue (autoLogin 入口)
- spec/流程_使用者自動登入.md

## ADR-025: Secondary stats API 採 fire-and-forget (主 API 控 loading)

**Status**: Accepted (2026-06-08)

**Context**:
- 統計資訊頁 (LayoutContentStaInfor.vue) 同時呼叫多支 stats API: 主 API (例如 `getStaUserAccountLogin`) + 多個 secondary API (`getStaUserSummary` / `getStaTokenSummary` / `getStaIpSummary` 等).
- 若全部 await 串接, 任一 secondary 失敗會打斷所有更新; 若全部 `Promise.all`, 任一 reject 也會整批失敗.
- 不解決會踩到: 一個 secondary 失敗導致整個 dashboard 不顯示資料, 過於脆弱.

**Decision**:
- 主 API (`getStaUserAccountLogin`) 控制 `isLoading` state, 主資料就緒後立刻關 loading.
- Secondary API 採 fire-and-forget — 各自送 request 後不 await, 完成則更新對應 reactive 欄位, 失敗則空 catch (`.catch(() => {})`) 內部 console.log 不擴散.
- 任一 secondary 失敗時, 該卡片顯示「-」或舊資料, 其他卡片照常更新; 主 API 失敗時才整個 dashboard 顯示錯誤.

**Consequences**:
- ✅ Dashboard 對 secondary API 抖動有韌性, 不會因單一支失敗就整個變空白.
- ✅ Loading state 由主 API 控, 使用者看到的反應時間與「最關鍵資料」對齊, 不受 secondary 拖累.
- ✅ Secondary 失敗的 log 可供日後排查, 不靜默吞錯.
- ⚠️ Secondary 卡片可能顯示「-」, 使用者不易察覺是 API 失敗還是真實無資料; 若需精準分辨, 須額外加 per-card 錯誤顯示.
- ⚠️ Fire-and-forget 下若 secondary 回應極慢, 使用者已切走頁面後才回來, 可能寫入已被 dispose 的 reactive 欄位; 需確認 component unmount 後不再寫入 (一般 Vue reactive 系統會自動處理, 但須留意).

**Affected**:
- src/components/LayoutContentStaInfor.vue:732 (5 secondary API 空 catch 區塊)
- server/procStaInfor.mjs (各 stats summary 函式)
- spec/流程_後台統計資訊.md

## ADR-026: 未驗證帳號重寄機制採同欄位 overwrite (非獨立 token 表)

**Status**: Accepted (2026-06-08)

**Context**:
- 自助註冊建立 user 但 email 尚未驗證之階段, 驗證 token 須儲存於某處供後續驗證信點擊比對. 兩種選項: (a) 獨立 verification token 表, 每次重寄新增一筆; (b) 存於 `users.tokenVerify` 單一欄位, 重寄時 overwrite.
- (a) 可保留歷史 token、但須額外清理機制; (b) 簡潔、自然「最新一封信有效」.
- 不解決會踩到: 重寄機制過於複雜、歷史 token 累積、或舊驗證信仍有效造成混淆.

**Decision**:
- 採 (b): 驗證 token 存於 `users.tokenVerify` 欄位, 重寄時直接 overwrite 舊 token.
- 重寄後舊驗證信 link 自動失效 (token 已被覆寫, 後端比對不符).
- 驗證成功後同時更新 `users.timeVerified` (記錄驗證時間) 並清空 `tokenVerify` (此後無 active token 留存).

**Consequences**:
- ✅ 設計簡潔, 不需獨立 verification token 表 / 清理 timer.
- ✅ 重寄機制天然 idempotent — 不論寄幾次, 最新一封信有效, 不會有「兩封同時有效造成混淆」.
- ✅ 驗證後 `tokenVerify` 清空, audit 視角清楚 (該帳號當前無 pending verification).
- ⚠️ 使用者若點到舊信會看到「驗證失敗」, 須提示其改點最新信; 屬合理體驗.
- ⚠️ `tokenVerify` 與 `timeVerified` 兩欄位的狀態組合 (有 token + 無 timeVerified = 未驗證 / 無 token + 有 timeVerified = 已驗證 / 有 token + 有 timeVerified = 不應發生) 須在所有查詢點正確判讀.

**Affected**:
- server/procCore.mjs (createUser / resendVerifyEmail / verifyEmailByToken)
- users table schema (`tokenVerify`, `timeVerified` 欄位)
- spec/流程_使用者創建帳密.md
- spec/流程_使用者一般登入.md

## ADR-027: 登入成功後視圖分流 (`view` 參數優先級)

**Status**: Accepted (2026-06-08)

**Context**:
- 登入 / 自動登入成功後, 使用者該被導到哪個頁面? 三種可能: (a) 走 `redir` URL (外部 redirect 來源)、(b) 停留後台 (`view=backstage`)、(c) 停留使用者頁 (`view=user`).
- 三者觸發條件混亂時, 體驗會錯亂 (例如從外部 SSO 進來但被丟到使用者頁, 而不是 redirect 回原系統).
- 不解決會踩到: 登入後體驗錯位、外部 SSO 整合斷裂.

**Decision**:
- 採三分支分流, 由 URL `?view=` 參數驅動:
  - `view=login` (預設, 或從外部 redirect 進來) → 登入成功後走 `redir` 轉址回原系統.
  - `view=backstage` → 登入成功後停留後台.
  - `view=user` → 登入成功後停留使用者頁.
- `view` 參數於登入頁 URL 上由前端或外部 redirect 帶入; 預設 `view=login` (對齊外部 SSO 整合主場景).
- 此分流規則自動登入 (autoLogin) 同樣適用 — 已快取 token 進來時仍依 `view` 決定停留處.

**Consequences**:
- ✅ 三種使用場景 (外部 SSO / 直接後台 / 直接使用者頁) 皆有明確路徑.
- ✅ 與 ADR-001 multi-session 接受並存 — 各裝置可獨立指定 `view` 進入不同頁面.
- ✅ `view` 為 URL 顯式參數, 前後端皆可直接讀取, 不靠隱性狀態.
- ⚠️ 三分支須在 mUI.mjs / PageLogin.vue / PageUser.vue 共用判讀邏輯, 不可任一頁自行假設預設值. 屬契約共識.
- ⚠️ 未來若新增第四種視圖場景 (例如 `view=admin-only`), 須同時更新所有判讀點.

**Affected**:
- src/plugins/mUI.mjs (view 分流邏輯)
- src/components/PageLogin.vue
- src/components/PageUser.vue
- spec/流程_使用者一般登入.md
- spec/流程_使用者自動登入.md
- spec/流程_使用者變更密碼.md

## ADR-029: checkUserPassword 端點未認證 (F-005)

**Status**: Accepted (2026-06-08)

**Context**:
- server/WWebSso.mjs:1191 之 `kpfun.checkUserPassword` RPC 不呼叫 checkToken, 任何人皆可不認證地打.
- 用途: 純政策驗證 (密碼長度 / 字元種類 / blacklist / 不含帳號連續字), 回傳 success 或 i18n 錯誤訊息.
- 三條呼叫鏈合理需求未認證: (a) 註冊時 user 尚無 token; (b) 變更密碼時雖有 token 但此純驗證不需; (c) 後台 admin 新增 user.
- Audit F-005 質疑: 全域 IP rate limit (verifyConn) 是否足夠抵禦 wordlist enumeration 與政策反推?

**Decision**:
- 採接受並文件化, 不加額外 per-token / per-IP-per-endpoint rate limit.
- 理由:
  1. **密碼政策不是 secret**: 業界普遍認為密碼政策本就不應視為敏感資訊 (多數網站註冊頁本就明列「至少 N 字 / 含大小寫 / ...」). 本系統 PageLogin.vue 註冊模式已採「reactive 提示」(使用者輸入後 i18n inline 紅字顯示具體規則), 攻擊者隨便打幾個字即得完整政策內容, 此 endpoint 並未額外洩露更多.
  2. **真實 brute force 已被 autoblock 擋住**: 同帳號 5 次失敗即鎖, wordlist 預篩之後的真實打點仍會被攔截.
  3. **此 endpoint 不洩露帳號存在性**: WWebSso.mjs:1191 handler 只傳 (lang, pw), opt.account 為空, noConsecutiveCharsFromAccount 政策對 account 之比對不會回傳「此 account 存在」的訊號.
  4. **加 rate limit 的工程成本中, 收益低**: botnet 散到多 IP 可繞過 per-IP 限流; per-token 限流保護不到註冊路徑 (註冊無 token).

**Consequences**:
- ✅ 不引入 per-IP-per-endpoint counter 之新 in-memory state 複雜度.
- ✅ 註冊與變更密碼之 inline 即時驗證 UX 保留.
- ✅ autoblock 仍守住真實帳號 brute force 攻擊面.
- ⚠️ 攻擊者可慢速 wordlist 預篩通過政策的候選, 但實際打 loginByAccountAndPassword 仍被 autoblock 攔, 無實質帳號接管風險.
- ⚠️ 攻擊者可探出政策參數 (minLength / 字元要求 / blacklist 範圍), 但此資訊本就視為公開 (註冊頁 reactive 提示已暴露相同資訊).
- ⚠️ PageUser.vue 變更密碼模式目前無 client-side 政策提示 (僅 server reject 後 inline 紅字), 與註冊頁體驗不一致. 屬可改善之 UX 議題, 但不影響本 ADR 安全結論 (政策不論顯式或反應式皆為公開資訊).

**Affected**:
- server/WWebSso.mjs:1191 (RPC handler)
- server/procCore.mjs:998 (checkUserPassword 純函式)
- src/components/PageLogin.vue 註冊模式 (reactive 政策提示 line 105-109 + computed regPasswordErrors line 519-549)
- src/components/PageUser.vue 變更密碼模式 (現無 client-side 政策提示, 僅 server reject 後 chPwNewError inline 紅字)
- 對齊 ADR-013 autoblock 帳號鎖定 (真實 brute force 防線)

## ADR-030: 部署拓樸 — 單機單 process 假設 (F-047 / F-048 / F-049 / F-055)

**Status**: Accepted (2026-06-08)

**Context**:
- Audit F-047 揭露 createUser TOCTOU race 之修法強烈依賴部署拓樸假設: 單機 → in-process mutex 即足, cluster → 須 DB-level unique constraint 或分散式 lock.
- 另 F-048 (kpAccountLoginFailed 計數 race) / F-049 (kpTokenCallApi / IpCallApi timer race) / F-055 (blockAccount timeBlocked lost update) 同樣依賴拓樸假設.
- 多條既有 ADR 之機制也基於此假設: ADR-008 admin 寫入後即時 invalidate 30s cache (in-process Map.clear) / ADR-013 帳號自動封鎖 in-memory state (in-process kp* counters) / ADR-023 cleanKp endpoint IP 白名單 (socket.remoteAddress) / ADR-033 pmKeyMutex (wsemi) in-process per-key mutex.

**Decision**:
- 業主拍板**單機單 process 部署** (PM2 fork mode = 1 instance / 單機 docker 一個 container / 開發環境直跑).
- 不採用 cluster / 多 pod / 多 instance 部署模型.
- 既有所有「in-process state / in-process mutex / in-process cache」機制視為**足夠且正確**, 不引入 Redis / DB-level unique constraint / 分散式 lock 等複雜度.

**Consequences**:
- ✅ **F-047 createUser TOCTOU 已解掉**: 初版用 per-key in-memory mutex 之複合 key `'createUser:account:email'`, 後續 audit R2L1-001 揭露此複合 key 在「同 account 不同 email」並行下不互斥, 改用 wsemi `cacheSt()` 之 `cst.setWithFree(['createUser:account:<a>', 'createUser:email:<e>'], fn)` 多 key 原子占位 + auto-cleanup (TTL), 兩段獨立 key 任一衝突即 reject (procCore.mjs:83 `let cst = cacheSt()`, :815). 單機 process 內 in-memory 即等於完全互斥.
- ✅ **F-054 adminResetUserPassword race 同上**, 已透過 ADR-033 `kmx('adminResetUserPassword:${targetUserId}', fn)` 序列化 + 30s throttle 解掉 (詳 ADR-031). `kmx` 為 wsemi `pmKeyMutex()` 實例 (procCore.mjs:77).
- ✅ ADR-008 admin 寫入後 `ocGetXxxList.clear()` 即時 invalidate 30s cache 對單機 dashboard 即時同步, 無需 inter-process 通知.
- ✅ ADR-013 帳號自動封鎖之 in-memory kpAccountLoginFailed / kpTokenCallApi / kpIpCallApi counters 單機共用, autoblock 觸發門檻精確.
- ✅ ADR-023 cleanKp endpoint 採 socket.remoteAddress 為 IP 來源可信 (單機直連, 無 LB X-Forwarded-For 偽造空間).
- ✅ **F-048 / F-049 / F-055 三條 in-process counter race 視為可接受 cosmetic**:
  - **F-048** kpAccountLoginFailed 計數 read-modify-write race: 單機 JS event loop 同步 await 邊界仍有窄 window, 但最多失敗計次少算 1 次, autoblock 門檻仍會觸發 (5 次失敗即鎖), ±1 偏差對安全無實質影響.
  - **F-049** kpTokenCallApi / kpIpCallApi 與 timer overwrite race: 同上理由, rate limit 視窗錯亂之最大偏差為秒級, 對 attack throughput 無實質緩解差.
  - **F-055** blockAccount 並行寫 timeBlocked lost update: 多並行請求寫 timeBlocked 都寫到「未來相近時間」, 取後者覆蓋前者, autoblock 仍生效, 僅 audit log 紀錄秒級不確定.
- ⚠️ **未來若需 cluster 化, 須新增 ADR superseding 此條** + 補對應修法: F-047/F-054 加 schema unique constraint 或 Redis-based distributed lock; F-048/F-049/F-055 計數搬離 in-memory 改 DB row + optimistic lock; ADR-008 cache invalidate 改 pub/sub; ADR-013 in-memory state 同款; ADR-023 socket IP 改信任 LB 的 X-Forwarded-First. 屬重大架構變更, 須整體重新評估.
- ⚠️ 開發環境 / staging 模擬 cluster 須明示, 不可隱性切換.

**Affected**:
- 對齊 ADR-008 (cache invalidate-on-write)
- 對齊 ADR-013 (帳號自動封鎖 in-memory state)
- 對齊 ADR-023 (cleanKp endpoint IP 白名單)
- 對齊 ADR-033 (按鈕雙擊防護 pmKeyMutex / cacheSt in-process)
- wsemi/src/pmKeyMutex.mjs (per-key in-process mutex; npm 套件)
- wsemi/src/cacheSt.mjs (多 key 原子占位 + TTL auto-cleanup, 供 createUser 用 R2L1-001 fix)
- server/procProtect.mjs (kpAccountLoginFailed / kpTokenCallApi / kpIpCallApi in-memory counters)

## ADR-031: adminResetUserPassword 並行 race 修補 (F-054)

**Status**: Accepted (2026-06-08)

**Context**:
- Audit F-054 揭露兩 admin 同時對同 user 點 Reset password 之 race 後果具體: lost update DB + 兩封不同明文密碼信寄出, user 收信但只有後一封可登入, UX 與安全嚴重混淆.
- 雙擊調研 DC-01 揭露單一 admin 快速雙擊同 button 撞同款 race (modal-before-loading 空窗最嚴重).
- 兩條 race 同源, 修法相同.

**Decision**:
- 採 ADR-033 三層防護收掉:
  1. **元件層**: `LayoutContentUsers.vue` 之 Reset password button 加 `:promiseUnlock="true"`, 第一次 click 立即上鎖, admin 點 Yes 並 resolve 之前無法雙進入 modal.
  2. **後端層**: `server/procCore.mjs` 之 `adminResetUserPassword` 函式 (:1215) 以 `kmx('adminResetUserPassword:${targetUserId}', async () => {...})` 序列化 + 鎖內 30s throttle (in-memory `lastResetTime` Map). `kmx` 為 wsemi `pmKeyMutex()` 實例 (procCore.mjs:77 `let kmx = pmKeyMutex()`). 同 targetUserId 並行被序列化, 鎖內第 2 次 throttle 命中 reject i18n key `'adminResetPasswordAlreadyTriggered'` (procCore.mjs:1220).
- 對齊 ADR-030 單機部署假設: in-process mutex + throttle Map 對單機 process 即等於完全互斥.

**Consequences**:
- ✅ DC-01 / F-054 race window 收掉, e2e regression `test/api-doubleclick.test.mjs` 之 `E2E-DC-01-admin-reset-double` 並行 2 次 reset 確認第 2 次 reject i18n key `'adminResetPasswordAlreadyTriggered'`.
- ✅ 兩 admin 同時 reset 同 user 場景: 第 2 個 admin 之 reset 被 30s throttle 擋, 顯示 throttle 訊息給 user, 第 1 個 admin 之 reset 不受影響.
- ⚠️ 若兩 admin 同 user reset 間隔 > 30s, 第 2 次 throttle 過期可重新觸發, 與單一 admin 兩次 reset 同款合理路徑.
- ⚠️ in-process throttle Map 在 process restart 後清空, 重啟瞬間之 throttle 視窗失效. 重啟頻率極低, 影響可忽略.
- ⚠️ 對齊 ADR-030 單機假設: cluster 化後 throttle Map 不跨 process 互斥, 需重新評估 (見 ADR-030).

**Affected**:
- src/components/LayoutContentUsers.vue (Reset password button 加 promiseUnlock)
- server/procCore.mjs (adminResetUserPassword 以 `kmx(key, fn)` 序列化 + 30s throttle; kmx 為 wsemi pmKeyMutex() 實例, :79)
- wsemi/src/pmKeyMutex.mjs (in-process per-key mutex helper; npm 套件)
- test/api-doubleclick.test.mjs E2E-DC-01 case
- 對齊 ADR-033 (按鈕雙擊防護分層)
- 對齊 ADR-030 (單機部署假設)

## ADR-032: verifyEmail 採 lazy clear, 不主動清 tokenVerify (F-053 race 修補)

**Status**: Accepted (2026-06-08)

**Context**:
- verifyEmail 與 resendVerifyEmail 並發時存在 read-check-save race: verifyEmail 讀 user 後 resendVerifyEmail 寫新 tokenVerify, verifyEmail 再寫 tokenVerify='' 把新 token 覆蓋, 導致使用者收到新驗證信但點下去顯示 'verifyEmailInvalidToken'.
- Audit F-053 揭露此 race, 機率極低 (需 1ms 內並發兩動作) 但體驗具體不良 (使用者剛收信點下去就無效, 困惑).
- 修法選項: (a) DB UNIQUE on tokenVerify 不可行 (空字串多 user 都有), (b) optimistic lock 仍有窄 race window + 複雜, (c) lazy clear (不清 tokenVerify) 一行解.

**Decision**:
- verifyEmail 成功路徑只設 timeVerified=now, **不主動清空 tokenVerify**.
- 已驗證 user 之 tokenVerify 仍保留舊值 (或被 resendVerifyEmail 後續覆寫為新值), 由 verifyEmail 入口之 `if (isestr(timeVerified)) reject 'verifyEmailAlreadyVerified'` 攔截 token 重用嘗試.

**Consequences**:
- ✅ 一行修補消除 race window (拿掉 tokenVerify: '').
- ✅ 不引入 lock / optimistic concurrency / DB constraint 複雜度.
- ✅ resendVerifyEmail 並發場景: 新 token 不被覆蓋, 使用者點新連結仍能驗證 (或得友善訊息).
- ⚠️ 已驗證 user 之 DB 紀錄 tokenVerify 欄位可能留有舊字串 (非空), 屬無害雜訊; 資料庫稽核 view 須理解此設計 (空字串 ≠ 已驗證, 須看 timeVerified).
- ⚠️ 若日後追加 「tokenVerify 為 admin 解密查詢條件」之功能, 須避開 verifyEmail 後 tokenVerify 仍非空之假設.

**Affected**:
- server/procCore.mjs (verifyEmail 函式體 — 拿掉 tokenVerify: '')
- spec/流程_使用者創建帳密.md (驗證信段更新)

## ADR-033: 按鈕雙擊防護分層

**Status**: Accepted (2026-06-08)

**Context**:
- 使用者快速雙擊提交按鈕可造成重複 API 呼叫: 重複插入資料 (createUser TOCTOU) / 重複寄信 (resendVerify) / 重複密碼變更 + 兩封信 (adminResetUserPassword 最嚴重).
- 全專案 36 個 WButtonCircle 用 0 次 promiseUnlock, 防護完全依賴 §5.1 canonical `updateLoading` 全頁 overlay, 在「sync 檢測 → overlay 開啟」之間有空窗; 對 modal-before-loading 之 case (adminResetUserPassword 點 Reset → showCheckYesNo → 點 Yes 才開 overlay) 空窗變更長.

**Decision**:
採三層防護, 每層獨立但互補:
1. **元件層 (frontend)**: 有副作用的提交按鈕用 WButtonCircle / WButtonChip 之 `:promiseUnlock="true"`, 第一次 click 立即上鎖 `loadingTrans=true`, caller 解 pm.resolve/reject 才解鎖. 比 `updateLoading` 早一層, sync 檢測都過不了第二次.
2. **頁面層 (frontend)**: `updateLoading(true)` 全頁 overlay 保留, 防 async API 期間的全頁互動. §5.1 canonical 不變.
3. **後端層 (backend)**: critical 路徑用 per-key in-process mutex / cacheSt 多 key 原子占位防 API 直打 / e2e race / 自動化攻擊繞過前端:
   - `adminResetUserPassword` / `changeUserPassword` / `resendVerifyEmail` 用 wsemi `pmKeyMutex()` 實例 `kmx` (procCore.mjs:77 `let kmx = pmKeyMutex()`), 以 `kmx(key, async () => {...})` 序列化同 key 並行 (procCore.mjs:931 / :1081 / :1215)
   - `createUser` 改用 wsemi `cacheSt()` 實例 `cst` (procCore.mjs:83 `let cst = cacheSt()`) 之 `cst.setWithFree([keyAccount, keyEmail], fn)` 多 key 原子占位 + TTL auto-cleanup (R2L1-001 fix: 原複合 key `'createUser:account:email'` 在「同 account 不同 email」並行下走不同鎖完全不互斥, 改 cacheSt 兩段獨立 key 任一衝突即 reject, procCore.mjs:812)

**Consequences**:
- ✅ 防使用者快速雙擊造成的資料污染 (DC-01 / DC-02 critical 議題收掉).
- ✅ 防 API 直打繞過前端: 後端 mutex 是最後一道防線.
- ✅ 不依賴單一防線 (defense-in-depth), 即使 frontend overlay 失效, backend mutex 仍守.
- ⚠️ pmKeyMutex / cacheSt 為 in-process only; cluster 多 process 部署下不互斥. 對齊 ADR-030 Accepted 「單機單 process 假設」(2026-06-08 業主拍板).
- ⚠️ `kmx` 對同 key 並行為**序列化**執行 (非直接 reject); 鎖內以 throttle / 唯一性檢查決定第 2 次是否 reject, 對外回 i18n key (adminResetUserPassword → `adminResetPasswordAlreadyTriggered`, resendVerifyEmail → `userRegistrationResendThrottled`, changeUserPassword 第 2 次密碼已改走 `userChangePasswordIncorrectOld`); createUser 之 `cst.setWithFree` 衝突 remap 回 `userRegistrationAccountExists` / `userRegistrationEmailExists`. 前端須以 `$tErr(err)` 顯示該 key (inline 紅字 / 忽略).
- ⚠️ promiseUnlock 改動會影響既有 e2e baseline (button 渲染含 loading icon 時可能 byte 不同), 須對應重產 baseline.
- ⚠️ **無自動 enforcement 機制**: 不採 PR template / lint rule / pre-commit hook, 依賴 CLAUDE.md「按鈕雙擊防護 (ADR-033)」段之文字規範 + 開發者 / agent 主動套 + 定期 audit 健檢 (grep `WButtonCircle` / `WButtonChip` 對比 `:promiseUnlock` 使用率). 業主拍板 (2026-06-08): enforcement 之工程成本 > 預期收益 (邊界判斷主觀: cancel / toggle 等按鈕不該套, lint rule 之 false positive 會煩死人), 此規範屬「文化層共識」非「機械層強制」.
- ⚠️ **handler 一律 method 名, 禁 inline async arrow**: 初版 ADR-033 4 顆按鈕全採 `@click="async ({pm}) => { try { await fn(); pm.resolve() } catch (e) { pm.reject(e) } }"` 寫法 → 全 e2e regression 61 fail (ChangePassword/Register/Login/ResetPassword/AutoLogin/Tokens[cht]). 根因: Vue 2 template compiler fnExpRE `/^([\w$_]+|\([^)]*?\))\s*=>|^function/` 不認 `async` 前綴 → arrow 被當 statement 包進 `function($event){<stmt>}` → Babel 編成「IIFE 定義 `_ref2` 但永不呼叫」 → handler 邏輯永不執行 → `pm.resolve` 永不觸發 → `loadingTrans=true` 永不重置 → button 永久卡鎖. 修法: 全部改 method 名 (對齊 w-component-vue 官方 `promiseUnlock` 範例; PageLogin.vue `onClickRegisterBtn` / `onClickResendVerifyBtn`, PageUser.vue `onClickSubmitChangePasswordBtn`, LayoutContentUsers.vue `onClickModifyItemPasswordByIdBtn` — 後者因須取 slot scope `props.row.id` 用 non-async arrow `(msg) => onClickXxxBtn(msg, id)` bridge). 全域 CLAUDE.md §5.1 已記入規則 + 識別 grep 指令.
- ⚠️ **`pm.resolve()` 一律放 handler 第一行 + fire-and-forget innerFn (議題 2 fix)**: 上一輪 `@click="async ({pm}) => { await fn(); pm.resolve() }"` 改成 method 名後仍 fail 5 個 baseline pixel drift (A.1/A.2/A.5/A.6/A.7), 根因: handler `await vo.fn()` → fn 內部 `await showCheckYes(...)` 等使用者點 modal OK 才解 → button `loadingTrans=true` 鎖到 modal 關閉 → e2e captureStable 在 modal 開啟期間截到 button loading 中 → 跟 PRE-ADR-033 OLD baseline (button 無 lock) byte 不同. 深查 w-component-vue 官方範例 + JSDoc 確認: **pm.resolve 設計意圖只是「釋放視覺鎖」, 不該 gate 在下游 modal 關閉**. 修法 canonical: handler 同步函式, 第一行立刻 `msg.pm.resolve()`, 再 `vo.fn()` fire-and-forget. 理由: ① 同步雙擊由 WButtonChip clickBtn 內 `if (loadingTrans) return` 擋 (pm.resolve 在 handler 第一行觸發後, pm.finally 仍是 $nextTick 才執行, 同 tick 內第二次 click 進不去); ② 非同步雙擊由 fn 內部 `updateLoading(true)` 全頁 overlay 接管 (對齊 §5.1 canonical); ③ modal 開啟期間使用者本就無法雙擊 button (modal 阻擋互動). 4 顆 button 全採此 pattern (PageUser.vue / PageLogin.vue × 2 / LayoutContentUsers.vue). 全域 CLAUDE.md §5.1「`promiseUnlock` button handler 之 `pm.resolve()` 一律放 handler 第一行」已記入完整規則 + 反模式 + 例外 + 識別 grep.

**Affected**:

## ADR-034: 後端錯誤訊息 i18n 統一 — reject key 字串 (key-only 契約)

**Status**: Accepted (2026-06-13)

**Context**:
- 後端錯誤原本 reject 「raw 英文人話字串」(`'token expired'` / `'account not verified'` / `'incorrect old password'` 等), 前端各 component catch 以 raw 字串 `if (errMsg === 'account not verified')` 判斷種類 + `$t(key)` 自行翻譯.
- 三個問題: (1) 以 raw 英文字串當判斷依據脆弱 — 後端改字串前端即壞; 且前端自行翻譯違反「前端不該知道 i18n key」之分層. (2) 部分 case 直接內插 raw 英文 → 中英混雜 (E2E-011: modal「儲存使用者數據失敗: token expired」中文 prefix + 英文 raw). (3) 翻譯邏輯散在前端各 catch, 跨流程不一致.
- 業主原則 (2026-06-12): 「錯誤處須提供 key 與訊息 — key 供後端 log 識別, 訊息需有 lang 才能產製回傳, 否則前端不知道 key 是什麼」. canonical 既有範例 = verifyEmail HTTP handler (底層 reject key 名 `'verifyEmailInvalidToken'` → handler 依 `?lang=` 查 kpLang 渲染).

**Decision**:
- 後端錯誤統一 reject **i18n key 字串** (key-only 契約; 非 `{ key, msg }` 物件, 後端不翻譯):
  - **底層 (procCore / procProtect)** reject **i18n key 名** (= procLang 字典 key), 供前端判斷種類 + 後端 log.
  - **kpfun 邊界層 (server/WWebSso.mjs)** 原樣 re-throw 底層之 key 字串, **不包成 `{ key, msg }`、不在後端翻譯** (WWebSso.mjs:546-548 註解明示 key-only 契約; 全 repo 無 `_tErr` 函式定義). 邊界層只在入口型別不符時映射為對外乾淨 key (如 `'tokenExpired'` / `'failedLoginForCatch'` / `'invalidRows'`).
  - **前端 catch**: 以 err 字串值判斷行為 (如 PageLogin.vue:769 `if (err === 'userRegistrationNotVerified')` → showResendVerify), 並以 `$tErr(err)` 翻譯 key 字串顯示 (`$tErr` = mUI.mjs:235 `getKpTextErr`, main.js:35 註冊; 內部 `getKpText(key)` 取模板 + 插值密碼政策值, 字典查無則回 key 本身).
- 技術前提 (已實測): reject key 字串經 w-converhp 序列化 → client `Promise.reject(...)` 無損傳到前端 catch.
- login 鏈須由前端 (mUI) 傳 `lang` 給 kpfun (login 原無 lang; lang 供後端 log / 寄信渲染用, 非用於翻譯回傳錯誤).

**Consequences**:
- ✅ 中英混雜根治 (E2E-011 等 modal 全中文/全英文依 lang).
- ✅ 前端以穩定 key 判斷種類, 不依賴 raw 英文字串 (後端改訊息文字不影響前端邏輯).
- ✅ 翻譯統一在前端 `$tErr(key)`, 前端 catch 收斂為「以 err 字串值判斷種類 + `$tErr(err)` 翻譯顯示」, 不再 raw 英文字串 if-else + `$t`.
- ✅ baseline 多數不需重產 — 顯示訊息前後相同 (同 i18n key 之翻譯, 翻譯統一收斂於前端 `$tErr(key)`); 僅 token-expired 中英混雜 case 需重產.
- ⚠️ **changePassword 例外**: 前端 catch 統一顯示 `userChangePasswordFail` (anti-information-leakage, 不洩漏「舊密碼錯」vs「token 失效」; PageUser.vue:482 忽略後端回傳之具體 key 不做 `$tErr`), 但後端仍 reject 具體 key (`userChangePasswordIncorrectOld`, procCore.mjs:1102) 供 log 識別 — 後端具體 key、前端統一訊息之刻意設計.
- ⚠️ **server-to-server REST endpoint 例外**: `getSsoUserInfor` / `getSsoUsersList` 非 kpfun, 回 machine-readable key (`'tokenExpired'`) 給 API caller 自行處理, 不翻譯 (與 kpfun key-only 契約一致, 差別僅在前端無 `$tErr` 翻譯層).
- ⚠️ internal invariant violation (`duplicate token` / `failed to find user` 等不該發生之錯誤) 統一收斂為 `anUnexpectedErrorOccurred`, 不逐一翻譯 (前端走 generic, 後端 log 保留 raw, 對齊 ADR-030 Round-3 audit C1 分類).
- ⚠️ **無自動 enforcement**: 新增 reject 須回 i18n key 名而非 raw 人話 (邊界層原樣 re-throw); 前端須以 `$tErr(key)` 翻譯顯示. 依賴 commit/ADR 文字規範 + 定期 audit (grep `Promise.reject` 之 raw 英文).

**Affected**:
- server/WWebSso.mjs (kpfun 邊界層原樣 re-throw 底層 key 字串, 不包 `{ key, msg }` / 不翻譯, 見 :513-515 key-only 契約註解; loginByAccountAndPassword / updateTokensList / updateIpsList 加 lang 參數)

## ADR-035: 密碼雜湊改 scrypt + per-user salt + pepper 強制 (D01 / D19 / D21 / D23)

**Status**: Accepted (2026-06-26)

**Context**:
- 早期密碼雜湊為「單次 SHA-512 + 全域共用 salt」: 共用鹽既是 KDF 鹽又是唯一防護, 無法防 rainbow table / precompute — DB 一旦外洩, 攻擊者可對全表共用同一張預算表離線比對.
- SHA-512 為快速雜湊, 非記憶體困難 (memory-hard) KDF, GPU 暴力速率極高, 不符 OWASP Password Storage 標準.
- pepper (伺服器端額外祕密) 原以 settings.json 之 `salt` 欄位字面值承載, 預設為佔位符 `{salt}`; 若生產環境忘了注入真實高熵值即上線, pepper 形同虛設.
- 不解決會踩到: DB 外洩後密碼可被離線批量破解、audit 不通過 best-practice、pepper 預設佔位符之誤上線風險.

**Decision**:
- **演算法改 Node `crypto.scryptSync` (記憶體困難 KDF) + per-user 隨機 salt**: 每筆密碼於雜湊時以 `crypto.randomBytes(16)` 產生獨立 per-user salt (16 bytes), 嵌入回傳字串; 即使 DB 全表外洩亦無法以單一 rainbow table 一次破解 (hashPassword.mjs:42 saltBuf, :46 scryptSync, KEYLEN=64 / SALTLEN=16 hashPassword.mjs:24,27).
- **自描述儲存格式 `scrypt:saltHex:hashHex`**: 演算法標記 + per-user 鹽 + 雜湊值打包成單一字串 (hashPassword.mjs:49), verifyPassword 自字串解析鹽與雜湊 (hashPassword.mjs:60-65), 不需於 DB 另開鹽欄位, 便於日後演算法遷移辨識.
- **settings `salt` 降為「可選 pepper」**: 不再是 KDF 鹽, 只與明文混合 (`` `${pw}:${salt || ''}` `` hashPassword.mjs:45 / verifyPassword hashPassword.mjs:90) 後再以 per-user 鹽做 scrypt; pepper 經 `SALT` 環境變數注入 (生產) 或 settings 佔位符 (測試).
- **D21 pepper 強制 (拒啟逃生閘)**: 後端啟動時若 pepper 為空或等於佔位符 `{salt}` 則**拒啟 throw** (WWebSso.mjs:176-178): 生產須經 `SALT` env 注入真實高熵 pepper; 測試 / 開發可設 `ALLOW_PLACEHOLDER_SALT=1` 逃生閘沿用佔位符 (測試密碼非機密, WWebSso.mjs:177-180 放行並 `[WARN]` log). `SALT` env 於 `g_getSettings.mjs:59-60` 注入 `st.salt` (取代 settings 佔位符), 種子端 pepper 於 `g_initialData.mjs:8` 同源 (`process.env.SALT || '{salt}'`).
- **D19 破壞性 / 不向後相容**: `verifyPassword` **只認 scrypt 格式** (tag 非 `'scrypt'` 直接回 false, hashPassword.mjs:66-68), 不相容舊 sha512 hash; 引用方升級須重產密碼或要求使用者重設 (對齊 ADR-046 clean break).
- **D23 scrypt 成本**: 採 Node 預設成本參數 (N=16384, r=8, p=1), 不額外調參.

**Consequences**:
- ✅ per-user salt + scrypt 達 OWASP Password Storage 標準: 記憶體困難 KDF 大幅拉高暴力成本, 獨立鹽消除 rainbow table / 全表 precompute.
- ✅ pepper 為額外防線: DB 外洩但 pepper 未洩時 (pepper 在 env / 設定檔而非 DB), 攻擊者缺 pepper 仍難重算.
- ✅ 自描述格式利於日後演算法遷移 (verify 時依 tag 分流), 不需 DB schema 變更.
- ✅ D21 拒啟逃生閘把「pepper 誤用佔位符上線」從靜默風險變成啟動即失敗, 強制生產注入真實 pepper.
- ⚠️ **D19 不向後相容**: 舊 sha512 hash 一律 verify 失敗, 升級即須重產 / 重設全部密碼; 因尚無主專案引用 (ADR-046), 採 clean break 不做遷移儀式.
- ⚠️ scrypt 為記憶體困難, 單次雜湊 CPU / 記憶體成本高於 SHA-512, 登入 / 改密碼延遲略增 (毫秒級), 屬可接受安全成本.
- ⚠️ **pepper 生命週期為引用方之部署責任, 非套件缺陷**(v3 re-audit D-α 重新確認, 對齊 ADR-040 之「套件 vs 部署契約」框架): pepper 一旦輪替(換 `SALT` env 值), 既有以舊 pepper 算出的 hash 全部 verify 失敗 — 這是任何 keyed-hash / pepper 機制的固有物理限制(換 key 本就無法還原用舊 key 算出的結果), 非本套件可修復或該修復之缺陷. 本套件的責任邊界止於「正確實作 scrypt + per-user salt + 可選 pepper hook + pepper 缺失時拒啟(D21)」; **`SALT` 該用什麼值、是否輪替、輪替時如何遷移既有使用者密碼, 由引用本套件之專案自行決定與管理**, 套件不主動提供 pepper 版本標記或輪替遷移機制(避免對非必要情境過度設計). 引用方若確有輪替需求, 建議策略: 保留舊 pepper 供 fallback 驗證 + 使用者下次成功登入時以新 pepper 透明 re-hash(此邏輯屬引用方應用層, 不在套件範圍).

**Affected**:
- server/hashPassword.mjs:30 (hashPassword: per-user salt + scrypt + 自描述格式) / :53 (verifyPassword: 解析 + 重算 + timingSafeEqual) / :24,27 (KEYLEN=64 / SALTLEN=16)
- server/procCore.mjs:320 (loginByAccountAndPassword 改 verifyPassword) / :1093 (changeUserPassword 舊密碼改 verifyPassword) / :825 (createUser hashPassword) / :1107 (changeUserPassword hashPassword) / :1235 (adminResetUserPassword hashPassword) / :1444 (updateTabItems hashPassword)
- server/WWebSso.mjs:172-180 (salt 讀取 + `process.env.SALT` 覆寫 + D21 拒啟 throw + ALLOW_PLACEHOLDER_SALT 逃生閘)
- server/g_getSettings.mjs:59-60 (SALT env 注入 st.salt)
- server/g_initialData.mjs:8 (種子端 pepper `process.env.SALT || '{salt}'`)
- 對齊 ADR-007 (password 比對 timing-safe; verifyPassword 內 crypto.timingSafeEqual hashPassword.mjs:97) / ADR-046 (clean break)

## ADR-036: 自動封鎖即時化 + 統一訊息 anti-enumeration (D07 / D24)

**Status**: Accepted (2026-06-26)

**Context**:
- 早期帳號登入失敗封鎖由 2 秒背景 timer 結算: 失敗紀錄先累積, 每 2s 輪詢一次才判定是否封鎖 — 從「達門檻」到「timer 觸發」之間有最長 2s 的突發猜測窗口, 攻擊者可於此窗口塞入額外猜測.
- 封鎖門檻原以 `>=` 比較 (次數 >= 上限即封鎖), 與「超過上限才封鎖」之直覺語意有 1 次落差.
- 被封鎖帳號登入原回 distinct `'loginAccountBlocked'`: 與「密碼錯誤」「帳號不存在」訊息不同, 攻擊者可藉此辨識「該帳號存在且已被鎖」, 洩漏帳號存在性 (account enumeration).
- 不解決會踩到: 封鎖前 2s 突發猜測窗口、門檻 off-by-one、封鎖狀態洩漏帳號存在性.

**Decision**:
- **D24 即時封鎖**: 帳號登入失敗封鎖改於**失敗當下同步即時觸發** (procProtect.mjs loginByAccountAndPassword catch 內: 記錄失敗 :206 → 窗內紀錄剪枝 :211-217 → 即時判定 :225 → `await blockAccount(account)` :227), 消除封鎖前突發窗口. **2s timer 已移除** (procProtect.mjs:249-251 註解明示「已移除, 改於登入失敗當下同步處理」).
- **D07 門檻改 `>`**: 封鎖判定由 `>=` 改為 `>` (procProtect.mjs:225 `if (nrecs > numForAccountLoginFailed)`), 即「次數超過上限」才封鎖.
- **D24 統一訊息 anti-enumeration**: 被封鎖帳號登入不再回 distinct `'loginAccountBlocked'`, 改回 generic **`'failedLoginForCatch'`** (procProtect.mjs:178), 與「密碼錯誤」「帳號不存在」三者一致, 攻擊者無法從訊息辨識帳號是否存在或是否被封鎖.
- `blockAccount` 為冪等 (重複寫 `timeBlocked` 由 `getBlockedByUser` 隱性解除判定擋, 對齊 ADR-013), 並發多次失敗各自觸發亦安全, 不需鎖 (procProtect.mjs:223-224 註解).
- **token / IP rate-limit 仍維持 2s timer 機制**, 僅門檻同步改 `>` (token: procProtect.mjs:343 setInterval / :372 `> numForTokenCallApi`; IP: :727 setInterval / :756 `> numForIpCallApi`).

**Consequences**:
- ✅ 即時封鎖消除「達門檻後 2s 內仍可猜」的突發窗口, 暴力試密碼閘更緊.
- ✅ 封鎖狀態走 generic 訊息, 對齊 ADR-003 防帳號列舉 — 攻擊者無法藉登入訊息推斷帳號存在性或封鎖狀態.
- ✅ 門檻 `>` 語意明確 (超過上限才鎖), 與 spec 自動封鎖機制一致.
- ⚠️ **UX 取捨**: 被封鎖的真實使用者只見 generic 失敗訊息 (無「帳號暫時鎖定, 請稍後再試」之明示), 排查體驗略差 — 以防帳號列舉換取, 屬安全與 UX 的取捨.
- ⚠️ token / IP rate-limit 仍為 2s timer (非即時): 其偏差為秒級, 對 attack throughput 無實質緩解差 (對齊 ADR-030 F-049 已知接受 trade-off), 故僅帳號路徑改即時.

**Affected**:
- server/procProtect.mjs:206 (記錄失敗時間) / :211-217 (窗內紀錄剪枝) / :225 (D07 門檻 `>`) / :227 (即時 blockAccount) / :249-251 (2s timer 已移除註解) / :178 (D24 封鎖回 generic 'failedLoginForCatch')
- server/procProtect.mjs:343,372 (token rate-limit 仍 2s timer, 門檻 `>`) / :727,756 (IP rate-limit 仍 2s timer, 門檻 `>`)
- spec/流程_自動封鎖機制.md
- spec/流程_使用者一般登入.md
- 對齊 ADR-003 (anti-enumeration 統一訊息) / ADR-013 (timeBlocked 隱性解除)

## ADR-037: 停用使用者即時撤銷 token (D04)

**Status**: Accepted (2026-06-26)

**Context**:
- 管理者於後台將使用者 `isActive` 設為 `'n'` (停用) 後, 該使用者既有的 active token 是否仍可用?
- 若不撤: 停用後使用者持既有 token 仍能通過驗證 (token 即身份, 對齊 ADR-009 token 不被密碼操作牽動), 停用意圖落空至 token 自然到期為止.
- 停用為 admin 明確「即刻禁止此人」之意圖, 與「變更密碼後不踢既有 session」(ADR-009) 之常態維運操作性質不同 — 停用須即時生效.
- 不解決會踩到: 被停用使用者持舊 token 繼續存取, 停用形同延遲生效.

**Decision**:
- Admin 將使用者 `isActive` 設為 `'n'` 時 (經 `checkTokenAndUpdateUsersList` → `updateUsersList`), 於儲存成功後**即時刪除該使用者名下全部 token** (procCore.mjs:1764-1785): 本批中 `isActive === 'n'` 之 row (:1770 判定), 取 `userId` (:1774) 後 `woItems.tokens.select({ userId })` 取陣列逐筆 `del` (:1778-1780).
- 設計上使用者不持有 `isApp='y'` token, 故一併撤 (撤 token 作法比照 `procProtect.blockAccount`, procCore.mjs:1764-1767 註解).
- 撤 token 為附帶副作用, 失敗僅記 `srLog.error` 不阻斷主流程; 冪等 (該 user 已無 token 時刪 0 筆無害).

**Consequences**:
- ✅ 停用即時生效, 被停用使用者既有 session 立即失效, admin 意圖確實落地.
- ✅ 與 ADR-009 並存而不矛盾: ADR-009 規範「變更 / 重設密碼」(常態維運) 不踢 session; 本條規範「停用」(明確禁止) 即時撤 — 兩者意圖不同故行為不同.
- ✅ 撤 token 失敗不阻斷主流程 (停用本身已落地), 對齊 ADR-018 副作用失敗不阻擋主結果之精神.
- ⚠️ 被停用使用者下次操作時受保護 API 回 token 失效, 前端清 LS 跳登入頁; 若停用為誤操作, 重新啟用後使用者須重新登入 (舊 token 已刪不可復原), 屬可接受.
- ⚠️ 撤 token 為「儲存成功後」之 best-effort 副作用, 非同一交易內 (updateTabItems 本無交易, 對齊 ADR-045); 極端時序下停用已寫但撤 token 失敗, 僅留 srLog.error 供補救.

**Affected**:
- server/procCore.mjs:1764-1785 (updateUsersList 內: isActive==='n' 即時刪該 user 全部 token)
- spec/流程_後台變更使用者資訊.md
- spec/流程_後台刪除使用者.md
- 對齊 ADR-009 (multi-device session 獨立) / ADR-018 (副作用失敗不阻擋主結果)

## ADR-038: 後台批次更新 account 唯一性驗證 (D08)

**Status**: Accepted (2026-06-26)

**Context**:
- 後台 Users 採「整張表編輯」批次 upsert (對齊 ADR-021). 原批次驗證僅檢查 `id` / `email` 之必填與唯一性, **遺漏 `account` 欄位**.
- 結果: admin 可批次寫入 account 為空, 或兩列 account 重複 / 與既有 user account 重複之資料 — account 為登入主鍵之一, 重複 / 空值會破壞登入查詢 (`_getGenUserByKV` 以 account 查 user) 之唯一性假設.
- 不解決會踩到: account 空值 / 重複污染 users 表, 登入查詢命中多筆或查無, 帳號體系不一致.

**Decision**:
- `updateTabItems` 寫入 users 時補 `account` 之必填與重複驗證 (與既有 id / email 檢查並列):
  - **必填**: account 為空 → `errAccount = 'accountRequired'` (procCore.mjs:1387-1388).
  - **本批內重複**: account 已在本批 kpAccount 出現 → `errAccount = 'accountDuplicate'` (procCore.mjs:1392-1393).
  - **與既有 user 重複**: account 已存在於 `accountToIdOld` 且非同一 id → `errAccount = 'accountDuplicate'` (procCore.mjs:1397-1398).
- reject 對應 i18n key `accountRequired` / `accountDuplicate`, 對齊 ADR-021 「任一驗證失敗整批 reject 不落地」.
- id / email 仍以 `ckKey()` 檢查 (procCore.mjs:1354 id / :1359 email).

**Consequences**:
- ✅ account 與 id / email 同等受必填 + 唯一性守護, users 表三主鍵欄位一致性完整.
- ✅ 對齊 ADR-021 整批 atomicity: 任一列 account 違規即整批 reject, 不落地半邊資料.
- ✅ reject i18n key 對齊 ADR-034 key-only 契約, 前端以 `$tErr(key)` 顯示.
- ⚠️ admin 批次編輯時若某列 account 違規, 整批 reject 須回前端修正後重送 (對齊 ADR-021 已知重送成本).
- ⚠️ 並發兩 admin 編輯同表仍 last-write-wins (對齊 ADR-021 已知限制), account 唯一性僅在單次批次內 + 對當下 DB 快照成立.

**Affected**:
- server/procCore.mjs:1387-1388 (accountRequired) / :1393-1394 (本批重複 accountDuplicate) / :1398-1399 (與既有重複 accountDuplicate) / :1355,1359 (id / email ckKey)
- server/procLang.mjs (accountRequired / accountDuplicate key, eng+cht)
- spec/流程_後台新增使用者.md
- spec/流程_後台變更使用者資訊.md
- 對齊 ADR-021 (批次 upsert 整批 atomicity) / ADR-034 (reject key-only 契約)

## ADR-039: getUserInfor 查無 target 回 i18n key (anti-enumeration) (D06)

**Status**: Accepted (2026-06-26)

**Context**:
- 對外 server-to-server 之 `getSsoUserInfor` / `getUserInfor` 以給定 key/value (account / email / token) 查 user. 若「查無 target」與「無權限」回不同訊息, 攻擊者 (持合法 app token / admin token) 可藉訊息差異辨識「某 account / email 是否存在」(account enumeration).
- 內層 `_getGenUserByKV` 之 raw reject (`'can not find the user by xxx'` / `'duplicate xxx'`) 同時供「登入防列舉」沿用 (登入時亦查 user), 不可直接改動內層訊息.
- 不解決會踩到: 對外查詢 API 洩漏 target 存在性, 削弱 ADR-003 / ADR-004 之防列舉與 IDOR 收緊成效.

**Decision**:
- **邊界轉 null**: 對外 `getUserInfor` 於邊界以 `.catch(() => null)` 把內層 raw reject 轉為 null (procCore.mjs:1606-1607), 不讓內層存在性訊息外漏; 邊界註解明示此 anti-enumeration 意圖 (procCore.mjs:1601-1605).
- **handler 統一 reject**: kpfun / REST handler 收到 null (`!iseobj(userTarget)`) 時統一 `reject('tokenNoPermission')` (WWebSso.mjs:959-964) — 「查無 target」與「無權限」回同一 key, 不洩漏 target 存在性.
- **內層 raw reject 維持**: `_getGenUserByKV` 之 raw reject 不改, 供登入路徑防列舉沿用 (登入失敗統一訊息由更上層收斂).

**Consequences**:
- ✅ 對外查詢 API「查無」與「無權限」同一 key, 攻擊者無法以此辨識 account / email / token 是否存在.
- ✅ 邊界轉 null 集中於一處 (procCore.mjs:1606-1607), handler 只需判 `!iseobj` 即 reject 統一 key, 不需各 handler 自行處理存在性遮蔽.
- ✅ 內層 raw reject 維持不動, 登入防列舉路徑不受影響, 改動爆炸半徑小.
- ✅ 對齊 ADR-004 (getSsoUserInfor IDOR 收緊) / ADR-006 (對外統一訊息) / ADR-034 (對外回乾淨 key).
- ⚠️ 合法 caller (admin / app) 查一個真的不存在的 target 時, 也只得 `tokenNoPermission` 而非「查無此人」, 排查時須以後端 log 區分, 屬安全取捨.

**Affected**:
- server/procCore.mjs:1606-1607 (getUserInfor 邊界 .catch(()=>null)) / :1602-1606 (anti-enumeration 邊界註解)
- server/WWebSso.mjs:959-964 (handler !iseobj → reject 'tokenNoPermission')
- server/procLang.mjs:816-820 (tokenNoPermission key, eng+cht)
- spec/流程_查詢使用者資訊.md
- 對齊 ADR-004 (IDOR 收緊) / ADR-006 (對外統一訊息) / ADR-034 (對外乾淨 key)

## ADR-040: verifyConn 之 IP 來源為部署契約 (非套件缺陷) (D02 / T04 / T15 / T18)

**Status**: Accepted (2026-06-26)

**Context**:
- Audit (D02 / T04 / T15 / T18) 曾以「本套件直接暴露於公網」之假設, 判定 `verifyConn` / `getIpByHeaders` 信任 `X-Forwarded-For` (XFF) 為資安缺陷 — 因 XFF 可被 client 任意偽造, 直接暴露時攻擊者可偽造 client IP 繞過 IP 限流 / 封鎖.
- 但本套件實際部署型態為**內網 + 多層反向代理** (業主拍板): 反代會正確設定 / 清洗 XFF, client 無法直接觸及後端 socket.
- 此假設衝突是 audit 假痛的典型來源 (合約外假設 → 需求擴大型假痛).
- 不解決會踩到: 把部署契約誤判為套件缺陷, 引入「改用 socket IP」之退化 (內網多反代下 socket 來源恆為反代 IP, 改用會使 IP 偵測全失效).

**Decision**:
- IP 限流 / 封鎖以 `X-Forwarded-For` 第一段為 client IP (procProtect.mjs:424-427: `get(headers, 'x-forwarded-for')` → `sep(c, ',')` → `get(s, 0)` → trim; 無 XFF 時才 fallback `req.info/socket/connection.remoteAddress` :431-451).
- **前提為部署於「會正確設定 / 清洗 XFF 的可信反代」之後 — 此為部署契約, 非套件缺陷**.
- **不加 trustedProxy / 不改用 socket IP**: 內網多反代下 socket 來源恆為最近一層反代 IP, 改用 socket IP 會使所有 client 看起來同一 IP → IP 偵測 / 限流 / 封鎖全部失效.
- 直接暴露於公網、無可信反代之部署**不在本套件支援契約內**.
- ips 表隨 XFF 值增長 (T15): 為同一部署契約下的衍生現象 (每個新 client IP 產生一筆), 不在套件層處理 (對齊 ADR-011 / ADR-012 token 表不主動清掃之精神 — 由部署 / admin 層管理).

**Consequences**:
- ✅ 內網多反代部署下 IP 偵測正確 (取 XFF 第一段為真實 client), 限流 / 封鎖有效.
- ✅ 不引入 trustedProxy 設定複雜度, 不退化為 socket IP (那會在目標部署型態下使 IP 機制全失效).
- ✅ 把 audit 之「公網暴露」假設明確劃為合約外, 對齊全域 §3.1 真痛三條件 (假設拉到合約外 = 需求擴大型假痛, 預設不修).
- ⚠️ **部署責任轉移**: 若引用方違反契約 (直接公網暴露 / 反代未清洗 XFF), 攻擊者可偽造 XFF 繞過 IP 機制 — 此為部署層責任, 套件已明示契約.

## ADR-041: token 經 URL query 傳遞為刻意設計 (D11 / T18)

**Status**: Accepted (2026-06-26)

**Context**:
- Audit (D11 / T18) 指出 session token 經 URL query (`?token=...`) 傳遞之風險: URL 會被 referrer header 帶往外站、被瀏覽器歷史 / 伺服器存取 log 紀錄, token 外洩面較大.
- 但本套件核心用途為 **SSO**: 跨站登入完成後須以 URL 帶 token 轉址 (redirect) 回應用端, 應用端再取 URL token 入站 — 此為 SSO redirect 流程之必要機制, 非疏忽.
- 不解決會踩到: 把 SSO 必要機制誤判為缺陷, 為消除「URL 帶 token」而破壞跨站登入轉址.

**Decision**:
- session token 經 URL query 傳遞為**刻意設計**, 因 SSO 轉址需求 (登入完成 → URL 帶 token 轉址回應用端), 維持不改.
- 緩解依部署契約 (對齊 ADR-040): 部署於**內網 + HTTPS** 降低 referrer / log 外洩面 (HTTPS 下 referrer 不跨協議洩漏、內網限制 log 觸及範圍).
- 前端 autoLogin 對 URL token 之採用受 ADR-024 約束 (LS token 優先於 URL token, 防 URL token 劫持已登入 session).

**Consequences**:
- ✅ SSO 跨站登入轉址流程完整可用, 對齊套件核心用途.
- ✅ 把 audit 之「URL token 風險」明確劃為「SSO 必要 + 部署緩解」, 不為消除假想風險破壞核心功能 (對齊全域 §3.1).
- ✅ URL token 劫持風險由 ADR-024 (LS 優先) 守住, 已登入使用者不會被 URL 帶來的 token 偷換.
- ⚠️ 違反部署契約 (公網 / HTTP) 時, URL token 之 referrer / log 外洩面放大 — 屬部署層責任 (對齊 ADR-040).
- ⚠️ URL token 仍可能進入瀏覽器歷史 / 反代 log; 內網 + HTTPS 為緩解非根除, 屬 SSO 機制之已知取捨.

**Affected**:
- src/plugins/mUI.mjs (autoLogin URL token 採用, 受 ADR-024 LS 優先約束)
- spec/流程_使用者自動登入.md
- 對齊 ADR-024 (autoLogin LS token 優先, 防 URL token 劫持) / ADR-040 (部署契約緩解)

- ✅ admin 後台 token 管理功能完整 (可為 server-to-server 整合鑄造 app token), 不引入「admin 不能鑄 isApp」之反直覺限制.
- ✅ 對齊 ADR-005 信任邊界模型 (集中於 token 簽發 / admin 身份), 不分散判斷.
- ✅ 把 audit 之「admin 鑄 isApp」明確劃為信任邊界內正常能力 (對齊全域 §3.1 — 後果具體性不成立, 未逾越既有權限).
- ⚠️ admin 帳號 / admin token 外洩時, 攻擊者可鑄造長效 isApp token 作為持久後門 — 此風險本質上等同 admin 外洩 (ADR-005 已記), 緩解靠保護 admin 憑證而非限制鑄造.

- 對齊 ADR-005 (isApp token bypass fun / 信任邊界集中於簽發)

## ADR-043: CSRF 評估 — token 存 localStorage 非 cookie (D05 / T20)

**Status**: Accepted (2026-06-26)

**Context**:
- Audit (D05 / T20) 要求評估系統之 CSRF (Cross-Site Request Forgery) 防護: 傳統表單型 CSRF 利用「瀏覽器自動隨跨站請求攜帶 cookie」之特性, 使攻擊者構造的跨站請求挾帶受害者憑證.
- 本系統認證 token 之儲存與傳遞方式決定 CSRF 是否適用.
- 不解決會踩到: 在不適用 CSRF 的架構上引入 anti-CSRF token / SameSite 等不必要機制.

**Decision**:
- 認證 token 存於 **localStorage** (非 cookie), 並經 kpFunExt RPC **參數**顯式傳遞 (非 cookie header) → 瀏覽器**不會自動**隨跨站請求攜帶此 token.
- 因此傳統表單型 CSRF (依賴 cookie 自動攜帶) **大致不適用**於本系統 — 攻擊者構造的跨站請求無法取得 localStorage 內的 token, 也無自動攜帶機制.
- 接受現狀, 不引入 anti-CSRF token / SameSite cookie 等針對 cookie 型 CSRF 的機制 (本系統無 cookie 認證).

**Consequences**:
- ✅ token 存 LS + RPC 參數顯式傳遞之架構, 天然規避 cookie 自動攜帶型 CSRF, 不需額外 anti-CSRF 機制.
- ✅ 把 audit 之 CSRF 項明確評估為「架構上大致不適用」, 不引入不必要的防護複雜度 (對齊全域 §3.1).
- ✅ 與 ADR-010 (LS 空字串慣例) / ADR-024 (LS token 優先) 之「single trusted session source = LS」模型一致.
- ⚠️ LS 儲存 token 之對應風險改為 **XSS** (若有 XSS 漏洞, 攻擊者腳本可讀 LS token) — CSRF 與 XSS 為不同威脅面, 本條僅結論 CSRF 不適用, XSS 防護 (輸入轉義 / CSP 等) 屬另一議題不在此條.
- ⚠️ 若未來改用 cookie 認證 (例如為 SSR 需求), 須重新評估並引入 anti-CSRF / SameSite — 本結論建立在「LS + RPC 參數」現狀上.

**Affected**:
- src/plugins/mUI.mjs (token 存取 localStorage; RPC 參數傳遞)
- 對齊 ADR-010 (LS 空字串慣例) / ADR-024 (LS token 優先, single trusted session source = LS)

## ADR-044: 批次更新原子性由引用方負責 (D09 / T26)

**Status**: Accepted (2026-06-26)

**Context**:
- Audit (D09 / T26) 指出後台批次寫入 (`updateTabItems` / syncAndReplace 類) 無 DB 層交易 (transaction) / rollback: del → add → diff 三組依序執行 (procCore.mjs:1429 del / :1454 insert / :1459 save), 若中途某組失敗, 前面已成功的寫入不會回滾 → 部分落地 (partial write).
- 全 procCore.mjs 無任何 `transaction` / `commit` / `rollback` 構造 — atomicity 非由 DB 層保證.
- 此邊界為單一管理員驅動 (admin 後台手動編輯), 未觀察到部分失敗之實機案例.
- 不解決會踩到: 在底層套件引入交易機制 (耦合特定 DB / ORM 交易能力), 限制引用方的儲存選型.

**Decision**:
- `updateTabItems` / syncAndReplace 類批次寫入**無 DB 層交易 / rollback**, 屬「單一管理員驅動、未觀察到部分失敗」之邊界 (對齊全域 §3.1 真痛三條件之「已被觀察」缺項 → 預設不修).
- **本套件不在此層引入交易**: atomicity 由引用此套件之開發者依其儲存後端 / 需求自行評估 (例如自行包交易 / 自行加 rollback 補償).
- 與 ADR-021 之關係: ADR-021 之「整批 atomicity」指**驗證階段** atomicity (全部驗證通過才開始寫, 任一驗證失敗整批 reject 不寫); 本條指**寫入階段**無 DB 交易 (驗證全過後的三組依序寫, 中途失敗不回滾) — 兩者分屬不同階段, 不矛盾.

**Consequences**:
- ✅ 底層套件不耦合特定 DB / ORM 之交易能力, 引用方儲存選型自由.
- ✅ 把 audit 之「無交易」明確劃為「未觀察 + 由引用方負責」, 不為假想的部分失敗引入耦合 (對齊全域 §3.1).
- ✅ ADR-021 驗證階段 atomicity 已擋掉「驗證可預見的失敗」(空值 / 重複 / 自我鎖死), 寫入階段真正失敗多為 DB 層異常 (連線斷 / 磁碟滿) 之罕見情境.
- ⚠️ **寫入階段真實失敗時可能 partial write** (例如 del 成功但 insert 失敗, 留下被刪未補的狀態); 引用方若需強原子性須自行於外層包交易 / 補償.
- ⚠️ 並發兩 admin 編輯同表仍 last-write-wins (對齊 ADR-021 已知限制), 本條不改變此並發特性.

**Affected**:
- server/procCore.mjs:1289 (updateTabItems 定義) / :1430 (del) / :1454 (insert) / :1459 (save) — 三組依序寫, 無 transaction/commit/rollback
- server/procCore.mjs:1719 (updateUsersList 呼叫) / :1836 (updateTokensList) / :1894 (updateIpsList)
- spec/流程_後台新增使用者.md
- 對齊 ADR-021 (驗證階段整批 atomicity, 與本條寫入階段無交易分屬不同階段)

## ADR-045: 統計 cache 失敗處置 — 偵測 undefined 轉 reject (D18 / T14)

**Status**: Accepted (2026-06-26) → **Superseded in part (2026-09-01)**: wsemi 1.8.81 之 `cache()` 新增 `cacheError:false`(失敗不快取、錯誤拋給執行者與等待中之併發呼叫、下次 get 重新執行)與 `timeFrom:'end'`(快取自 fun 結束起算),`procStaInfor` 三支 getter 改傳此二選項,以 `.catch` 記 `srLog.error({ key:'getStaDataFailed' })` 後 reject,**「偵測 undefined」與「失敗結果被快取 30s 不可即時重試」兩點不再適用**;對外契約(reject `'getStaDataFailed'`)不變。以下為原決策紀錄。

**Context**:
- 統計頁各 summary 經 wsemi cache (30s TTL) 包覆 worker 計算結果. wsemi cache 之 lib 行為: worker reject 時, cache 把失敗結果「吞掉回 undefined」並**快取 30 秒** (lib 無「失敗不快取」選項).
- 後果: (1) worker 失敗時若直接回傳 cache 結果, 會把 undefined 洩漏給前端 (前端拿到 undefined 渲染異常); (2) 失敗結果被快取 30s, 期間不可即時重試 (再讀仍回 undefined).
- 不解決會踩到: 統計 worker 失敗時前端收到 undefined 渲染破裂、無明確錯誤訊息.

**Decision**:
- 統計 summary 取 cache 結果後**偵測 undefined** (procStaInfor.mjs:229 / :317 / :385 `if (r === undefined)`): 命中即視為 worker 失敗 → `srLog.error({ ..., key: 'getStaDataFailed' })` 記錯誤 key (procStaInfor.mjs:231 / :319 / :387) → `Promise.reject('getStaDataFailed')` (procStaInfor.mjs:233 / :321 / :389), **不對外洩漏 undefined**.
- 接受 lib 限制: 失敗結果於 30s 內被快取, 期間不可即時重試 (統計頁非即時關鍵, 30s 後 cache 過期自然重算).

**Consequences**:
- ✅ worker 失敗時前端收到明確 i18n key `getStaDataFailed` (走載入失敗 fallback, 對齊 ADR-002), 不收到 undefined.
- ✅ 後端 `srLog.error` 保留錯誤 key, 供 audit / 統計分析 (對齊本專案 log 記錄要點).
- ✅ 三支 summary (UserAccountLogin / Token / Ip) 統一同款偵測 + reject, 行為一致.
- ⚠️ **失敗結果 30s 內不可即時重試** (lib 無失敗不快取選項): 統計 worker 失敗後, 即使下游已恢復, 仍須等 cache 30s 過期才重算 — 統計頁非即時關鍵, 屬可接受 trade-off.
- ⚠️ 對齊 ADR-025 (secondary stats fire-and-forget): secondary summary 失敗時前端該卡片走「-」/ 舊資料, 主 API 失敗才整頁錯誤; 本條之 reject 'getStaDataFailed' 即該失敗訊號來源.

**Affected**:
- server/procStaInfor.mjs:229,231,233 (getStaUserAccountLogin: undefined 偵測 / srLog.error / reject) / :317,319,321 (getStaToken) / :385,387,389 (getStaIp)
- server/procLang.mjs (getStaDataFailed key, eng+cht)
- spec/流程_後台統計資訊.md
- 對齊 ADR-002 (載入失敗 fallback 訊息呈現) / ADR-025 (secondary stats fire-and-forget) / ADR-008 (統計 30s cache)

**Decision**:
- 上述密碼雜湊格式 + 自動封鎖 / 訊息行為 + 停用撤 token 等為對引用方之破壞性變更; 因尚無任何主專案引用本套件, **不做正式 major 版本號 / changelog / 遷移指引儀式**, 直接 **clean break** (不考慮向後相容、不留 sha512 相容路徑、不留舊訊息相容層).
- 決策歷史 / 設計取捨仍以本檔 ADR 完整保留 (供日後第一個引用方參考), 但不額外產出面向「既有使用者」的遷移文件 (因無既有使用者).

**Consequences**:
- ✅ 不為不存在的下游投入遷移儀式工程, 對齊全域 §2.3 簡潔優先 (不為一次性 / 不存在情境做設計).
- ✅ clean break 使 codebase 不背向後相容包袱 (無 sha512 雙路徑 / 無舊訊息相容層), ADR-035 verifyPassword 可只認 scrypt 單一格式, 實作乾淨.
- ✅ ADR 完整保留決策歷史, 第一個引用方接入時可一次性對齊最新契約 (而非逐版遷移).
- ⚠️ **一旦有主專案開始引用, 本決策即失效**: 之後的破壞性變更須恢復正式版本號 / changelog / 遷移指引儀式 (對齊 §6 spec 為真理 — 屆時須新增 ADR superseding 本條).
- ⚠️ clean break 假設「無既有 hash / 既有 session 需保留」; 若日後發現有遺漏的引用方 / 既有資料, 須補一次性資料遷移 (重設全部密碼), 不可回頭加相容層.

**Affected**:
- 對齊 ADR-035 (密碼雜湊 D19 不向後相容 clean break) / ADR-036 (封鎖行為破壞性變更) / ADR-037 (停用即時撤 token) / ADR-046 (框架升級屬未來重大變更)
- 本檔 (設計要點與取捨.md — 決策歷史以 ADR 保留, 取代遷移指引)

## ADR-048: 對外功能之 spec 覆蓋分層 — 非所有 endpoint 都建獨立「流程_*.md」 (2026-07-09 稽核追認)

**Status**: Accepted (2026-07-09)

**Context**:
- 本套件對外面 = `server/WWebSso.mjs` 之 HTTP handler + kpFunExt RPC。並非每個 endpoint 都對應一支 `spec/流程_*.md`「重要流程」文件。
- 2026-07-09 spec 覆蓋稽核曾將 `getSsoUsersList`「無流程 spec」標為缺口。主代理複查後確認**非缺口**: 它有 `test/api-httpendpoints.test.mjs:99-175` 四個 case(admin token→200 回清單不含 password、無 token→`tokenExpired`、無效 token→`tokenExpired`、**非 admin viewer→被 `funCheckAdmin` 擋 @ :171** 之權限邊界), 且 admin-only 守門(`WWebSso.mjs:903` `{fun: funCheckAdmin}`)對齊 ADR-004。誤報根因: 稽核者只掃 `spec/流程_*.md` 未看 `test/api-*.mjs`。

**Decision** — 對外功能依性質分三層覆蓋, 不強求人人有 `流程_*.md`:
1. **使用者可觀察之重要流程**(登入 / 註冊 / 變更密碼 / 後台 CRUD / 封鎖 / 統計 等)→ 建 `spec/流程_*.md` + e2e。
2. **server-to-server REST endpoint**(`getSsoUsersList` / `getSsoUserInfor`, 供外部系統以 sys token 介接, 無 UI)→ **不建流程 spec**, 以 `test/api-httpendpoints.test.mjs` 之 API 契約測試覆蓋(含權限邊界); 契約記於本檔「server-to-server REST endpoint 例外」節 + ADR-004(IDOR 收緊)。
3. **內部工具 / 無分支資訊查詢**(`cleanKpIpCallApi` / `cleanKpAccountLoginFailed` 限 127.0.0.1 白名單; `getWebInfor` 純資訊無分支)→ **不建流程 spec, 亦不需 e2e**。

**Consequences**:
- ✅ 不為 server-to-server / 內部工具端點投入 UI 流程 spec + e2e 之過度工程。
- ✅ 覆蓋不打折: server-to-server 端點仍有 api 契約測試(含權限邊界)保護。
- ⚠️ **稽核對外功能覆蓋度時, `spec/` 與 `test/` 兩處都要看**; 只掃 spec 會誤把第 2/3 層當「未覆蓋缺口」(2026-07-09 已發生一次)。
- 📌 測試檔命名對應: 第 2/3 層之測試放 `test/api-*.mjs`。原 `e2e-doubleclick` / `e2e-getuserinfor` 兩檔為純 API 卻用 `e2e-` 前綴, 已於 2026-07-10 依 J-1 裁決更名為 `test/api-doubleclick.test.mjs` / `test/api-getuserinfor.test.mjs`(名實相符, 對齊全域 §14.3 三前綴分層)。

**Affected**:
- server/WWebSso.mjs (getSsoUsersList / getSsoUserInfor / cleanKpIpCallApi / cleanKpAccountLoginFailed / getWebInfor)
- test/api-httpendpoints.test.mjs (server-to-server 契約測試)
- 對齊 ADR-004 (IDOR admin-only 收緊) + 本檔「server-to-server REST endpoint 例外」節

## ADR-049: /api/logoutSsoUser 為 /api/logoutByToken 之重複別名端點 — 保留並凍結, 移除須確認無外部依賴 (2026-07-10 J-2 裁決)

## ADR-050: 本套件為可安裝套件, 升級不可破壞引用方啟動契約 (Supersedes ADR-047) (2026-08-20)

**Status**: Accepted (2026-08-20)

**Context**:
- ADR-047 以「尚無任何主專案引用本套件」為前提採 clean break。此前提為**錯誤事實**：`rddmanager_sso` 自 `w-web-sso@1.0.37` 起即為引用方。
- 2026-08-20 引用方升級至 1.0.56，settings 未動即啟動失敗（連撞 `invalid siteUrl` 與 `invalid passwordPolicy` 兩次 throw），且舊 DB 全體使用者（含 admin）因密碼雜湊格式變更無法登入並遭誤導為「密碼錯誤」計入封鎖。事證要點已收錄於本 ADR Context 與 z修正規劃書.md 升級破壞事件節（原始外部報告文件已閱畢刪除）。
- 根因鏈：(1) 2026-05-02 加入自助註冊功能時，`allowUserRegistration` 出生即預設 `true`（新功能對所有引用方預設強制開啟，連帶強制 `siteUrl`）；(2) `passwordPolicy` 出生即無條件 throw，無程式內建預設，與同檔其他設定「未給即回退預設值」慣例相悖；(3) 全部測試以套件自帶完整 settings 驗收（`genTempSettings` 只能改值不能缺鍵），「引用方缺鍵」路徑零覆蓋；(4) 已搬移之 settings 鍵（`chpwEmTitle` 等）靜默失效無警告。

**Decision**（升級相容鐵則，對本套件所有後續變更生效）:
1. **啟動契約不可破壞**：任一舊版本之 settings 原封不動，新版必須能正常啟動與服務。新增設定鍵一律要有程式內建預設值；「未給即 throw」僅允許用於「有給但給錯」之情形。
2. **新功能開關一律 opt-in**：行為開關預設 `false`，引用方明確設 `true` 才啟用；讀取採 `=== true` 嚴格判定，非布林不視為開啟。
3. **settings 既有鍵不得停用**：settings 是安裝方唯一介面，既有鍵一律持續支援原語意，擴充不可要求安裝方搬移設定。真有不得不停用之鍵（須業主明確裁決），至少啟動掃描印 `[WARN]` 告知替代管道，絕不允許靜默失效。
4. **內建資源須有引用方覆寫管道**：套件內建之模板等資源（引用方無法改 `node_modules` 內檔案），必須提供 settings 覆寫管道（如 `pathTemplate` 自訂模板資料夾、`kpLangExt` 覆寫語系鍵），內建值僅為預設。
5. **資料格式破壞性變更須有遷移路徑或可辨識錯誤**：不可讓資料層不相容偽裝成一般業務錯誤（如舊 hash 驗證失敗與「密碼打錯」走同一 reject 並計入封鎖）。本次密碼雜湊變更由引用方裁決以「重建重匯入使用者資料」處置，套件端不補相容層（維持 ADR-035 scrypt 單一格式）。
6. **升級驗收情境以「舊引用方原封升級」為準**：以不含新鍵之舊式 settings 啟動須成功，不得只以套件自帶完整 settings 驗收。

**2026-08-20 已落地實作**:
- `allowUserRegistration` 預設改 `false`，讀取處 `get(opt, 'allowUserRegistration', false) === true` 一行式（原 `normalizeAllowUserRegistration` 包裝函式與其具名匯出一併移除，`WWebSso.mjs` 還原 `export default WWebSso` 單一出口）
- `passwordPolicy` 未給採程式內建預設（`server/defaultPasswordPolicy.mjs`，與自帶 settings.json 同組）+ 印 `[INFO]`；有給才逐欄驗證
- 信件文字鍵 `chpwEmTitle` / `chpwEmContent` / `regVerifyEmTitle` / `regVerifyEmContent` 恢復完整支援（另擴充 `resetPwEmTitle` / `resetPwEmContent` / `verifyEmailResultContent`）：逐語系物件，各值可給文字或檔案路徑（基於啟動路徑，檔案存在即初始化讀檔），有給即優先於內建；1.0.37 之 35 個 settings 鍵經逐鍵盤點全數持續讀取生效
- 語系文字統一入單一字典 kpLang：內建預設存於 `procLang.mjs` 語系鍵（信件 body 不做檔案模板，`server/template/` 只留複雜模板 `verifyEmailResult.html`），settings 信件鍵以 `kpLangExtEmail` 逐語系覆寫入字典，`kpLangExt` 為最終覆寫層（整鍵覆寫，供測試/CI）；procCore 寄信只查 kpLang 單一來源，`{placeholder}` 置換值經 htmlEscape；前端 `webInfor.kpLang` 傳 `kpLangWeb`（剔除後端寄信專用鍵，內部文字不外洩）；合併順序由 `test/unit-lang.test.mjs` 直測守護；套件自帶 settings.json 含全部鍵作為安裝方範本
- `verifyBaseUrl` 可由 settings 提供（原硬編 `http://localhost:{serverPort}` 使註冊功能於非本機部署實質不可用），未給回退本機並於開放註冊時印 `[WARN]`
- `pathTemplate` 可由 settings 指定自訂模板資料夾，缺檔逐檔回退內建（信件 body 與驗證結果頁客製管道）
- 驗收：以移除三鍵之 1.0.37 式 settings 實測啟動成功（`[INFO]` 採內建密碼政策、廢棄鍵 `[WARN]` 正常印出、伺服器正常監聽）

**Consequences**:
- ✅ 舊引用方 settings 原封升級即恢復正常啟動，無須補鍵。
- ✅ 註冊功能回歸 opt-in：未曾要求註冊的引用方不再被迫供應 `siteUrl`。
- ⚠️ 對「已依 1.0.5x 預設 true 而隱性依賴註冊開啟」的引用方屬行為變更：須明確設 `allowUserRegistration: true`（本套件自帶 settings 已明確設 true，自身開發與 e2e 不受影響）。
- ⚠️ 破壞性變更之版本儀式（major bump / CHANGELOG）依 ADR-047 失效條款恢復，由業主裁決版號策略。

**Affected**:
- server/WWebSso.mjs（設定讀取與守門）/ server/defaultPasswordPolicy.mjs（新）/ server/procCore.mjs（renderEmailBody 模板回退）
- test/unit-register.test.mjs（opt-in 閘門測試改測 procCore 真實 reject）
- 取代 ADR-047；對齊 ADR-035（scrypt 單一格式維持，資料遷移由引用方重建處置）

## ADR-051: 統計 log 掃描改單趟核心 + 檔級彙總快取 (staLogsCore) (2026-08-31)

**Status**: Accepted (2026-08-31)

**Context**:
- 後台統計頁 3 支 API (`getStaToken` / `getStaIp` / `getStaUserAccountLogin`; `getStaIpSummary` 內部再呼叫 `getStaIp`) 各開一個 worker 掃近 7 天 log, 每行先做 `ot(v.time)` + `format` + `isAfter` 三次 dayjs 才比對 `event` (命中率 staIp 0.3%). 引用方 rddmanager 實測近 7 天 169 檔 / 352 MB / 236 萬行, 冷快取端到端 12–21 秒, 期間前端只顯示靜止「等待數據中…」(調研與複審: `建議sso調整.md`).
- 成本 = O(近 7 天全系統請求數), 使用者數增加時線性惡化; 只調換判斷順序仍是線性.
- w-syslog 依**寫入當下時鐘**切檔 (`formatter.mjs:41-68`), 整點跨過後舊檔不再被寫入 (transport 緩衝外溢會落新檔而非舊檔), 故封閉檔之彙總可快取.

**Decision**:
- 新增 `server/staLogs/staLogsCore.mjs` 為三支統計之共用核心: (1) 單趟掃描同時餵三個過濾器, 每檔只讀一次; (2) 逐行先比 `event`, 命中才取時間; `time` 為 epoch ms 數值直接 `>` 比較, 非數值 (ISO 字串) 走 dayjs 慢路徑; 桶標籤以分鐘整數 memo 查表 (任何整分鐘偏移之時區與逐行 format 等價); 就地累加不建陣列; (3) 檔級彙總快取: 鍵 `(name, size, mtimeMs)`, 檔內最早可計入行 `minTimeMs > tStartMs` (窗過濾為 no-op) 才沿用, 否則 (邊界檔) 重掃; 當前小時檔因 size 變動自然重掃; 快取依 fmt (hr/day) 分開; 檔案自清單消失即淘汰; (4) single-flight: 同參數併發共用同一 in-flight promise.
- 掃描仍在 worker (SSO 為驗證樞紐, 主執行緒不可阻塞), 但改為**單一** worker 只收「需重掃之檔案清單」回每檔彙總; 快取本體留主執行緒 (`staLogsCore.callWorker.mjs`). 三支 `sta*.mjs` / `sta*.callWorker.mjs` 改為薄殼, 簽章與輸出形狀不變; 原三支 `*.shellWorker.mjs` 移除.
- `procStaInfor.mjs` 三支 getter 外加 single-flight, 繞開 wsemi cache 對執行中者之 1000 ms 輪詢等待 (前端六支並行時 `getStaIpSummary`→`getStaIp` 與直呼 `getStaIp` 必撞); ADR-045 之 undefined 偵測與 30 秒 cache 維持. **2026-09-01 更新**: wsemi 1.8.81 之 `cache()` 改為執行中共用 in-flight promise (不輪詢), 並新增 `timeFrom` / `cacheError` 選項; 三支 getter 改傳 `{ timeFrom:'end', cacheError:false }`, 自建 single-flight 與 undefined 偵測一併移除 (見 ADR-045 Superseded 註記).
- 失敗語意: 資料夾項目略過 (原 `fsTreeFolder` 會列出子資料夾, 對其開讀取串流即 throw 使整支 API 失敗); 單檔讀取錯誤略過該檔、`srLog.warn({ key: 'staLogsFileSkipped' })`、不入快取, 不整體失敗.
- **刻意差異 (唯一)**: 無 `time` 或無法解析之行不計入任何桶 (原實作 `ot(undefined)` 視為 now 而計入當前桶); ISO 字串 time 仍計入.
- `timeInterval` 非 'day' 一律視同 'hr' (原三檔以 `==='day'` 決定 fmt、`==='hr'` 決定 unit, 傳其他值時兩者不一致).
- settings 新鍵 `logNumKeep` (opt-in): 未給採 w-syslog 預設 (hr: 365*24 / day: 365), 有給但非正整數視為設定錯誤 throw; `settings.json` 範本展示 8760 (= 預設, 行為中性). 對齊 ADR-050.
- `procCore._getGenUserByKV` 查無/重複使用者之 `console.log` 改 `srLog.debug` (app token 之速率封鎖路徑每 2 秒觸發, console 洗版); app token 是否明確跳過速率封鎖為安全政策, 另案裁決, 本輪不動.
- **P2 (前端先到先畫, 2026-09-01)**: `LayoutContentStaInfor.vue` 主內容改 `v-if="!errMsg"` 立即渲染骨架 (頁首 + 各區塊標題); 4 張使用者卡片與管控狀態 6 個數值以 `loadingUserSummary` / `loadingTokenSummary` / `loadingIpSummary` 旗標 (各自 `.finally` 關) 切換「w-component-vue `WIconLoading` cir-rotate 轉圈」與數字; 三張頻率圖以 `optX` 是否為 null 切換 300px 轉圈佔位區 (與圖同高, 不跳版) 與圖; 移除整頁「等待數據中…」與 `firstLoading`. 任一 API reject 仍整頁切 errMsg (E2E-002 契約不變). 載入完成後 DOM 與改造前完全一致, 既有 baseline 不變; 卡片數值列載入中佔位高度 32px = 載入後 `text-2xl` 行高 (實測). 色票沿用本頁既有次要文字色 `#6b7280`.

**驗證** (2026-08-31):

## ADR-052: 應用系統 token (isApp='y') 明確豁免 token 調用次數封鎖 (2026-09-01)

**Status**: Accepted (2026-09-01)

**Context**:
- `procProtect` 每 2 秒掃 `kpTokenCallApi`, 任一 token 於 `minForTokenCallApi` 內呼叫數 > `numForTokenCallApi` 即 `blockAccountByToken` → 以 token 查 userId → `getGenUserByUserId` → 封鎖使用者並刪 token (流程_自動封鎖機制 B 段).
- 應用系統 token (`isApp='y'`, 如主系統 `token-for-app` / `id-for-app-main`) 由內部 token creation 路徑簽發, **無對應 users 紀錄** (`g_initialData.mjs` 只建 token). 主系統後端每次驗證使用者都問 SSO, 約 4 個併發使用者即超過 1000 次/10 分鐘 → 每 2 秒走進 `blockAccountByToken` → `getGenUserByUserId` 查無 → reject → 印 3 行 console (`can not find the user by id`) 永不停止.
- 事實上 app token **從未被封鎖** (封鎖對象是使用者, app token 無使用者), 但這是靠失敗路徑達成的隱性豁免 (全域規範 §8 第四類「有 A→B 卻靠例外攔住」).

**Decision**:
- `blockAccountByToken` 取得 token 物件後, `isApp==='y'` 即 `srLog.debug({ event:'fun-blockAccountByToken', key:'appTokenSkipRateLimit' })` 並 return, 不查使用者、不封鎖. 行為與現況相同 (本來就沒封成), 只是把隱性豁免寫成顯性規則並消除 console 洗版.
- 政策宣告: **app token 不受個人 token 速率封鎖** (`numForTokenCallApi`). 理由: app token 代表整個引用系統的流量, 上限以「單一使用者」尺度訂定不適用; app token 應僅由內部簽發且不開放外部註冊 (`procCore.mjs:438` 既有註解), 其濫用防線為 token 保管與 IP 層封鎖 (`numForIpCallApi`, 對 app 所在 IP 仍生效).
- `procProtect` 之 `getTokenByKV` 每 2 秒仍會執行一次 (與現況同), 不另做 kpTokenCallApi 剔除 (保持最小改動).

**驗證** (2026-09-01):
- `test/api-autoblock-apptoken.test.mjs`: 以 `numForTokenCallApi=5` 之臨時 settings 重啟後端, `token-for-app` 連打 8 次 → 3 秒後仍有效 (checkToken true、tokens 表仍存在); 對照組 `token-for-basic` 同法 → 3 秒後失效 (封鎖機制確實觸發).
- 既有 `e2e-autoblock` token-block 案例語意不變.

**Consequences**:
- ✅ SSO console 不再每 2 秒印 3 行; 豁免規則可讀可測.
- ⚠️ 引用方若把 app token 外流, 速率封鎖不會攔它 (現況本來就攔不住); 保護在 IP 封鎖與 token 保管.

**Affected**:
- server/procProtect.mjs (blockAccountByToken isApp 早退; opt 增 srLog) / server/WWebSso.mjs (傳 srLog)
- spec/流程_自動封鎖機制.md (B09a) / test/api-autoblock-apptoken.test.mjs (新)
- 對齊 ADR-045 (cache 失敗處置維持)、ADR-050 (settings 新鍵 opt-in)
