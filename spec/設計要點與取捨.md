## ADR-001: Multi-session 接受 (同帳號多 active token 並存)

**Status**: Accepted (2026-06-08)

**Context**:
- 業主需求為「同一使用者可在多裝置 / 多瀏覽器同時保有登入態」(辦公桌 PC + 手機 + 平板情境). 若每次新登入就 invalidate 既有 token, 跨裝置體驗會被打斷, 與業主期待不符.
- Audit F-046 指出 `loginByAccountAndPassword` 並行調用時, 若同時走「先查既有 token 是否仍有效→無則新發」邏輯, 存在 check-then-act race condition, 可能同瞬間發出 2 張 token. 若強行修補此 race, 需引入 per-user lock / 序列化, 換來的卻是與業主多裝置需求衝突的「單 active token」語意.
- 不解決層面: race 修補的工程代價遠大於踩到的代價 (同帳號同一瞬間發 2 張 token, 兩張皆合法、皆可用, 並不造成資料污染或權限越界).

**Decision**:
- 採「同帳號多 active token 並存」模型: 每次 `loginByAccountAndPassword` 成功皆發新 token, **不 reuse 既有 token、不 invalidate 既有 token**.
- 同一裝置同一瀏覽器內已快取 token 時, 前端 `autoLogin` (mUI.mjs) 於 App 啟動階段 short-circuit, 直接以快取 token 入站, 不會重打 `loginByAccountAndPassword`. 故「重複登入打 API」場景僅出現於跨裝置 / 跨瀏覽器 / 清空 localStorage 後再登入.
- `logoutByToken` 只 invalidate **當下這張** token (清 localStorage + 後端刪除該 token record), 不影響同帳號其他裝置 active session.
- F-046 race 標為 **Accepted by design**, 不修.

**Consequences**:
- ✅ 跨裝置 / 跨瀏覽器多 active session 流暢, 對齊業主需求.
- ✅ 同瀏覽器內 reload 由 frontend autoLogin short-circuit, 不會反覆觸發後端發 token, 後端負載合理.
- ✅ 省去 per-user lock 工程複雜度與其衍生的死結 / 效能風險.
- ⚠️ 同一瞬間並行登入仍可能發出 2 張 token, 兩張皆合法可用 (無實質危害, 但 audit log 會看到 2 筆相鄰 token 簽發).
- ⚠️ 使用者懷疑帳號被盜時, 自助登出僅清掉「當下這張」token, 其他裝置 session 不受影響; 須走 admin 手動清 (或變更密碼後等既有 token 自然到期, 見 ADR-009 multi-device session 獨立).
- ⚠️ Admin 後台金鑰清單會出現同帳號多筆 active token, 屬預期行為, 不視為異常.

**Affected**:
- spec/流程_使用者一般登入.md
- spec/流程_使用者登出.md
- spec/流程_後台金鑰清單.md
- spec/流程_自動封鎖機制.md
- server/procCore.mjs (loginByAccountAndPassword / logoutByToken)
- src/plugins/mUI.mjs (autoLogin short-circuit)

## ADR-002: 訊息呈現分流 (modal / toast / inline)

**Status**: Accepted (2026-06-08)

**Context**:
- 早期程式碼混用 `alert()` / `$alert` / 自訂 modal 三種呈現方式, 一個流程結果有時走 modal、有時走 toast、有時走 inline 紅字, 體驗割裂.
- 全域 §5.1 已禁用瀏覽器內建 `alert()` (e2e 截不到圖、無法 pixel baseline). 但即使全面改成 DOM 模態, 仍須訂出**何時用哪一種**的契約, 否則「成功 modal / 失敗 modal / 例外 toast」混淆會讓使用者誤判操作是否成功.
- 不解決會踩到: e2e 視覺回歸缺口 (toast 4s 自動消失難 baseline)、使用者對「無感操作」與「失敗操作」分辨不清、跨流程體驗不一致.

**Decision**:
- **操作結果 (成功 / 可預期失敗)** → `vo.$dg.showCheckYes` 持久 modal, 須點 OK 才消失. 含: 註冊成功、變更密碼成功、admin 儲存 Users/IPs/Tokens 成功、重設密碼成功等.
- **非預期例外** (catch 區內無從預期之 throw / network down / 後端 500) → `vo.$alert(vo.$t('anUnexpectedErrorOccurred'), { type: 'error' })` 低調 toast, 4s 自動消失. 設計意圖: 非預期錯誤應低調, 用 modal 反而過度放大、傷感受可靠度.
- **欄位驗證** (帳號為空 / 密碼過短 / email 格式錯) → inline 紅字 (reactive error var), 不彈窗.
- **Yes/No 確認** (刪除前確認 / 解除權限前確認) → `vo.$dg.showCheckYesNo` modal.
- **載入失敗 fallback 區塊**: 初次 mount 之 getAndRelaData (LayoutContentUserInfor / LayoutContentStaInfor) 用 `v-if="!firstLoading && !errMsg"` 控制主內容渲染, errMsg 有值時走 v-else 顯示 i18n 載入失敗訊息. 與其他 3 類訊息不同: (a) 阻塞性質介於 modal 與 inline 之間 (主內容隱藏, 但無 OK 按鈕需點); (b) 通常為「token 失效 / 後端不通」之系統性錯誤, 非單欄位驗證.
- 對齊 §5.1 「非同步提交的 core() + finally 統一寫法」: inline 錯誤於進 core() 第一步清空, 同步檢測階段填 inline 錯誤並 early-return, 確定要打 API 才開 loading, 外層 catch 才走 $alert 收非預期例外.

**Consequences**:
- ✅ 三種訊息類型一目了然, 使用者立刻分辨「我做的事成功了 / 我輸入的東西錯了 / 系統出了意料外的問題」.
- ✅ 持久 modal 與 inline 紅字皆可 pixel baseline e2e 回歸守護, 取代原本 alert / toast 的 e2e 盲區.
- ✅ 非預期錯誤的 toast 不放大警訊, 對偶發網路抖動友善, 不打斷使用者主流程.
- ⚠️ 新增流程時須在「結果 / 例外 / 驗證 / 確認」四種之間正確分類, 分錯會體驗錯位 (例如把可預期失敗丟去 toast 反而會被忽略).
- ⚠️ toast 4s 自動消失無法 pixel baseline, 故 e2e 對「非預期例外」case 僅做語意斷言 (text contains), 不做整頁 byte-equal — 此為設計取捨, 不視為測試缺口.

**Affected**:
- src/components/PageLogin.vue (register / login error handling)
- src/components/PageUser.vue (changePassword / forceChangePw)
- src/components/LayoutContentUsers.vue
- src/components/LayoutContentTokens.vue
- src/components/LayoutContentIps.vue
- src/components/LayoutContentStaInfor.vue
- src/components/LayoutContentUserInfor.vue
- spec/流程_使用者創建帳密.md
- spec/流程_使用者變更密碼.md
- spec/流程_後台新增使用者.md
- spec/流程_後台IP清單.md
- spec/流程_後台金鑰清單.md

## ADR-003: 防帳號列舉 — 失敗訊息統一化

**Status**: Accepted (2026-06-08)

**Context**:
- 登入 / 自助註冊 / 重寄驗證信流程皆面臨「帳號不存在 / 密碼錯誤 / 帳號停用 / 帳號未驗證 / 帳號過期」等多種失敗原因.
- 若前端直接呈現具體原因, 攻擊者可逐筆試帳號清單以推斷哪些帳號已存在 (account enumeration), 大幅降低後續鎖定攻擊 / 釣魚攻擊的成本.
- 不解決會踩到: 帳號列舉、admin 帳號被識別後遭針對性攻擊、與 `getSsoUserInfor` 限制 (ADR-004) 對齊原則受損.

**Decision**:
- 後端 `loginByAccountAndPassword` 對外回傳統一字串 (`'incorrect user account or password'`) 涵蓋: 帳號不存在、密碼錯誤、`isActive !== 'y'`、`timeVerified` 為空 (未驗證)、帳號過期等多種情境.
- 後端內部 log 仍保留具體 reject 原因, 供 audit / 維運時追溯, 不影響資安信號.
- 前端 PageLogin 登入失敗 handler 將後端回傳訊息原封呈現於 modal, 不嘗試解析或補充細節.
- 同樣原則延伸至自助註冊 (註冊用 email 已存在不揭露)、重寄驗證信 (帳號不存在 / 已驗證皆統一訊息) — 不對外洩露「該 email 是否已註冊」此一 bit.

**Consequences**:
- ✅ 攻擊者無法以登入失敗訊息辨識帳號是否存在, 大幅提高列舉成本.
- ✅ 後端內部 log 保留 audit 細節, 不影響維運追查.
- ✅ 跨流程訊息語意一致, 前端 PageLogin / register 共用同套呈現邏輯, 降低維護負擔.
- ⚠️ 真實使用者輸錯帳號時, 看不到「您打錯帳號」或「您的密碼錯了」的差異, 排查體驗略差 — 屬安全與 UX 的取捨.
- ⚠️ 帳號停用 / 未驗證的情況也走同訊息, 使用者可能誤以為密碼錯, 反覆嘗試後觸發 ADR-013 自動封鎖. 屬已知體驗代價.

**Affected**:
- server/procCore.mjs:287, 302, 310 (loginByAccountAndPassword reject 點)
- src/components/PageLogin.vue:781-782 (login error mapping)
- spec/流程_使用者一般登入.md
- spec/流程_使用者創建帳密.md
- spec/流程_查詢使用者資訊.md

## ADR-004: `getSsoUserInfor` 收緊 IDOR — 限 admin / app caller

**Status**: Accepted (2026-06-08)

**Context**:
- `/api/getSsoUserInfor` 原開放給任何持有有效 token 的使用者呼叫, 可以「給定 userId / account / email」查詢任一使用者資訊.
- 結果: 任一登入使用者可窮舉所有 userId, 列舉系統內所有帳號 (含 admin 帳號) 並取得其基本資料 (姓名 / email / 角色), 屬 IDOR (Insecure Direct Object Reference) 漏洞.
- 不解決會踩到: 一般使用者可偵察到 admin 帳號, 接著針對 admin 做密碼噴灑 / 釣魚, 大幅降低系統整體安全性.

**Decision**:
- 收緊 `getSsoUserInfor` 為 caller mode (a): `{ fun: funCheckAdmin }`, 僅 admin 使用者或 app token 可呼叫.
- 利用 app token 的 `isApp='y'` 自動 bypass `fun` 檢查的語意 (見 ADR-005), `funCheckAdmin` 一個檢查同時涵蓋「admin 使用者」與「app token」兩種合法 caller, 不需新增 `funCheckAdminOrApp`.
- 一般使用者欲查自己資訊改走 `getUserByToken` (token 即身份, 無 IDOR 風險).

**Consequences**:
- ✅ 阻擋一般使用者列舉系統帳號, 消除 IDOR 漏洞.
- ✅ app token 仍可正常呼叫此 API 做 server-to-server 查詢, 不影響系統整合場景.
- ✅ 利用 ADR-005 `isApp` bypass 機制, 程式碼簡潔, 無新增權限分類.
- ⚠️ 若系統未來新增「使用者可查其他使用者」之需求 (例如 user directory), 須另開 endpoint 並重新設計權限. 此 API 不可再放寬.

**Affected**:
- server/WWebSso.mjs:1110, 1114, 1341 (getSsoUserInfor 路由與 RPC 入口)
- server/procCore.mjs:400 (isApp bypass 語意)
- spec/流程_查詢使用者資訊.md

## ADR-005: App token (`isApp='y'`) 跳過 `fun` 驗證

**Status**: Accepted (2026-06-08)

**Context**:
- 系統需要兩類 caller 身份: (1) 經 `loginByAccountAndPassword` 取得 token 的使用者; (2) 內部系統 / 第三方整合服務以預配 app token 直接呼叫 API.
- 若每個受保護 endpoint 都要寫「先試 user `fun` 檢查 → 失敗再試 app token 檢查」雙路徑, 程式碼會大幅重複, 且易遺漏其中一條.
- 不解決會踩到: 維運須為每個 endpoint 分別維護 user / app 兩套權限檢查, 一不慎就漏寫導致 app 整合失敗或權限放寬.

**Decision**:
- App token (建立時 `isApp='y'`) 於 `_checkTokenByObj` (procCore.mjs:412) 階段自動 bypass `fun` 檢查 — 不論 handler 傳入的 `opt.fun` 是 `funCheckAdmin` / `funCheckUser` / 其他, 一律視為通過, 由此 token 持有人 (app) 被視為 admin 等級身份.
- App token 僅供「內部簽發」, 不對外開放使用者自助建立 (註冊流程無從產生 `isApp='y'` token). 信任邊界由「token 簽發過程」守住, 而非「驗證過程」.
- Handler 端只需寫一個 `fun` (通常為 `funCheckAdmin`) 即可同時授權「admin 使用者」與「app token」.

**Consequences**:
- ✅ 每個受保護 endpoint 只寫一個 `fun` 檢查, 同時涵蓋兩類合法 caller, 程式碼簡潔.
- ✅ 信任邊界集中於「token 簽發」, 不分散於各 endpoint, 易於 audit.
- ✅ 與 ADR-004 `getSsoUserInfor` 收緊機制無縫對齊, 同一個 `funCheckAdmin` 服務兩類合法 caller.
- ⚠️ 一旦 app token 外洩, 等同 admin 帳號外洩, 後果嚴重. 須將 app token 視為高敏資料, 限制傳遞通路與儲存方式.
- ⚠️ 未來若需新增「app token 不應做 X 但 admin 可以」之差異化權限, 此設計無法直接表達, 須擴充驗證機制.

**Affected**:
- server/procCore.mjs:400, 412 (`_checkTokenByObj` `isApp` bypass)
- server/WWebSso.mjs (所有 `{ fun: funCheckAdmin }` 之 handler)
- spec/流程_查詢使用者資訊.md

## ADR-006: `checkToken` 對外統一 `'token expired'`

**Status**: Accepted (2026-06-08)

**Context**:
- Token 驗證可能因多種原因失敗: token 不存在 (從未簽發或已被刪)、token 過期、token 對應 user 已被停用、token 對應 user 不符 `fun` 要求 (例如非 admin 卻打 admin 限定 API).
- 若 API 對外回傳不同 reject 訊息, 攻擊者可透過試探不同 token 值反推出 (a) 哪些 token 字串「曾存在過」(token 不存在 vs token 過期訊息不同)、(b) 哪些帳號被停用、(c) 哪些帳號是 admin.
- 不解決會踩到: token / 帳號狀態 / 角色之 information leakage, 削弱 ADR-003 防列舉與 ADR-004 IDOR 收緊的成效.

**Decision**:
- `checkToken` (procCore.mjs:524) 對外一律回傳 `'token expired'` 字串, 不論真實 reject 原因為何 (不存在 / 過期 / user 停用 / 不符 fun).
- 後端內部 `_checkToken` 仍保留具體布林與字串分流, 供 log 與內部呼叫者判斷.
- 此原則同樣套用於 `getSsoUserInfor` / stats endpoints / 其他經 `funCheckAdmin` 的 API: 不符權限的 caller 一律看到 `'token expired'`, 不暴露「你的 token 有效但你不是 admin」之差別.

**Consequences**:
- ✅ 攻擊者無法從 reject 訊息推斷 token / 帳號 / 角色狀態, 全面對齊 defense-in-depth.
- ✅ 內部 log 仍保留 audit 細節, 不影響維運.
- ✅ 與 ADR-003 防帳號列舉、ADR-004 IDOR 收緊形成一致的「對外不洩露細節」契約.
- ⚠️ 真實 token 過期的使用者與「token 仍有效但權限不足」的使用者看到同訊息, 客服排查時須以後端 log 為主, 不能單靠使用者回報的訊息判別.
- ⚠️ 前端見到 `'token expired'` 一律走「清 LS token + 跳回登入頁」流程, 若使用者實際是權限不足 (例如非 admin 誤入 admin 頁面), 也會被登出 — 屬可接受的副作用, 與權限模型對齊.

**Affected**:
- server/procCore.mjs:486, 524 (checkToken / `_checkToken` 統一 reject 訊息)
- spec/流程_查詢使用者資訊.md (E2E-002 描述 unified 'token expired' 行為)
- spec/流程_使用者自動登入.md

## ADR-007: Password hash 比對採 `crypto.timingSafeEqual`; token 比對使用 `===`

**Status**: Accepted (2026-06-08)

**Context**:
- 密碼比對若使用 `===` 短路比對, 理論上字串前綴匹配長度愈長、比對時間愈長, 攻擊者可透過遠端計時推測 hash 內容 (timing side-channel).
- 實務上: 帳號自動封鎖 (ADR-013) 已大幅限制可探測次數, 遠端 timing 攻擊在本系統環境下不切實際. 但 defense-in-depth 原則仍應採時間恆定比對.
- Token 比對則為另一情境: token 為 UUIDv7 (128-bit entropy), 純隨機, 無前綴規律可言; 加上 LMDB in-memory 儲存, 比對快至毫秒以下, timing 訊號被網路抖動完全淹沒, 攻擊不可行.
- 不解決會踩到: 密碼若採 `===` 雖實質安全, 但無法回應 audit 對 best-practice 的要求; token 若強行套 timing-safe 比對, 徒增複雜度無實質防禦.

**Decision**:
- **Password hash 比對**: `procCore.mjs:46` 新增 `timingSafePasswordEqual` helper, 包裝 `crypto.timingSafeEqual` + 額外 length check (防 DB corruption / 空字串造成 throw). 同時用於 `loginByAccountAndPassword` (procCore.mjs:295) 與 `changeUserPassword` (procCore.mjs:1008) 之舊密碼驗證.
- **Token 比對**: 保留 `===` (procCore.mjs:448), 標註設計意圖 — UUIDv7 entropy + LMDB in-memory 已足夠, timing-safe 無實質收益.
- 兩種比對在程式碼中明確區隔, 不可後續一視同仁套同一種比對.

**Consequences**:
- ✅ Password 比對達 best-practice timing-safe, 回應 audit defense-in-depth 要求.
- ✅ Token 比對保留簡潔 `===`, 不引入無意義的複雜度.
- ✅ 兩種比對的設計意圖明示於 code comment (procCore.mjs:46, :448), 後續維護者不會誤判.
- ⚠️ 若未來改用其他 token 簽發機制 (例如可預測短字串 token), 須重新評估是否要切換為 timing-safe 比對 — 此 ADR 之決策建立在 UUIDv7 假設上.

**Affected**:
- server/procCore.mjs:46 (timingSafePasswordEqual helper)
- server/procCore.mjs:295 (loginByAccountAndPassword)
- server/procCore.mjs:448 (token `===` 比對, 設計註記)
- server/procCore.mjs:1008 (changeUserPassword 舊密碼驗證)
- spec/流程_使用者一般登入.md
- spec/流程_使用者變更密碼.md

## ADR-008: Admin 寫入後即時 invalidate 30s cache

**Status**: Accepted (2026-06-08)

**Context**:
- 後台 Users / Tokens / IPs 三份清單與其 stats 查詢 (procStaInfor) 套用 30s read-through cache (wsemi cache), 大幅降低高頻外部讀取對 DB 的負載.
- 但 admin 在後台對清單做寫入 (新增 user / 修改 IP 白名單 / 撤銷 token) 後, 若必須等 30s cache 自然過期才看到變更, 體驗很差 — admin 會以為「儲存沒成功」並重複點擊, 引發 ADR-012 寫入後 race / 重複 commit.
- 不解決會踩到: admin 寫完看不到結果、重複送、UX 與資料一致性兩頭損.

**Decision**:
- 每個 admin 寫入路徑 (`checkTokenAndUpdateUsersList` / `checkTokenAndUpdateTokensList` / `checkTokenAndUpdateIpsList`) 於**成功寫入後**立即呼叫 `cache.clear('fun')` 對應 key, 清掉相關 list 的 cache.
- Cache invalidation 必須放在「寫入成功後」, 不放在 reject 路徑 — 寫入失敗時 DB 未變、cache 不應清, 反而會增加無謂的 DB 重抓.
- 採 wsemi cache `needExec=true` 機制: 清空後保留 TTL 設定不變, 下次讀取觸發重新計算並重設 30s TTL.
- 外部高頻讀取 (例如 stats summary 被多前端 polling) 仍享 30s cache 加速; 只有「admin 剛寫入」這條時序窗口會繞過 cache.

**Consequences**:
- ✅ Admin 寫入後 dashboard 立刻同步, 無 30s 等待延遲.
- ✅ 外部高頻讀取仍享 cache 加速, 系統整體負載不受 invalidation 影響.
- ✅ Cache 與 DB 一致性由「寫入即清」契約保證, 不會出現「DB 已更新但 cache 仍舊」之窗口 (對 admin 視角而言).
- ⚠️ 多 admin 並發寫入時, 兩次 invalidation 可能相鄰但仍正確 — 每次 invalidation 後緊接的下一次讀取都會 trigger 重抓, 不會殘留舊資料.
- ⚠️ 若未來新增「非 admin 路徑」的寫入 (例如使用者自助更新某欄位), 須同步加上對應 cache invalidation, 否則會出現「使用者寫了但 stats 仍舊」.

**Affected**:
- server/procCore.mjs:1613, 1731, 1789 (checkTokenAndUpdate*List 之 cache 清除)
- server/procStaInfor.mjs:46 (cache read 端)
- spec/流程_後台新增使用者.md

## ADR-009: Multi-device session 獨立 (變更 / 重設密碼後不清除既有 token)

**Status**: Accepted (2026-06-08)

**Context**:
- 使用者變更密碼 (主動) 或 admin 重設使用者密碼 (被動) 後, 既有的多裝置 active token 是否要全部 invalidate?
- 若強制 invalidate: 安全性較好 (假設密碼被盜, 重設後立刻趕走所有 session), 但與 ADR-001 multi-session 接受相衝突 — 使用者只是定期變更密碼也會被踢下所有裝置, 體驗極差.
- 若不 invalidate: 既有 token 持續可用至自然到期, 多裝置體驗順暢, 但若密碼真的被盜, 攻擊者持有的 token 仍可繼續使用至到期.
- 不解決會踩到: 安全性與 UX 兩頭擺盪, 無清楚契約.

**Decision**:
- 採「不清除既有 token」策略: 變更密碼 (流程_使用者變更密碼) 與重設密碼 (流程_後台重設使用者密碼) 後, 既有 token 不被 invalidate, 多裝置可繼續使用至自然到期 (見 ADR-010 token 效期).
- 使用者若疑似帳號被盜, 須額外由 admin 走「後台金鑰清單」手動撤銷該帳號所有 token, 或等既有 token 自然到期 (預設 `minExpired` 分鐘, 通常數小時).
- 此決策對齊 ADR-001 multi-session 接受 — 同一信念: 「session 生命週期由 token 自身控制, 不被密碼操作牽動」.

**Consequences**:
- ✅ 變更密碼為日常維運操作, 不打斷多裝置體驗, 對齊業主需求.
- ✅ 與 ADR-001 multi-session 接受形成一致的 session 模型, 不出現「multi-session 但密碼變更就清空」的不一致.
- ✅ 對齊「token 即身份」原則 — token 一旦簽發, 其有效性由自身 `timeEnd` 控制, 不受其他欄位影響.
- ⚠️ 密碼真的外洩時, 攻擊者持有的 token 不會立即失效, 仍可用至到期; 此為已知 trade-off, 對應的緊急應變方案為「admin 手動撤銷所有 token」.
- ⚠️ Spec 明確記載此為設計取捨, 不視為 audit finding.

**Affected**:
- server/procCore.mjs (changeUserPassword / adminResetUserPassword 不觸及 token table)
- spec/流程_使用者變更密碼.md
- spec/流程_後台重設使用者密碼.md
- spec/流程_自動登入.md

## ADR-010: Token 效期與 session 管理約定 (`minExpired`, localStorage 清空慣例)

**Status**: Accepted (2026-06-08)

**Context**:
- Token 簽發、自動登入、登出三條流程須共用同一套 token 生命週期定義, 否則前端與後端會對「token 何時失效」「LS 何時清空」做不同假設.
- 不解決會踩到: 登出後 LS 殘留舊 token 字串、自動登入誤判失效 token 為有效、token 自然到期前後行為不一致.

**Decision**:
- Token 建立時 `timeEnd = now + minExpired` 分鐘 (`minExpired` 由 settings.json 設定, 預設數小時等級).
- 登出時前端將 LS token **設為空字串** (`localStorage.setItem('token', '')`), 非 `removeItem`. 此慣例讓「未曾登入」與「登出後」皆呈現空字串, 自動登入端統一以 `isestr(token)` 判 falsy.
- 自動登入啟動時讀 LS token, 若 `isestr` 為 falsy 則直接視為未登入, 不打後端 API; 若 truthy 則送後端 `checkToken` 驗證, 後端依 `timeEnd` 判斷.
- Token 自然到期不主動清 LS — 由下一次自動登入呼叫 `checkToken` 時被後端拒, 前端再清 LS + 跳登入頁.

**Consequences**:
- ✅ 三條流程共用同一 token 生命週期定義, 前後端假設一致.
- ✅ LS 空字串慣例讓「未登入」與「登出」狀態統一, 簡化 autoLogin 入口判斷.
- ✅ Token 自然到期由後端權威判斷, 前端不做時鐘比對, 避免前端時鐘漂移造成的不一致.
- ⚠️ 使用者登出後 LS 仍留 token key (值為空字串), 在某些 LS 偵測工具看來會被誤判為「有此 key」. 屬已知慣例.
- ⚠️ Token 自然到期前 (例如剩 1 分鐘) 使用者仍可進行操作, 中途突然失效 — 前端須對所有受保護 API 的 `'token expired'` reject 統一處理 (清 LS + 跳登入頁).

**Affected**:
- server/procCore.mjs (loginByAccountAndPassword / logoutByToken / checkToken)
- src/plugins/mUI.mjs (autoLogin / setToken / clearToken)
- src/App.vue (initialization)
- spec/流程_使用者一般登入.md
- spec/流程_使用者自動登入.md
- spec/流程_使用者登出.md
- spec/流程_使用者變更密碼.md

## ADR-011: cleanTokens timer disabled (token 不主動清掃)

**Status**: Accepted (2026-06-08)

**Context**:
- 早期設計考慮過「定期 timer 掃描 tokens table, 把已過 `timeEnd` 的 token 自動刪除」以節省 DB 空間.
- 但實作後發現: timer 觸發時若該 token 對應之 user 仍在使用 (browser tab 開著未關), 即便 token 已過 `timeEnd` 也可能仍持有 — 自動清除等於把使用者強制踢下線, 與 ADR-001 multi-session 接受 / ADR-009 多裝置獨立精神衝突.
- 不解決會踩到: 使用者 SSO session 在莫名時間被踢、無預警跳回登入頁、體驗破裂.

**Decision**:
- cleanTokens timer **disabled**, 不主動清掃過期 token.
- 過期 token 改由「下次被 checkToken 驗證時」自然判定為失效 (見 ADR-010), 此時前端會清 LS 並跳登入頁, 對使用者而言是「我打開頁面才看到要重新登入」, 而非「我正在用就突然被踢」.
- 已過期但未被驗證的 token 仍留在 DB, 由 admin 後台金鑰清單檢視 (此清單不過濾過期, 見 ADR-012).
- DB 空間影響微乎其微 (token record 小、UUIDv7 + 少數欄位), 不需主動回收.

**Consequences**:
- ✅ 使用者 session 體驗一致 — 只有「自己嘗試操作」時才會看到要重新登入, 永不被無預警踢線.
- ✅ 對齊 ADR-001 / ADR-009 的 session 獨立精神, 系統不主動操弄 session 生命週期.
- ✅ 省去 timer 邏輯與其潛在 race condition (例如清掃時剛好有 refresh / login 寫入).
- ⚠️ 過期 token 累積於 DB, 長期看 token table 會持續增長. 預計每年增長量可接受 — 若未來需空間回收, 須另開 admin 手動 / 批次清掃機制, 不可重新啟用定期 timer.
- ⚠️ Admin 後台看到大量過期 token, 須以 `timeEnd` 欄位自行判讀, 對應 ADR-012.

**Affected**:
- server/procCore.mjs (cleanTokens 函式或對應 timer 註冊處)
- server/procProtect.mjs
- spec/流程_後台金鑰清單.md
- spec/流程_使用者自動登入.md

## ADR-012: `getTokensList` 不過濾過期 token (admin 自行判讀)

**Status**: Accepted (2026-06-08)

**Context**:
- 後台金鑰清單需呈現 tokens 給 admin 檢視. 若僅顯示「未過期」token, admin 無法看到歷史 session 紀錄、無法追溯「該帳號過去從哪些 IP 登過」等 audit 需求.
- 若全部顯示 (含過期), admin 須自行以 `timeEnd` 欄位判讀哪些仍 active. 與 ADR-011 「不主動清掃」對齊.
- 不解決會踩到: admin audit 資訊不全 / 顯示邏輯與資料庫實際內容不一致.

**Decision**:
- `getTokensList` 回傳**全部** tokens, 不依 `timeEnd` 過濾.
- 後台金鑰清單 UI (LayoutContentTokens.vue) 顯示 `timeEnd` 欄位, admin 可依此判斷 active / 過期.
- 同帳號可能因 ADR-001 multi-session 出現多筆 token, 屬預期行為.
- API 回傳前剝除 `password` 等不相關欄位 (見 ADR-014), 但 `timeEnd` / `isApp` / `timeCreate` 等 audit 欄位保留.

**Consequences**:
- ✅ Admin 取得完整 audit trail, 可追溯歷史 session.
- ✅ 與 ADR-011 「不主動清掃」對齊, DB 與顯示一致.
- ✅ Admin 可主動以 UI 排序 / 篩選 `timeEnd` 自行決定看 active 或全部.
- ⚠️ Tokens 數量隨時間增長, 清單可能變長; 未來若超出可用視覺量級, 須加分頁或預設過濾 (但仍提供「顯示全部」選項).
- ⚠️ Admin 須具備判讀 `timeEnd` 的能力, 不能誤把「過期 token」當作「仍可登入的 session」.

**Affected**:
- server/procCore.mjs (getTokensList / checkTokenAndGetTokensList)
- src/components/LayoutContentTokens.vue

## ADR-013: 帳號自動封鎖採「隱性解除」(比對當前時間, 不主動清 `timeBlocked`)

**Status**: Accepted (2026-06-08)

**Context**:
- 連續登入失敗超過閾值時, 系統將 `users.timeBlocked` 寫為「現在 + 封鎖分鐘數」, 之後比對來判斷該帳號是否仍被封鎖.
- 封鎖時間到期後如何「解除」? 兩種選項: (a) 顯性 — 用 timer 定期掃描, 把已到期的 `timeBlocked` 清空; (b) 隱性 — 不主動清, 只在每次查詢時用「現在 vs timeBlocked」比對判定.
- (a) 涉及額外 timer 邏輯、可能與寫入操作 race; (b) 簡單但須保證所有查詢點皆採同樣比對邏輯.
- 不解決會踩到: 封鎖到期後行為不一致、timer 與寫入 race、額外維運負擔.

**Decision**:
- 採 (b) 隱性解除: 不主動清 `timeBlocked` 欄位, 解除完全靠「當前時間 vs timeBlocked」比對.
- 所有判定封鎖狀態的位置統一走 `procCore.getBlockedByUser` (account 自動封鎖) 與 `procCore.getBlockedByOip` (IP 自動封鎖), 兩函式內部統一比對邏輯, 不在各 caller 自行比對.
- `timeBlocked` 欄位永久保留歷史封鎖時間, 同時作為 audit 紀錄 (admin 可看到該帳號何時曾被封鎖).
- 對應 IP 封鎖機制同此原則, 見 spec/流程_自動封鎖機制.md.

**Consequences**:
- ✅ 省去 timer 邏輯與 race condition.
- ✅ `timeBlocked` 同時兼任 audit 欄位, 不需額外封鎖歷史 table.
- ✅ 所有判定點統一函式入口, 比對邏輯一致, 不會出現「某處判到期、某處沒判」的差異.
- ⚠️ 須保證**所有**查詢封鎖狀態之處都走 `getBlockedByUser` / `getBlockedByOip`, 不可有 caller 自己讀 `timeBlocked` 後做比對 — 否則容易遺漏隱性解除邏輯造成永久封鎖.
- ⚠️ 過期 `timeBlocked` 累積於使用者欄位 (每次新封鎖會 overwrite), 不會無限增長, 屬可接受.

**Affected**:
- server/procCore.mjs:getBlockedByUser, getBlockedByOip
- server/procProtect.mjs
- spec/流程_自動封鎖機制.md
- spec/流程_使用者一般登入.md (登入時封鎖檢查)
- spec/流程_使用者自動登入.md (autoLogin 時封鎖檢查)

## ADR-014: API 回傳前剝除 `password` 欄位

**Status**: Accepted (2026-06-08)

**Context**:
- `users` table 之 `password` 欄位儲存 hash 值. 即便為 hash 而非明文, 仍不應隨任何 API 回傳暴露於外 — 一旦外洩, 攻擊者可離線暴力比對.
- 多個 API 回傳 user 物件 (後台 Users 編輯、新增、查詢使用者資訊), 若任一條漏寫剝除邏輯就會洩露 hash.
- 不解決會踩到: hash 隨 API 回傳洩露、攻擊者離線比對風險、相關 audit 不通過.

**Decision**:
- 所有回傳 user 物件之 API 統一在回傳前剝除 `password` 欄位.
- 統一在 `procCore.getGenUserByKV` (或其衍生) 回傳路徑做剝除, 而非各 handler 自行處理 — 集中於一處降低遺漏風險.
- 此原則延伸至: `checkTokenAndUpdateUsersList` (新增 / 修改回傳)、`checkTokenAndDeleteUsers`、`getSsoUserInfor`、`getUserByToken` 等所有暴露 user 物件之 endpoint.

**Consequences**:
- ✅ Hash 值不隨任何 API 洩露, 攻擊者無法離線比對.
- ✅ 集中剝除於一處, 不會因某 handler 漏寫而洩露.
- ✅ 與 ADR-003 / ADR-004 / ADR-006 對外不洩露細節的整體契約對齊.
- ⚠️ 內部 RPC 若需要 password (例如登入時驗證) 須走另一條路徑 (`procCore` 內部函式, 不經 API), 不可圖方便直接讀剝除後的物件.
- ⚠️ 未來新增「回傳 user 物件」之 endpoint 時, 須確認走過統一剝除路徑, 不可自行 query DB 後直接回傳.

**Affected**:
- server/procCore.mjs (getGenUserByKV 回傳路徑)
- server/WWebSso.mjs (所有暴露 user 物件之 handler)

## ADR-015: Stats 頁 e2e baseline 截 cards 區 (y:0..330) 排除動態 chart

**Consequences**:
- ✅ Stats 頁 e2e baseline 穩定可重現, 不再受 chart 動態渲染影響.
- ✅ Cards 區的視覺回歸 (i18n / layout / icon) 仍受守護.
- ✅ 維護成本降低, 不需反覆 regen 因 chart 微差導致的 flake.
- ⚠️ Chart 視覺改動 (例如 chart 換 library / 配色) 不被 e2e baseline 抓到, 須額外做人工 UAT.
- ⚠️ 若未來業主新增 cards 至 `y > 330` 之區域, 須調整截圖範圍.

## ADR-016: E2E hermetic seed lifecycle (resetToBaseSeed + insertTestUsers + deleteNonBaseSeed)

**Status**: Accepted (2026-06-08)

**Context**:
- E2E 測試彼此並行 / 順序執行時, 若共用 DB 而無清楚邊界, 一條測試殘留的 user / token / IP 會污染下一條測試的初始狀態, 造成 byte-equal baseline flake (對應全域 §6.3 「pixel 不一致 5 類成因」之第 1 類 DB 內容不同).
- 但若每條測試「整個 DB 清空再 seed」, e2e 啟動時間爆炸, 跑全套套件耗時不可接受.
- 不解決會踩到: e2e 跨測試污染、baseline flake、測試彼此耦合難 debug.

**Decision**:
- 採「base seed + 特化 seed」雙層: base seed (admin user + 必要基礎資料) 為所有 e2e 共用初始狀態, 測試啟動前由 `resetToBaseSeed` 重置至此.
- 個別 e2e 於 `before()` / 自己的 setup 階段以 `insertTestUsers` (或同類 helper) 插入本檔特化資料 (例如 `id-login-ok` user).
- 個別 e2e 於 `after()` / cleanup 階段以 `deleteNonBaseSeed` 移除本檔特化資料, 不動 base seed.
- 此契約使每條 e2e 「進場時 DB 等於 base seed」「出場時 DB 等於 base seed」, 順序 / 並行皆 hermetic.
- 對應全域 §6.3 rubric §5「Cleanup 完整」.

**Consequences**:
- ✅ E2E 彼此 hermetic, 不互相污染, baseline byte-equal 可靠.
- ✅ 不需「整個 DB 清空」, base seed 為共用基礎, 啟動成本可接受.
- ✅ Setup 與 cleanup 對稱, 防止測試殘留累積.
- ⚠️ Base seed 內容變動 (例如新增 admin 帳號 / 新增基礎 IP 白名單) 須同步更新所有 e2e 的預期, 屬統一變更負擔.
- ⚠️ 若 e2e 測試本身就是「驗證 admin 自我鎖死」(ADR 外的 spec 規則, 但相關), 須留意 base seed admin 不能被該測試刪除, 否則破壞 hermetic 契約.

**Affected**:
- test/e2e-setup.mjs (resetToBaseSeed / insertTestUsersAndTokens / deleteNonBaseSeed helpers)
- test/e2e-*.test.mjs (所有 e2e 檔)
- server/g.initialData.mjs (base seed 定義)

## ADR-018: 寄信失敗不阻擋流程結果 (SMTP fail 僅 log, 不 reject)

**Status**: Accepted (2026-06-08)

**Context**:
- 自助註冊 (寄驗證信)、重寄驗證信、變更密碼 (寄通知信)、後台重設密碼 (寄通知信) 等流程皆涉及寄信. SMTP 服務可能因外部因素失敗 (郵件供應商 down / 暫時 throttle / DNS 抖動).
- 若 SMTP 失敗就 reject 整個流程, 使用者註冊不成功、admin 重設密碼失敗 — 對「主操作」之 UX 影響大且非使用者本身的錯.
- 不解決會踩到: 寄信偶發失敗導致主流程整批失敗, 使用者反覆嘗試、admin 操作體驗破裂.

**Decision**:
- 寄信統一採 fire-and-forget 模式: 主流程 (例如 `createUser` / `changeUserPassword` / `adminResetUserPassword`) 完成 DB 寫入後觸發寄信, 寄信失敗僅記 console / log, **不 reject** 主流程.
- 使用者 / admin 視角為主操作成功 (帳號已建立 / 密碼已變更); 寄信若失敗, 使用者可主動走「重寄驗證信」流程補救, 或 admin 走 audit log 追查.
- 此契約由 `procCore.mjs` 寄信呼叫點之 `.catch(err => console.log(...))` 模式統一表達.

**Consequences**:
- ✅ 主流程不被外部 SMTP 抖動拖累, UX 穩定.
- ✅ 主操作成功之 DB 狀態與使用者視角一致, 不出現「使用者以為失敗但 DB 已寫入」之矛盾.
- ✅ 提供補救機制 (重寄驗證信 / audit log), 寄信失敗有可挽回路徑.
- ⚠️ 使用者可能完成註冊但收不到驗證信, 須自行察覺並走重寄 — 屬已知 UX 代價.
- ⚠️ 寄信失敗的 log 須有人定期檢視 (或上 alerting), 否則大量失敗會無聲累積. 屬維運責任, 不在程式碼契約內.

**Affected**:
- server/procCore.mjs (createUser / changeUserPassword / adminResetUserPassword 寄信呼叫點)
- server/template/*.html (email template)
- spec/流程_使用者創建帳密.md
- spec/流程_使用者變更密碼.md
- spec/流程_後台重設使用者密碼.md

## ADR-019: 強制變更密碼不可繞過 (`isForceChangePw` 旗標 + UI 鎖死)

**Status**: Accepted (2026-06-08)

**Context**:
- Admin 重設使用者密碼後, 使用者下次登入時須被強制變更密碼 (不可使用 admin 給的隨機密碼一直登入). 若使用者可繞過 (例如 close modal 後繼續使用), 安全強制流程失去意義.
- 不解決會踩到: 隨機密碼長期可用、admin 重設意圖被繞過、與 ADR-001 multi-session 對齊的「token 不被牽動」精神反而成為漏洞 (重設後 token 不失效 + 不強制變更 = 完全繞過).

**Decision**:
- Admin 重設後寫入 `users.isForceChangePw = 'y'`.
- 使用者下次登入後 (或自動登入後), 前端偵測該旗標, 自動展開變更密碼表單.
- 表單**取消按鈕隱藏** (只剩送出), 不可關閉 / 不可 close modal.
- 使用者唯一離開路徑為**登出**; 登出後重新登入仍會被拉回強制變更表單 (旗標未清).
- 變更密碼成功後, 後端清 `isForceChangePw` 旗標, 使用者恢復正常流程.

**Consequences**:
- ✅ 安全強制流程不可繞過, admin 重設意圖確實落地.
- ✅ 與 ADR-009 multi-device session 獨立並存 — token 不被 invalidate, 但使用者拿 token 進來後仍被強制變更.
- ✅ 使用者體驗清楚 — 只有兩條路: 改密碼 or 登出.
- ⚠️ 使用者若拒絕變更密碼, 等同放棄此帳號 (登出即等於無法回到後台). 屬安全前提.
- ⚠️ 強制流程的 UI 須與一般變更密碼共用 component 但動態隱藏取消鈕, 須謹慎處理 component 重用避免漏隱藏.

**Affected**:
- server/procCore.mjs (adminResetUserPassword 寫入旗標, changeUserPassword 清除旗標)
- src/components/PageUser.vue (偵測 `isForceChangePw` 展開表單, 隱藏取消鈕)
- spec/流程_後台重設使用者密碼.md
- spec/流程_使用者變更密碼.md

## ADR-021: 後台批次 upsert 契約 (`ltdtDiffByKey` add/diff/del 三分支, 整批 atomicity)

**Status**: Accepted (2026-06-08)

**Context**:
- 後台 Users / IPs / Tokens 三份清單採「整張表編輯」模式 — admin 在前端表格中任意新增 / 修改 / 刪除多列, 按「儲存」一次送出整張表的最新狀態.
- 後端須判斷哪些列是新增 / 修改 / 刪除, 並對每類各自驗證. 若任一列驗證失敗該如何處理?
- 不解決會踩到: 部分列成功部分失敗導致 DB 半邊資料, 或前端表格與 DB 狀態不一致.

**Decision**:
- 後端統一以 `ltdtDiffByKey` 比對前端送來的整張表 vs DB 現狀, 拆為 add / diff / del 三組.
- 對每組分別走對應驗證 (`ckKey` 檢查整表唯一性、欄位格式檢查、自我鎖死檢查 ADR-020 等).
- **任一驗證失敗整批 reject 不落地** — atomicity 由「全部驗證完才寫」契約守住.
- 寫入成功後立即 invalidate cache (見 ADR-008).

**Consequences**:
- ✅ DB atomicity 保證, 不會出現部分列成功部分失敗的中間狀態.
- ✅ Add / diff / del 三組分別處理, 各自的驗證邏輯不混淆.
- ✅ 與 ADR-008 cache invalidate-on-write 對齊, 寫入後 dashboard 立刻同步.
- ⚠️ Admin 一次編輯整張表時, 任一列錯誤導致整批 reject, 須回前端修正後重送; 若表很大且只錯一列, 重送的網路成本較高 — 屬可接受.
- ⚠️ 並發兩 admin 同時編輯同一張表, 後送者會以「自己看到的版本」覆蓋前送者的變更 (last-write-wins). 多 admin 並發編輯非設計重點, 屬已知限制.

**Affected**:
- server/procCore.mjs (checkTokenAndUpdateUsersList / TokensList / IpsList, updateTabItems)
- src/components/LayoutContentUsers.vue
- src/components/LayoutContentTokens.vue
- src/components/LayoutContentIps.vue

## ADR-022: 自助註冊驗證信採 server-rendered 結果頁 (非 SPA redirect)

**Status**: Accepted (2026-06-08)

**Context**:
- 自助註冊後使用者收到驗證信, 點擊 link 帶 token + lang 進系統. 點擊後使用者期待立即看到「驗證成功 / 失敗」結果頁.
- 若該 link 進 SPA, SPA 須等 JS 載入、router 解析 query、打 API 驗 token、依結果切換畫面 — 中間使用者看到的是 SPA 載入畫面, 體驗延遲且不確定.

**Decision**:
- 驗證 link 不進 SPA, 直接進後端 server-rendered HTML 頁 (`WWebSso.verifyEmail` handler).
- 後端收到 link 後同步驗 token, 直接回傳「驗證成功 / 失敗」之白底 HTML 頁.

**Consequences**:
- ✅ 驗證結果立即呈現, 無 SPA 載入延遲.
- ✅ Lang 端到端跟隨, 使用者看到的訊息與註冊時選擇的語系一致.
- ✅ 驗證流程獨立於 SPA, 即使 SPA 部分功能異常也不影響驗證可達性.
- ⚠️ 結果頁為 server-rendered, 樣式與主 SPA 不一致, 需額外維護一套簡化樣式.
- ⚠️ 結果頁無 i18n runtime 切換 — 使用者一進此頁就是當初註冊時的語系, 中途無切換鈕. 屬合理範疇.

## ADR-023: 多裝置 cleanKp endpoint 採 IP 白名單 (不信 X-Forwarded-For)

**Status**: Accepted (2026-06-08)

**Context**:
- `cleanKpIpCallApi` 與 `cleanKpAccountLoginFailed` 為 e2e 測試 cleanup 用 endpoint, 可重置 in-memory rate-limit / 自動封鎖計數器.
- 若這兩 endpoint 接受任意 caller, 攻擊者可外部觸發以繞過自動封鎖機制 (ADR-013).
- IP 限制若依 X-Forwarded-For header 判斷, 攻擊者可偽造 header. 須直接以 socket 層級 client IP 判斷.
- 不解決會踩到: 自動封鎖機制被外部 reset, 無法守住暴力試密碼閘.

**Decision**:
- `cleanKpIpCallApi` 與 `cleanKpAccountLoginFailed` 入口檢查 `socket.remoteAddress` (真實 TCP 連線來源), 不採 X-Forwarded-For.
- 來源 IP 須在 settings 中明確白名單清單內 (預設僅 127.0.0.1), 不在則 reject.
- E2E 測試於 localhost 跑, 天然滿足白名單; production 環境無此 endpoint 對外使用案例.

**Consequences**:
- ✅ 即使部署於 reverse proxy 後方 (proxy 帶 X-Forwarded-For), 此 endpoint 仍只信實際 TCP 連線來源, 無法被外部偽造繞過.
- ✅ 自動封鎖機制不會被外部 reset, defense-in-depth 完整.
- ✅ E2E cleanup 場景仍可用, 不影響測試可達性.
- ⚠️ 若未來部署架構變動 (例如真的需要從 proxy 後方某 trusted host 呼叫), 須擴充白名單機制 (例如允許多個白名單 IP / 子網), 不可改為信 X-Forwarded-For.
- ⚠️ Reverse proxy 配置不當時 (proxy 把 client IP 直接當 socket.remoteAddress 而非 X-Forwarded-For) 可能整套錯位, 屬部署層責任.

**Affected**:
- server/WWebSso.mjs:822, 879 (cleanKp* handlers IP 檢查)
- server/procProtect.mjs (getIpByHeaders 一般使用者流程, 與此契約對照)
- spec/流程_自動封鎖機制.md

## ADR-024: 前端 autoLogin cache-priority (LS token 優於 URL `?token`)

**Status**: Accepted (2026-06-08)

**Context**:
- 系統支援兩種 token 進入路徑: (a) localStorage 已快取的 token (上次登入留下); (b) URL `?token=...` 帶入 (例如其他系統 redirect 過來).
- 若兩者同時存在, 採用哪個? 若採用 URL token, 攻擊者可構造帶 token 的 URL 騙使用者點擊, 使用者瀏覽器原有 LS token 被覆寫, 等於被劫持 session.
- 若採用 LS token, 已有合法 session 的使用者不會被 URL 帶來的 token 偷換掉; 但需注意「使用者主動清 LS 後從別處 redirect 過來」之合法場景仍能進.
- 不解決會踩到: URL token 劫持風險.

**Decision**:
- `autoLogin` (mUI.mjs:520 區段) 優先使用 LS cached token; 若 LS 存在 truthy token, 即使 URL 帶 `?token=` 也忽略.
- 若 LS 為空 (`isestr` falsy), 才採用 URL `?token=`. 採用後寫入 LS, 後續一切以 LS 為準.
- 此契約使「single trusted session source = LS」成立, URL token 僅為「初次進入」之引導.

**Consequences**:
- ✅ 已登入使用者不會被 URL 帶來的 token 劫持, session 安全性提升.
- ✅ 仍支援「從外部系統 redirect 帶 token 進來」之合法場景 (LS 空時自動採用 URL token).
- ✅ 與 ADR-010 「localStorage 空字串慣例」對齊, `isestr` 判 falsy 為單一判定入口.
- ⚠️ 使用者若想「強制切換到 URL 帶來的新 token」, 須先手動登出 (清 LS), 再從 URL 進; 屬合理流程.
- ⚠️ 開發 / debug 時若想以 URL token 覆蓋當下 session, 須先清 LS, 體驗略繁瑣 — 屬可接受工程代價.

**Affected**:
- src/plugins/mUI.mjs:520 (autoLogin cache priority)
- src/App.vue (autoLogin 入口)
- spec/流程_使用者自動登入.md

## ADR-025: Secondary stats API 採 fire-and-forget (主 API 控 loading)

**Status**: Accepted (2026-06-08)

**Context**:
- 統計資訊頁 (LayoutContentStaInfor.vue) 同時呼叫多支 stats API: 主 API (例如 `getStaUserAccountLogin`) + 多個 secondary API (`getStaUserSummary` / `getStaTokenSummary` / `getStaIpSummary` 等).
- 若全部 await 串接, 任一 secondary 失敗會打斷所有更新; 若全部 `Promise.all`, 任一 reject 也會整批失敗.
- 不解決會踩到: 一個 secondary 失敗導致整個 dashboard 不顯示資料, 過於脆弱.

**Decision**:
- 主 API (`getStaUserAccountLogin`) 控制 `isLoading` state, 主資料就緒後立刻關 loading.
- Secondary API 採 fire-and-forget — 各自送 request 後不 await, 完成則更新對應 reactive 欄位, 失敗則空 catch (`.catch(() => {})`) 內部 console.log 不擴散.
- 任一 secondary 失敗時, 該卡片顯示「-」或舊資料, 其他卡片照常更新; 主 API 失敗時才整個 dashboard 顯示錯誤.

**Consequences**:
- ✅ Dashboard 對 secondary API 抖動有韌性, 不會因單一支失敗就整個變空白.
- ✅ Loading state 由主 API 控, 使用者看到的反應時間與「最關鍵資料」對齊, 不受 secondary 拖累.
- ✅ Secondary 失敗的 log 可供日後排查, 不靜默吞錯.
- ⚠️ Secondary 卡片可能顯示「-」, 使用者不易察覺是 API 失敗還是真實無資料; 若需精準分辨, 須額外加 per-card 錯誤顯示.
- ⚠️ Fire-and-forget 下若 secondary 回應極慢, 使用者已切走頁面後才回來, 可能寫入已被 dispose 的 reactive 欄位; 需確認 component unmount 後不再寫入 (一般 Vue reactive 系統會自動處理, 但須留意).

**Affected**:
- src/components/LayoutContentStaInfor.vue:732 (5 secondary API 空 catch 區塊)
- server/procStaInfor.mjs (各 stats summary 函式)
- spec/流程_後台統計資訊.md

## ADR-026: 未驗證帳號重寄機制採同欄位 overwrite (非獨立 token 表)

**Status**: Accepted (2026-06-08)

**Context**:
- 自助註冊建立 user 但 email 尚未驗證之階段, 驗證 token 須儲存於某處供後續驗證信點擊比對. 兩種選項: (a) 獨立 verification token 表, 每次重寄新增一筆; (b) 存於 `users.tokenVerify` 單一欄位, 重寄時 overwrite.
- (a) 可保留歷史 token、但須額外清理機制; (b) 簡潔、自然「最新一封信有效」.
- 不解決會踩到: 重寄機制過於複雜、歷史 token 累積、或舊驗證信仍有效造成混淆.

**Decision**:
- 採 (b): 驗證 token 存於 `users.tokenVerify` 欄位, 重寄時直接 overwrite 舊 token.
- 重寄後舊驗證信 link 自動失效 (token 已被覆寫, 後端比對不符).
- 驗證成功後同時更新 `users.timeVerified` (記錄驗證時間) 並清空 `tokenVerify` (此後無 active token 留存).

**Consequences**:
- ✅ 設計簡潔, 不需獨立 verification token 表 / 清理 timer.
- ✅ 重寄機制天然 idempotent — 不論寄幾次, 最新一封信有效, 不會有「兩封同時有效造成混淆」.
- ✅ 驗證後 `tokenVerify` 清空, audit 視角清楚 (該帳號當前無 pending verification).
- ⚠️ 使用者若點到舊信會看到「驗證失敗」, 須提示其改點最新信; 屬合理體驗.
- ⚠️ `tokenVerify` 與 `timeVerified` 兩欄位的狀態組合 (有 token + 無 timeVerified = 未驗證 / 無 token + 有 timeVerified = 已驗證 / 有 token + 有 timeVerified = 不應發生) 須在所有查詢點正確判讀.

**Affected**:
- server/procCore.mjs (createUser / resendVerifyEmail / verifyEmailByToken)
- users table schema (`tokenVerify`, `timeVerified` 欄位)
- spec/流程_使用者創建帳密.md
- spec/流程_使用者一般登入.md

## ADR-027: 登入成功後視圖分流 (`view` 參數優先級)

**Status**: Accepted (2026-06-08)

**Context**:
- 登入 / 自動登入成功後, 使用者該被導到哪個頁面? 三種可能: (a) 走 `redir` URL (外部 redirect 來源)、(b) 停留後台 (`view=backstage`)、(c) 停留使用者頁 (`view=user`).
- 三者觸發條件混亂時, 體驗會錯亂 (例如從外部 SSO 進來但被丟到使用者頁, 而不是 redirect 回原系統).
- 不解決會踩到: 登入後體驗錯位、外部 SSO 整合斷裂.

**Decision**:
- 採三分支分流, 由 URL `?view=` 參數驅動:
  - `view=login` (預設, 或從外部 redirect 進來) → 登入成功後走 `redir` 轉址回原系統.
  - `view=backstage` → 登入成功後停留後台.
  - `view=user` → 登入成功後停留使用者頁.
- `view` 參數於登入頁 URL 上由前端或外部 redirect 帶入; 預設 `view=login` (對齊外部 SSO 整合主場景).
- 此分流規則自動登入 (autoLogin) 同樣適用 — 已快取 token 進來時仍依 `view` 決定停留處.

**Consequences**:
- ✅ 三種使用場景 (外部 SSO / 直接後台 / 直接使用者頁) 皆有明確路徑.
- ✅ 與 ADR-001 multi-session 接受並存 — 各裝置可獨立指定 `view` 進入不同頁面.
- ✅ `view` 為 URL 顯式參數, 前後端皆可直接讀取, 不靠隱性狀態.
- ⚠️ 三分支須在 mUI.mjs / PageLogin.vue / PageUser.vue 共用判讀邏輯, 不可任一頁自行假設預設值. 屬契約共識.
- ⚠️ 未來若新增第四種視圖場景 (例如 `view=admin-only`), 須同時更新所有判讀點.

**Affected**:
- src/plugins/mUI.mjs (view 分流邏輯)
- src/components/PageLogin.vue
- src/components/PageUser.vue
- spec/流程_使用者一般登入.md
- spec/流程_使用者自動登入.md
- spec/流程_使用者變更密碼.md

## ADR-029: checkUserPassword 端點未認證 (F-005)

**Status**: Accepted (2026-06-08)

**Context**:
- server/WWebSso.mjs:1346 之 `kpfun.checkUserPassword` RPC 不呼叫 checkToken, 任何人皆可不認證地打.
- 用途: 純政策驗證 (密碼長度 / 字元種類 / blacklist / 不含帳號連續字), 回傳 success 或 i18n 錯誤訊息.
- 三條呼叫鏈合理需求未認證: (a) 註冊時 user 尚無 token; (b) 變更密碼時雖有 token 但此純驗證不需; (c) 後台 admin 新增 user.
- Audit F-005 質疑: 全域 IP rate limit (verifyConn) 是否足夠抵禦 wordlist enumeration 與政策反推?

**Decision**:
- 採接受並文件化, 不加額外 per-token / per-IP-per-endpoint rate limit.
- 理由:
  1. **密碼政策不是 secret**: 業界普遍認為密碼政策本就不應視為敏感資訊 (多數網站註冊頁本就明列「至少 N 字 / 含大小寫 / ...」). 本系統 PageLogin.vue 註冊模式已採「reactive 提示」(使用者輸入後 i18n inline 紅字顯示具體規則), 攻擊者隨便打幾個字即得完整政策內容, 此 endpoint 並未額外洩露更多.
  2. **真實 brute force 已被 autoblock 擋住**: 同帳號 5 次失敗即鎖, wordlist 預篩之後的真實打點仍會被攔截.
  3. **此 endpoint 不洩露帳號存在性**: WWebSso.mjs:1349 handler 只傳 (lang, pw), opt.account 為空, noConsecutiveCharsFromAccount 政策對 account 之比對不會回傳「此 account 存在」的訊號.
  4. **加 rate limit 的工程成本中, 收益低**: botnet 散到多 IP 可繞過 per-IP 限流; per-token 限流保護不到註冊路徑 (註冊無 token).

**Consequences**:
- ✅ 不引入 per-IP-per-endpoint counter 之新 in-memory state 複雜度.
- ✅ 註冊與變更密碼之 inline 即時驗證 UX 保留.
- ✅ autoblock 仍守住真實帳號 brute force 攻擊面.
- ⚠️ 攻擊者可慢速 wordlist 預篩通過政策的候選, 但實際打 loginByAccountAndPassword 仍被 autoblock 攔, 無實質帳號接管風險.
- ⚠️ 攻擊者可探出政策參數 (minLength / 字元要求 / blacklist 範圍), 但此資訊本就視為公開 (註冊頁 reactive 提示已暴露相同資訊).
- ⚠️ PageUser.vue 變更密碼模式目前無 client-side 政策提示 (僅 server reject 後 inline 紅字), 與註冊頁體驗不一致. 屬可改善之 UX 議題, 但不影響本 ADR 安全結論 (政策不論顯式或反應式皆為公開資訊).

**Affected**:
- server/WWebSso.mjs:1346 (RPC handler)
- server/procCore.mjs:900 (checkUserPassword 純函式)
- src/components/PageLogin.vue 註冊模式 (reactive 政策提示 line 105-109 + computed regPasswordErrors line 519-549)
- src/components/PageUser.vue 變更密碼模式 (現無 client-side 政策提示, 僅 server reject 後 chPwNewError inline 紅字)
- 對齊 ADR-013 autoblock 帳號鎖定 (真實 brute force 防線)

## ADR-031: P1 待裁示 — Admin reset password race (F-054)

- 暫定 Pending, 待業主決議.

**Consequences (若選 c, 接受)**:
- ✅ 不增工程複雜度.
- ⚠️ Audit 文件須明示此 trade-off, 兩 admin 並發重設同 user 時最終密碼為「最後寫入者勝」.

- ✅ 完全避免 race.
- ⚠️ 工程成本中高, 須處理 lock / 版本欄位之 schema 變動.

## ADR-032: verifyEmail 採 lazy clear, 不主動清 tokenVerify (F-053 race 修補)

**Status**: Accepted (2026-06-08)

**Context**:
- verifyEmail 與 resendVerifyEmail 並發時存在 read-check-save race: verifyEmail 讀 user 後 resendVerifyEmail 寫新 tokenVerify, verifyEmail 再寫 tokenVerify='' 把新 token 覆蓋, 導致使用者收到新驗證信但點下去顯示 'verifyEmailInvalidToken'.
- Audit F-053 揭露此 race, 機率極低 (需 1ms 內並發兩動作) 但體驗具體不良 (使用者剛收信點下去就無效, 困惑).
- 修法選項: (a) DB UNIQUE on tokenVerify 不可行 (空字串多 user 都有), (b) optimistic lock 仍有窄 race window + 複雜, (c) lazy clear (不清 tokenVerify) 一行解.

**Decision**:
- verifyEmail 成功路徑只設 timeVerified=now, **不主動清空 tokenVerify**.
- 已驗證 user 之 tokenVerify 仍保留舊值 (或被 resendVerifyEmail 後續覆寫為新值), 由 verifyEmail 入口之 `if (isestr(timeVerified)) reject 'verifyEmailAlreadyVerified'` 攔截 token 重用嘗試.

**Consequences**:
- ✅ 一行修補消除 race window (拿掉 tokenVerify: '').
- ✅ 不引入 lock / optimistic concurrency / DB constraint 複雜度.
- ✅ resendVerifyEmail 並發場景: 新 token 不被覆蓋, 使用者點新連結仍能驗證 (或得友善訊息).
- ⚠️ 已驗證 user 之 DB 紀錄 tokenVerify 欄位可能留有舊字串 (非空), 屬無害雜訊; 資料庫稽核 view 須理解此設計 (空字串 ≠ 已驗證, 須看 timeVerified).
- ⚠️ 若日後追加 「tokenVerify 為 admin 解密查詢條件」之功能, 須避開 verifyEmail 後 tokenVerify 仍非空之假設.

**Affected**:
- server/procCore.mjs (verifyEmail 函式體 — 拿掉 tokenVerify: '')
- spec/流程_使用者創建帳密.md (驗證信段更新)

## ADR-033: 按鈕雙擊防護分層

**Status**: Accepted (2026-06-08)

**Context**:
- 使用者快速雙擊提交按鈕可造成重複 API 呼叫: 重複插入資料 (createUser TOCTOU) / 重複寄信 (resendVerify) / 重複密碼變更 + 兩封信 (adminResetUserPassword 最嚴重).
- 全專案 36 個 WButtonCircle 用 0 次 promiseUnlock, 防護完全依賴 §5.1 canonical `updateLoading` 全頁 overlay, 在「sync 檢測 → overlay 開啟」之間有空窗; 對 modal-before-loading 之 case (adminResetUserPassword 點 Reset → showCheckYesNo → 點 Yes 才開 overlay) 空窗變更長.

**Decision**:
採三層防護, 每層獨立但互補:
1. **元件層 (frontend)**: 有副作用的提交按鈕用 WButtonCircle / WButtonChip 之 `:promiseUnlock="true"`, 第一次 click 立即上鎖 `loadingTrans=true`, caller 解 pm.resolve/reject 才解鎖. 比 `updateLoading` 早一層, sync 檢測都過不了第二次.
2. **頁面層 (frontend)**: `updateLoading(true)` 全頁 overlay 保留, 防 async API 期間的全頁互動. §5.1 canonical 不變.
3. **後端層 (backend)**: critical 路徑 (createUser / adminResetUserPassword / changeUserPassword / resendVerifyEmail) 用 `server/procMutex.mjs` 包 per-key in-process mutex, 防 API 直打 / e2e race / 自動化攻擊繞過前端.

**Consequences**:
- ✅ 防使用者快速雙擊造成的資料污染 (DC-01 / DC-02 critical 議題收掉).
- ✅ 防 API 直打繞過前端: 後端 mutex 是最後一道防線.
- ✅ 不依賴單一防線 (defense-in-depth), 即使 frontend overlay 失效, backend mutex 仍守.
- ⚠️ procMutex 為 in-process only; cluster 多 process 部署下不互斥. 對齊 ADR-030 Pending 部署拓樸假設 (目前單機).
- ⚠️ 加 mutex 後第 2 次並行請求會 reject 'operation in progress', 前端須處理該 reject (顯示 inline 紅字 / 忽略).
- ⚠️ promiseUnlock 改動會影響既有 e2e baseline (button 渲染含 loading icon 時可能 byte 不同), 須對應重產 baseline.

**Affected**:
- server/procMutex.mjs (新建)
- server/procCore.mjs (createUser / adminResetUserPassword / changeUserPassword / resendVerifyEmail 4 處包 withLock)
- src/components/PageLogin.vue (register / resendVerify 按鈕加 promiseUnlock)
