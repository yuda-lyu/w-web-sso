# 後台統計資訊流程

## 觸發

管理員登入後台後，左側導覽預設停在「Statistics information」（後台統計資訊頁，`LayoutContentStaInfor.vue`）。此頁聚合呈現使用者 / 金鑰 / IP 三大面向之計數卡片、頻率圖表（登入 / 金鑰 / IP）與管控狀態卡片，提供管理員一頁綜覽系統運行狀況。

後端 `getStaUserSummary` / `getStaTokenSummary` / `getStaIpSummary` / `getStaUserAccountLogin` / `getStaToken` / `getStaIp` 共 6 個 RPC 皆以 `funCheckAdmin` 包裝（`server/WWebSso.mjs:1412,1419,1426,1433,1440,1448`），**僅具 admin 權限的有效 token 可存取**；token 無效／過期／非 admin 一律 reject。

## 重要流程

- **E2E-001**
  - title: 管理員進入統計資訊頁顯示初始檢視態
  - description: 驗證管理員以有效 admin token 登入後台後進入「Statistics information」頁，前端 mounted 階段呼叫 `getAndRelaData` 並行呼叫 6 個 `getSta*` API，後端各自回傳統計結果，前端依序綁定至使用者區（total/active/locked/expired）、管控區（active/created24h/ending24h/ended/conn24h/blocked）卡片與三個頻率圖表（freqLogin/freqToken/freqIp）。本案例為此流程之入口檢視，後續失敗案例皆以此為對照基準。屬正常成功路徑案例。
  - flow:
    - 測試資料：admin user（帳號 `stainfor-admin` / 密碼 `Pw@stainfor1` / `isActive='y'` / `isAdmin='y'` / `timeVerified` 有值 / `redir` 帶 `?view=backstage&token={token}`）+ 有效 admin token（timeEnd 為 60 分鐘後）+ base seed（3 users + 4 tokens + 0 ips）。
    - 操作：開乾淨登入頁（localStorage 無 token）→ 輸入帳號與密碼 → 點「Log in」/「登入」按鈕 → 跳 backstage 預設停在 Statistics 頁 → 等所有 `getSta*` API 回完。
    - 驗證：
      1. 語意（DOM 文字）：頁面含「Statistics information」/「統計資訊」標題 + 使用者資訊區「Total Users」/「總使用者」標籤 + 管控狀態區「Active tokens」/「有效金鑰數量」標籤。
      2. 視覺：與 baseline `test/pics/stainfor/stainfor-{eng,cht}-E2E-001-page-loaded.png` byte-equal。
    - 雙語：eng / cht 各一輪。
    - 清理：移除本檔特化 user 與 admin token，保留 base seed。

- **E2E-002**（暫緩，待 production 修復後加入）
  - title: 管理員 token 失效時頁面 cards 顯示 0
  - description: 設計上此案例驗證「token 失效時 cards 數值應為 0」，但實作端 `getStaUserSummary` / `getStaTokenSummary` / `getStaIpSummary` 3 個 endpoint **未呼叫 `checkToken`**（詳見下節「已知 production gap」），故 token 失效不會影響 cards 數值，本案例目前無法成立。待 production 修補後再加入此案例與對應 baseline。

## 執行流程

```
001  使用者開 Statistics 頁, 觸發 mounted hook  [LayoutContentStaInfor.vue:387]
002      呼叫 getAndRelaData()  [LayoutContentStaInfor.vue:393]
003          設 isLoading=true, errMsg=''  [LayoutContentStaInfor.vue:721-722]
004          並行呼叫 6 個 getSta* API  [LayoutContentStaInfor.vue:723-744]
005              grStaUserSummary()  [LayoutContentStaInfor.vue:608]
006                  fapi.getStaUserSummary(token)  [LayoutContentStaInfor.vue:615]
007                      checkToken(token, {fun: funCheckAdmin})  [procStaInfor.mjs]
008                          token 無效 / 過期 / 非 admin:
009                              reject  → outer catch
010                      回傳 {total, active, locked, expired}
011                  .then 設 userOverview = res  [LayoutContentStaInfor.vue:617]
012                  .catch 寫 console.log  [LayoutContentStaInfor.vue:619]
013              outer catch (僅 grStaUserSummary):
014                  errMsg = $t('getDataError')  [LayoutContentStaInfor.vue:726]
015              outer finally:
016                  isLoading = false  [LayoutContentStaInfor.vue:729]
017              grStaTokenSummary() / grStaIpSummary() / grStaUserAccountLogin() / grStaToken() / grStaIp()  [LayoutContentStaInfor.vue:732-744]
018                  各自 .then 綁定對應 reactive 變數 (tokenStatus / ipCharacteristic / freqLogin / freqToken / freqIp)
019                  各自 .catch 僅 console.log (不影響 isLoading / errMsg)
020      template render
021          v-if="!isLoading" → 主內容 (卡片 + 圖表 + 表格)
022          v-else (= isLoading=true 時):
023              v-if="isLoading" → 顯示「等待數據中...」 (waitingData)
024              v-if="errMsg" → 顯示 errMsg (註: 因 finally 必設 isLoading=false, 此分支實際無法觸發, 屬死碼)
```

## 參數來源

| 概念 | 來源 | 流程影響 |
|---|---|---|
| 操作者 token | 前端 store（登入後 admin token） | 後端以 `funCheckAdmin` 驗證；失效則所有 `getSta*` reject，前端 reactive 變數維持初始空值 |
| 統計時間範圍 | 後端 `procStaInfor` 內部固定（最近 7 天 + 各時間粒度 1hr/4hr/8hr/1day） | 與請求時間相對；本檔之 seed `timeCreate` 設為 2025-01-01（>1 年前），三個頻率圖表均落在 7 天視窗外 → 圖表渲染空資料 |

## spec 規則摘要

- **權限**：6 個 `getSta*` 皆 admin-only（`funCheckAdmin`）。
- **粒度**：本頁為純顯示（無修改 / 刪除 / 儲存）。不會觸發 `showCheckYes` modal 或 `$alert` toast。
- **邊界**：頁面交互元素（時間粒度選擇 / 個別顯示 checkbox / 顯示全部連結）僅影響前端圖表渲染樣式，不會重新呼叫後端 API；故本流程不涵蓋此類 UI 互動之 e2e。
- **契約**：mount 時並行呼叫 6 個 `getSta*`；`grStaUserSummary` 的 promise 之 finally 設 `isLoading=false`；其他 5 個各自 catch 僅 console.log。
- **死碼揭露**：模板 `v-else` 內的 `errMsg` 區塊因 `isLoading` 必於 finally 被設為 `false`，實際 UI 無法看到錯誤文字；本案例不依賴此死碼，視為 production 已知設計取捨，文件化於本 spec 而非作為 bug 修正。
- **截圖範圍取捨**：E2E-001 的 byte-equal baseline 僅截上方 cards 區（y:0..330），刻意排除下方三個頻率圖表。理由：圖表呈現「最近 7 天」資料且依登入活動 bucket 化（1hr 預設粒度），spike 位置會隨測試執行的小時 bucket 變動，跨時間 byte-equal 不穩；而 cards 區（Total Users / Active Users / Blocked Users / Expired Users）僅依賴 DB seed 計數（與 wall-clock 無關），可確定性穩定。圖表本身之渲染正確性屬於 ECharts 套件邊界，不適合用 pixel byte-equal 守護，本流程不涵蓋。

## 已知 production gap（待修補）

於撰寫本 spec 時發現：

- `server/procStaInfor.mjs` 內 `getStaUserSummary` / `getStaTokenSummary` / `getStaIpSummary` 3 個函式（line 47 / 95 / 151）**未接 token 參數、未呼叫 `checkToken`**，僅直接讀 `getUsersListCache` / `getTokensListCache` / `getIpsListCache` 並回傳統計。
- `server/WWebSso.mjs` line 1415 / 1422 / 1429 雖以 `pf.getStaUserSummary(token, { fun: funCheckAdmin })` 形式包裝，但實作 `async () => { ... }` 忽略所有傳入參數 → token 驗證實際被繞過。
- **影響**：任何能呼叫此 3 個 RPC 的請求（無論 token 有效與否、是否為 admin）都可取得後台使用者 / Token / IP 之統計總數，屬「敏感資料外洩」級別之安全議題。
- **與本 spec 之關聯**：因此 E2E-002（token 失效時 cards 應顯示 0）目前無法成立——cards 數值與 token 是否有效無關，已於上方 E2E-002 條目暫緩。
- **建議修補方向**：`procStaInfor.mjs` 內 3 個 Summary 函式改為 `async (token, opt) => { await p.checkToken(token, opt); ... }`（與下方 6 個 `checkTokenAndGet*` 同款驗證機制），修補後即可加入 E2E-002 並產 baseline。
- 上述屬 production code 議題，**非本次 spec/e2e 任務 scope，待後續另行處理**。
