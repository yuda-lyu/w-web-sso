# 查詢使用者資訊流程

## 觸發

外部 SSO sub-app 透過 HTTP `GET /api/getSsoUserInfor` 查詢某使用者之 profile，為跨應用整合之對外入口。caller 帶入操作者 token 與目標查詢條件（key / value），後端依 key 是否為 `'token'` 分流至 `p.checkTokenAndGetUserByToken`（以 token 字串為 value 反查使用者）或 `p.checkTokenAndGetUserInfor`（以指定欄位查使用者）；兩條分支皆以 `funCheckAdmin` 包裝（`server/WWebSso.mjs:952,939`），**僅具 admin 權限之有效操作者 token 或 `isApp='y'` 之應用系統 token 可存取**；token 無效／過期／非 admin 一律 reject。

內部另提供 `kpfun.getUserByToken` 與 `kpfun.getUserInfor` 兩支 RPC（`server/WWebSso.mjs:1186,1180`）：
- `kpfun.getUserByToken(token)`：給前端 / w-ui-loginout 自查自身 token 對應之使用者用，後端以 `p.checkTokenAndGetUserByToken(token, token)` 實作（`server/WWebSso.mjs:1190`），**僅驗證 token 有效（未過期、可解），不限制是否為 admin**。此 RPC 亦為前端「使用者資訊」頁（`src/components/LayoutContentUserInfor.vue:306` 於 mounted 呼叫 `$fapi.getUserByToken(token)`）渲染登入者自身 profile 之資料來源。
- `kpfun.getUserInfor(token, key, value)`：HTTP `/api/getSsoUserInfor` 之 RPC 對稱版本，後端以 `funCheckAdmin` 包裝（`server/WWebSso.mjs:1201`），僅 admin 操作者 token 或 app token 可存取。

## 重要流程

- **E2E-001**
  - title: admin 操作者 token 經 HTTP 查他人成功取得對方 profile
  - description: 驗證 admin 操作者持有效 admin token，以 `key=token` / `value=<target user 之 token 字串>` 呼叫 HTTP `GET /api/getSsoUserInfor` 時，後端 `funCheckAdmin` 通過、`checkTokenAndGetUserByToken` 以 target token 反查使用者並回傳完整 profile（含 id / account / name / email / isAdmin / timeVerified / timeExpired / timeBlocked / isActive 等欄位）。本案例為查詢使用者資訊流程之 golden path，亦為其餘失敗情境（非 admin 操作者、token 失效）之對照基準。
  - flow:
    - 測試資料：admin 操作者 user `id-getuserinfor-admin`（帳號 `getuserinfor-admin` / `isAdmin='y'` / `isActive='y'` / `timeVerified` 有值）+ 對應有效未過期 admin token；target user `id-getuserinfor-user-b`（帳號 `getuserinfor-user-b` / `isAdmin='n'` / `isActive='y'` / `timeVerified` 有值）+ 對應有效未過期 token。
    - 操作：對後端 `GET /api/getSsoUserInfor` 發送 HTTP 請求，query 帶 `token=<admin 操作者 token>` / `key=token` / `value=<target user 之 token 字串>`。
    - 驗證（等待後端回應後）:
      1. HTTP status：200。
      2. 回傳 body：`state === 'success'`，`msg` 為物件且 `msg.id === 'id-getuserinfor-user-b'`、`msg.account === 'getuserinfor-user-b'`、`msg.isAdmin === 'n'`、`msg.isActive === 'y'`。
    - 雙語：不適用（API-only，無 UI 文字渲染）。
    - 清理：移除本檔特化 user 與 token，保留 base seed。

- **E2E-002**
  - title: 非 admin 操作者 token 經 HTTP 查他人遭拒
  - description: 驗證一般（非 admin）操作者持有效但 `isAdmin='n'` 之 token 呼叫 HTTP `GET /api/getSsoUserInfor` 查他人時，後端 `funCheckAdmin` 判定為 false、`checkTokenAndGetUserByToken` 之 `_checkTokenByObj` 內部 `b2=false` 致 `checkToken` reject `'tokenExpired'`，handler 內 `await` 上拋至 `pm2resolve` 外層、body `state='error'`、`msg='tokenExpired'`。本案例為權限邊界守門驗證點：操作者 token 本身有效（未過期、簽章正確），但不具 admin 權限即不得查他人，亦為 §spec 規則摘要「endpoint 僅接受 admin user 或 app token」契約之最小反向驗證。reject 訊息與「token 已過期」相同（'tokenExpired'）為刻意設計——避免 caller 由訊息差異推論「token 本身狀態 vs 角色不足」之區別。
  - flow:
    - 測試資料：一般操作者 user `id-getuserinfor-user-a`（帳號 `getuserinfor-user-a` / `isAdmin='n'` / `isActive='y'` / `timeVerified` 有值）+ 對應有效未過期 token；target user `id-getuserinfor-user-b`（任意一個非自身之 user 即可）+ 對應有效未過期 token。
    - 操作：對後端 `GET /api/getSsoUserInfor` 發送 HTTP 請求，query 帶 `token=<一般操作者 token>` / `key=token` / `value=<target user 之 token 字串>`。
    - 驗證（等待後端回應後）:
      1. HTTP status：200（後端以 `pm2resolve` 包裝，reject 於 body 而非 HTTP 狀態碼）。
      2. 回傳 body：`state === 'error'`，`msg` 為 i18n key `'tokenExpired'`（caller funCheckAdmin 失敗於 `_checkTokenByObj` 之 b2=false 路徑，由 `checkToken` 統一收斂為 key `'tokenExpired'`，與 token 真實過期同訊息以防 information leakage）。
    - 雙語：不適用（API-only，無 UI 文字渲染）。
    - 清理：移除本檔特化 user 與 token，保留 base seed。

- **E2E-003**
  - title: 無效或過期 token 呼叫 HTTP 遭拒
  - description: 驗證操作者持「DB 不存在」（無效）或「`timeEnd` 已過」（過期）之 token 呼叫 HTTP `GET /api/getSsoUserInfor` 時，後端 `checkToken` 內部 `_checkToken` 於 `woItems.tokens.select` 找不到對應紀錄即 reject `'invalid token'`（內層字串），但外層 `checkToken` 之 `.catch` 將此內層 reject 統一覆寫為 i18n key `'tokenExpired'`（防 information leakage，使「查無 token」與「token 過期」對外無法區分）；handler 之 `await` 上拋至 `pm2resolve` 外層、body `state='error'`、`msg` 為 i18n key `'tokenExpired'`。本案例與 E2E-002 同屬 reject 路徑，但攔截點位於更前段（token 本身就無法解），用以驗證 `funCheckAdmin` 觸發前已先過 token 有效性閘門。
  - flow:
    - 測試資料：不建立操作者 user / token；操作者 token 直接帶入一段任意字串（保證 DB 無此紀錄）；target token 同樣帶入任意字串（不影響本案例之 reject 點）。
    - 操作：對後端 `GET /api/getSsoUserInfor` 發送 HTTP 請求，query 帶 `token=<DB 不存在之任意字串>` / `key=token` / `value=<任意字串>`。
    - 驗證（等待後端回應後）:
      1. HTTP status：200（後端以 `pm2resolve` 包裝，reject 於 body 而非 HTTP 狀態碼）。
      2. 回傳 body：`state === 'error'`，`msg` 為 i18n key `'tokenExpired'`（`_checkToken` 於 `woItems.tokens.select` 找不到紀錄即 reject 內層字串 `'invalid token'`，外層 `checkToken` 之 `.catch` 統一覆寫為 `'tokenExpired'` 對外回應，與 token 真實過期同訊息以防 information leakage）。
    - 雙語：不適用（API-only，無 UI 文字渲染）。
    - 清理：本案例未建立任何 user 或 token，無資料殘留須清除；保留 base seed。

## i18n 訊息粒度規則

本流程之 reject 訊息為 **後端 i18n key**（`tokenExpired` / `tokenNoPermission`，已建於 `procLang.mjs:812,817`，eng/cht 齊備），由 HTTP body 直接傳回給 caller（SSO sub-app）；此 endpoint 為 server-to-server REST，回 machine-readable key 供 API caller 自行判斷或查表翻譯。`_checkToken` / `getUserByToken` 內部之 `invalid token` / `duplicate tokens` / `invalid timeEnd` 為原始字串，但皆於外層 `checkToken` 之 `.catch` 統一覆寫為 key `tokenExpired`，caller 永遠看不到這些內部字串（防 information leakage）。

| 觸發情境 | caller 實際收到 (key) | 收斂位置 | 規則 |
|---|---|---|---|
| 操作者 token 在 DB 找不到 | `tokenExpired` | `procCore.mjs:563-569`（`_checkToken` 內 `woItems.tokens.select` 無紀錄 reject `invalid token`，被 `checkToken` 之 `.catch` 覆寫） | 攔截於 `funCheckAdmin` 觸發前，token 本身就無法解；對外與過期同訊息 |
| 操作者 token 在 DB 找到多筆 | `tokenExpired` | `procCore.mjs:563-569`（內層 reject `duplicate tokens`，被 `.catch` 覆寫） | 同上，屬資料異常，對外不洩露 |
| 操作者 token `timeEnd` 已過 | `tokenExpired` | `procCore.mjs:560`（`_checkTokenByObj` 回 b1=false → `checkToken` `.then` 設 errTemp） | 攔截於 `funCheckAdmin` 觸發前，過期 token 一律拒絕 |
| 操作者 token 有效但非 admin | `tokenExpired` | `procCore.mjs:560`（`_checkTokenByObj` 之 b2=false → `checkToken` `.then` 設 errTemp） | `funCheckAdmin` 回 false 致 b2=false，與「token 真實過期」同訊息統一收斂，防 caller 由訊息差異推論狀態（資訊外洩防禦） |
| 操作者 token 有效但 target token / key-value 查無對應 user | `tokenNoPermission` | `WWebSso.mjs:965`（handler 內 `iseobj(userTarget)` 檢核失敗分支 reject 此 key） | caller 通過 `funCheckAdmin` 但 target 不存在時，handler 外層以「無權限」回應，不洩露「查無此 user」之資料存在性 |

實際對外 reject 值為 i18n key（`procLang.mjs:812,817` 已建 eng/cht）；caller 端依需要查表翻譯。

## 參數來源

| 概念 | 來源 | 流程影響 |
|---|---|---|
| 操作者 token | HTTP `query.token` | 後端以 `funCheckAdmin` 驗證；失效則 reject |
| 查詢 key | HTTP `query.key`（如 `'token'` / `'account'` / `'email'` / `'id'`） | `'token'` 走 `checkTokenAndGetUserByToken`，其餘走 `checkTokenAndGetUserInfor` |
| 查詢 value | HTTP `query.value`（依 key 對應） | 反查 target user 之鍵值 |
| 後端 admin 守門 | handler 內固定帶 `{fun: funCheckAdmin}` | endpoint 永遠以 admin 守門，caller 無法略過 |

## spec 規則摘要

- **權限**：HTTP `/api/getSsoUserInfor` endpoint **僅接受 admin user 或 app token 之 caller**，透過雙重保險落實：
  1. handler 兩條分支皆固定帶 `{fun: funCheckAdmin}`（`WWebSso.mjs:952,939`）。
  2. `procCore.mjs:439` 之 `_checkTokenByObj` 對 `isApp === 'y'` 之 token 略過 `fun` 驗證，使應用系統 token 可直接通行（系統間整合用，視同管理者）；對 `isApp !== 'y'` 之使用者 token 則強制執行 `funCheckAdmin`。
- **粒度**：reject 訊息為後端 i18n key（`procLang.mjs:812,817` 已建 eng/cht）。caller 之 token 任何認證失敗（過期 / 非 admin / DB 找不到 / 多筆）皆於 `checkToken`（`procCore.mjs:557-569`）統一收斂為 key `'tokenExpired'`（防 information leakage：不讓 caller 由訊息差異區分 token 狀態 vs 角色不足）；僅當 caller 通過認證但 target 查無對應 user 時，handler 外層才以 key `'tokenNoPermission'`（`WWebSso.mjs:965`）回應。
- **邊界**：
  - 「使用者查自己」走 RPC `kpfun.getUserByToken(token)`（`WWebSso.mjs:1186`，後端以 `checkTokenAndGetUserByToken(token, token)` 實作，**不帶 `fun` opt**），與 HTTP endpoint 不同 path；該 RPC 僅驗證 token 有效（未過期、可解），不限制是否為 admin，供前端「使用者資訊」頁（`LayoutContentUserInfor.vue:306`）/ w-ui-loginout 自查自身使用。
  - `key === 'token'` 時以 target token 反查使用者；`key !== 'token'` 時以指定欄位查使用者，查無回 null（handler 外層轉為 key `'tokenNoPermission'`）。
  - 回傳之 user 物件為白名單欄位（`procCore.mjs:1584-1599` / `procCore.mjs:1636-1649`），不含 `password` 等敏感欄位。
- **契約**：
  - HTTP body 結構固定為 `{state, msg}`：`state='success'` 時 `msg` 為 user 物件；`state='error'` 時 `msg` 為錯誤 i18n key（`tokenExpired` / `tokenNoPermission`）。
  - reject 路徑於 `pm2resolve` 統一收斂，HTTP status 一律為 200，狀態以 body `state` 區分。
  - app token（`isApp='y'`）於 `_checkTokenByObj` 與 `getUserByToken` 兩處皆走 bypass 分支，視同 admin；其虛擬 user 物件之 `isAdmin='y'` / `isActive='y'` 為固定值。

## 已知 production gap

- **`kpfun.getUserInfor`（RPC 對稱版本）目前 frontend 無 caller**：`WWebSso.mjs:1195` 已對稱 HTTP endpoint 帶上 `{fun: funCheckAdmin}` opt（`WWebSso.mjs:1201`），防 future 誤用（後續若有 frontend / 內部模組接入此 RPC，admin 守門即生效，不會出現「HTTP 有守門、RPC 無守門」之權限破口）。本流程之 e2e 不涵蓋此 RPC（無 caller 即無觀察點），紀錄於此供日後接入時對齊驗證範圍。
- **`kpfun.getUserByToken` 不帶 `funCheckAdmin`**：此為設計取捨而非 gap，用途為使用者查自身（`token` 與 `tokenTarget` 同一字串，`WWebSso.mjs:1186`），不應要求自身為 admin 才能查自身 profile。前端「使用者資訊」頁（`LayoutContentUserInfor.vue:306`）即走此 RPC 渲染登入者自身 profile（顯示 name / account / email / 封鎖 / 過期 / 驗證 / 有效 / 身份等欄位，雙語且支援 RWD）。若日後此 RPC 被誤用於「以一個 token 查另一個 token」場景，須補上 admin 守門或開新 RPC，不可沿用本支。
