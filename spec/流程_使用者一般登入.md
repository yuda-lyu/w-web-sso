# 使用者一般登入流程

## 觸發

使用者在 PageLogin.vue 輸入帳號密碼，點擊「Log in」按鈕。

## 重要流程

- **E2E-001**
  - title: 使用者輸入帳密成功登入
  - description: 驗證在帳號啟用、密碼正確、email 已驗證、帳號未過期、未被暫時封鎖之所有前置條件皆滿足時，使用者於登入頁輸入正確帳號與密碼並點擊「Log in」按鈕後，能成功通過後端 protect 層與核心層的逐項驗證、取得後端建立之有效 token、由前端寫入 localStorage，並依使用者資料中之 redir 欄位轉址至指定功能頁（本案例為 user view）。此案例為登入流程之 golden path，亦為其餘失敗情境（密碼錯誤 / 帳號不存在 / 帳號未驗證 / 帳號停用 / 帳號過期 / 帳號封鎖等）之對照基準。
  - flow:
    - 測試資料：user `id-login-ok`（帳號 `login-ok` / 密碼 `Pw@login1` / `isActive='y'` / `timeVerified` 有值 / `timeExpired` 未來 / `timeBlocked` 空 / `redir` 帶 `?view=user&token={token}`）。
    - 操作：開乾淨登入頁（localStorage 無 token） → 輸入帳號與密碼 → 點「Log in」/「登入」按鈕。
    - 驗證（等待 redirect 完成後）：
      1. 語意：DOM 上不再出現「Log in」/「登入」按鈕（已離開登入頁）。
      2. 視覺：與 baseline `test/pics/login/login-{eng,cht}-E2E-001-ok.png` 視覺一致（pixelmatch 容差）。
    - 雙語：eng / cht 各一輪。
    - 清理：移除本檔特化 user，保留 base seed。

- **E2E-002**
  - title: 使用者輸入帳密失敗，密碼錯誤
  - description: 驗證使用者於登入頁輸入存在且啟用之帳號，但密碼與後端儲存之雜湊不符時，後端核心層比對失敗、回傳統一錯誤訊息「使用者帳密錯誤無法登入 / User account or password is incorrect」，且前端 PageLogin 留在登入頁、以紅字 inline 形式呈現該訊息，使用者未取得任何 token、亦未轉址至任何功能頁。本案例之錯誤訊息為防帳號列舉設計之共用訊息，與 E2E-008（帳號停用）、E2E-015（帳號不存在）完全相同，避免攻擊者由訊息差異推斷帳號是否存在；E2E-008 並進一步與本案例共用同一張 baseline。
  - flow:
    - 測試資料：user `id-login-wrong-pw`（帳號 `login-wrongpw` / 後端儲存密碼雜湊對應 `Pw@login2` / `isActive='y'` / `timeVerified` 有值 / `timeExpired` 未來 / `timeBlocked` 空 / `redir` 帶 `?view=user&token={token}`），實際送出之密碼為 `Pw@wrong99`（與後端不符）。
    - 操作：開乾淨登入頁（localStorage 無 token） → 輸入帳號與錯誤密碼 → 點「Log in」/「登入」按鈕。
    - 驗證（等待後端回應與錯誤訊息渲染後）:
      1. 語意：頁面可見文字含「User account or password is incorrect」/「使用者帳密錯誤無法登入」（與 E2E-008 / E2E-015 共用同一條訊息，防帳號列舉）。
      2. 視覺：與 baseline `test/pics/login/login-{eng,cht}-E2E-002-wrong-pw.png` 視覺一致（pixelmatch 容差）。
    - 雙語：eng / cht 各一輪。
    - 清理：移除本檔特化 user，保留 base seed。

  - description: 承接 E2E-004 之重寄表單展開狀態，驗證使用者於表單填入與該帳號相符之 email 並送出後，後端應成功寄送驗證信，且前端以 CheckYes 彈窗顯示「Verification email has been resent」/「驗證信已重新寄出」之成功訊息。此案例為「未驗證完整流程」五段截圖點之第 3 段，截圖點為彈窗開啟後之穩定態；後續流程於關閉彈窗後繼續，並於 Step 4 由 AgentMail API 收信取得驗證連結（不另截圖）。

## i18n 訊息粒度規則

後端依序檢查 (1) 帳號封鎖 → (2) 帳號存在 → (3) 帳號啟用 → (4) 密碼正確 → (5) email 已驗證 → (6) 帳號未過期 → (7) token 建立。檢查順序屬 spec，不得隨意調動 (重排會洩露帳號存在性)。

前端依後端 reject 字串對映至 i18n 鍵後顯示對應語系翻譯，**錯誤字串本身不直接顯示給使用者**。

| 觸發情境 | i18n 鍵區位 (grep 提示) | 顯示位置 | 粒度規則 (spec) |
|---|---|---|---|
| 帳號不存在 | `server/procLang.mjs` 找 `failedLoginForCatch` 等通用登入失敗鍵 | PageLogin 錯誤訊息區 | **與「密碼錯誤」共用同一條訊息，禁止洩露帳號是否存在 (防帳號列舉)** |
| 密碼錯誤 | 同上 | 同上 | 同上 |
| 帳號已停用 (isActive !== 'y') | 同上 | 同上 | **與「帳號不存在」共用同一條訊息**：procProtect 階段以 `can not find the user by account` reject，前端視同帳號不存在 (防帳號列舉) |
| 帳號被封鎖 (timeBlocked > now) | `server/procLang.mjs` 找 `failedLoginForCatch` | PageLogin 錯誤訊息區 | **與「密碼錯誤 / 帳號不存在 / 帳號已停用」共用同一條訊息**：procProtect 階段以 generic key `failedLoginForCatch` reject，不洩露帳號是否被封鎖或存在 (防帳號列舉) |
| 帳號未驗證 (無 timeVerified) | `server/procLang.mjs` 找 `userRegistrationNotVerified` 等註冊未驗證系列鍵 | PageLogin 錯誤訊息區 + 重寄驗證信連結 | 顯示尚未驗證的固定訊息，並提供重寄驗證信入口 |
| 帳號已過期 (timeExpired < now) | `server/procLang.mjs` 找 `loginAccountExpired` | PageLogin 錯誤訊息區 | 顯示帳號已過期的固定訊息 |
| 重寄驗證信時 email 不符 | `server/procLang.mjs` 找重寄驗證信錯誤系列鍵 (`userRegistration*` 前綴) | PageLogin 重寄驗證信錯誤訊息區 | 訊息可明確指出 email 不符（此時使用者已通過帳密前置條件，不再有列舉風險）；**但帳號不存在與 email 不符共用同一 key `userRegistrationResendInvalidEmail`**（帳號不存在仍偽裝成 email 不符，比一般 email 不符更保守，防列舉依然存在） |
| 重寄驗證信但已驗證 | 同上 | 同上 | 訊息可明確指出已驗證 |
| 登入成功但 redir 為空 (view=login 場景) | `server/procLang.mjs` 找 `failedLoginForNoRedir` | PageLogin 錯誤訊息區 | 顯示無有效轉址的固定訊息 |
| 未預期錯誤 (catch 內無對應分支) | `server/procLang.mjs` 找 `failedLoginForCatch` | PageLogin 錯誤訊息區 | console.log 原始 err 供除錯，UI 顯示與「帳密錯誤」相同的通用訊息 |

實際 i18n 鍵名與翻譯文字 → 寫測試時 grep `server/procLang.mjs` 對應前綴後直接讀取，避免在本文件 mirror 翻譯字串造成 drift。

## 登入成功分流

| URL 條件 | useRedir | redir 欄位 | 結果 |
|---|---|---|---|
| 無 view 或 `view=login` | true | 有值 | 轉址至 redir 網址 |
| 無 view 或 `view=login` | true | 無值 | 顯示無有效轉址錯誤 (見 i18n 訊息粒度規則表) |
| `view=backstage` | false | 不看 | 留在前端進入後台 |
| `view=user` | false | 不看 | 留在前端進入使用者資訊頁 |

## 參數來源

本流程涉及以下執行期參數，**讀取優先序：`settings.json` 覆寫值 > `server/WWebSso.mjs` 預設**：

| 概念 | 來源 (優先序) | 流程影響 |
|---|---|---|
| Token 有效期 (建立 token 時 timeEnd = now + N 分鐘) | `settings.json` 找 token 有效期相關 key → `server/WWebSso.mjs` opt 預設 | 影響登入後 token 多久過期、自動登入流程可用窗口 |
| 失敗次數 / 觀察分鐘數 / 封鎖時長 (背景 timer 判定 timeBlocked 用) | `settings.json` 找登入失敗相關 key → `server/WWebSso.mjs` opt 預設 | 影響「帳號被暫時封鎖」觸發條件，本流程僅讀取 timeBlocked 結果，不直接消費這些閾值 |

實際數值 → 寫測試時讀 `settings.json` 對應 key，若無覆寫則查 `server/WWebSso.mjs` opt 預設。

## spec 規則摘要（粒度 / 邊界 / 順序 / 契約）

- **驗證順序**：protect 層 `timeBlocked` 檢查 → 核心查 user → `isActive` 檢查 → 密碼比對 → `timeVerified` 檢查 → `timeExpired` 檢查 → 建立 token。**順序屬 spec 不得調動**（調動會洩露帳號存在性）。
- **粒度**：
  - 帳號不存在 / 密碼錯誤 / `isActive='n'` / 帳號封鎖（`timeBlocked` 未到期）**共用同一條訊息**，禁止洩露帳號是否存在或是否被封鎖（防帳號列舉）。
  - 未驗證（顯示重寄連結）/ 已過期 各自具體訊息。
  - 重寄驗證信時 email 不符可洩露（使用者已通過帳密前置條件，無列舉風險）。
- **邊界**：
  - 核心層查 user **不限 `isActive`**（以便逐一檢查狀態，再由 spec 順序決定何時 reject）。
  - 登入成功分流以 URL `view` 為準（`login` / `backstage` / `user`）。
  - `view=login` 須有 `redir`，無 `redir` 顯示無有效轉址錯誤。
- **契約**：
  - protect 層 reject 字串（i18n key，如 `failedLoginForCatch` / `userRegistrationNotVerified` / `loginAccountExpired`）原樣上拋給 `WWebSso` handler，再原樣上拋給 `mUI.login`，再上拋給 `PageLogin`；PageLogin 依錯誤字串對應 i18n 鍵後顯示，**錯誤字串本身不直接顯示**。
  - **例外路徑**：登入成功但 `redir` 為空時，`mUI` 前端層 reject 的是內部字串 `'invalid redir'`（非 procLang i18n key）；PageLogin 以 `else if (err === 'invalid redir')` 特例分支將其映射為 `$t('failedLoginForNoRedir')` 顯示（見 `PageLogin.vue:774-777`）。此為唯一一條「前端內部字串 → 特例映射 key」路徑，與後端 key 原樣上拋路徑不同。
  - 登入成功須同時取得 user object 與 token，任一無效 reject。
  - Token 建立時 `timeEnd = now + minExpired 分鐘`；本流程結束後 token 寫入 localStorage 供自動登入使用。
- **安全防護**：
  - 密碼雜湊比對採 `crypto.timingSafeEqual`（常數時間比對），避免比對所耗時間隨字串前綴相符長度而變動，阻擋以時間差推測密碼雜湊內容之 timing side-channel attack。即使本系統已具備 autoblock 帳號鎖定機制（短時間內多次失敗即觸發 `timeBlocked`），使遠端 timing attack 於實務上不可行，仍視為 best-practice 之 defense-in-depth，不因鎖定機制存在而退回一般字串等號比對。
