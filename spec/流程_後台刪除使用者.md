# 後台刪除使用者流程

## 觸發

管理員於 LayoutContentUsers.vue 後台 Users list 勾選一列以上, 點「刪除勾選使用者」垃圾桶按鈕將該批列從前端 rows 過濾, 再點「儲存」批次提交至後端執行 procOrm del.

## 重要流程

- **E2E-001**
  - title: 管理員進 Users list 看到初始未勾選清單
  - description: 驗證管理員以有效 token 登入後進入 Users list 編輯模式，且未勾選任何列時的初始畫面：表內可看到 du-admin 與 du-target 等列，垃圾桶按鈕因 hasItemsCheck=false 隱藏。本案例為「勾選後點刪除」流程鏈第 1 段（delete-success 步驟 1: 001-initial-users-list），主角共用 admin / target user 由本檔自行 own、不外擴。
  - flow:
    - 測試資料：admin user `id-du-admin`（帳號 `du-admin` / 密碼 `Pw@duadmin1` / `isAdmin='y'` / `isActive='y'` / `timeVerified` 有值 / `timeExpired` 未來 / `timeBlocked` 空 / `redir` 帶 `?view=backstage&token={token}`），target user `id-du-target`（帳號 `du-target` / 密碼 `Pw@dutarget1` / `isAdmin='n'` / `redir` 帶 `?view=user&token={token}`），admin token 有效 60 分鐘。

      1. 語意：DOM body 含 `du-admin` 與 `du-target`（清單呈現初始狀態）；垃圾桶按鈕不存在（無勾選時 trash 隱藏）。
      2. 視覺：與 baseline `test/pics/deleteuser/deleteuser-{eng,cht}-E2E-001-initial-users-list.png` 視覺一致（pixelmatch 容差）。

## 執行流程

### 一、勾選列（rowChecked）

```
001  管理員於 ag-grid 列首 checkbox 勾選一列以上 (僅 isEditable 顯示 checkbox)
002  WAggridVue rowChecked 回呼觸發  [LayoutContentUsers.vue:1057]
003  vo.itemsCheck = cloneDeep(rs)  [LayoutContentUsers.vue:1062]
        rs 為 ag-grid 回傳之勾選列陣列, 元素含 data.id (用於後續比對)
004  hasItemsCheck = size(vo.itemsCheck) > 0 = true → 垃圾桶按鈕浮現
        (按鈕顯示條件: isEditable && hasItemsCheck)
```

### 二、刪除（deleteItemsCheck）

```
001  管理員點垃圾桶按鈕「刪除勾選使用者」  [LayoutContentUsers.vue:160]
002  size(vo.itemsCheck) === 0 守門 → 為 0 顯示對應錯誤訊息即 return
        (正常 UI 流程下, hasItemsCheck=false 時按鈕不顯示, 此分支為防呆)
003  rows = get(vo, 'opt.rows', []) → cloneDeep(rows)
004  逐一掃描 vo.itemsCheck:
        id = get(v, 'data.id', '')
        若 id 非有效字串 → continue (跳過)
        rows = filter(rows, (vv) => vv.id !== id)   //從 rows 移除該 id
005  vo.itemsCheck = []   //勾選清空 (rows 內已不含這些列, ag-grid 也不會再回傳這些 row)
006  vo.users = cloneDeep(rows) → 連帶驅動 computed 重算 items / opt.rows, 表格立即少列
007  isModified = true → 顯示紅底「儲存」按鈕
        注意: 此階段未呼叫任何後端 API, DB 仍未刪除. 須點儲存才會送至後端落地.
        本函式亦未提供 undo: 若反悔須直接「不點儲存」, 重整頁面 / 重拉 getUsersList 取回原列.
```

## spec 規則摘要（粒度 / 邊界 / 順序 / 契約）

- **驗證順序**：前端 `isError` 攔截 → 前端 rows 空檢查 → 前端自我保護（含 cannotDeleteSelf）→ 後端 `checkToken`（含 funCheckAdmin）→ 後端自我保護（含 cannotDeleteSelf）→ `ckKey('id')` / `ckKey('email')` → procOrm del 寫入。任一層 reject 即整批不落地。
- **粒度**：刪自己 / 解除自己 admin / 停用自己分別用不同訊息；token 失效與身分不足共用同一訊息（不洩露身分檢查）。
- **邊界**：
  - 無獨立 deleteUser API：刪除走 `updateUsersList` 批次儲存共用路徑，由 ltdtDiffByKey 自動推得 del 群組。
  - 無前端二次確認 dialog：點垃圾桶僅執行 rows 過濾 + isModified=true；真正落地需 admin 再點「儲存」。此 gap 即「逃生口」（反悔可不點儲存）。
  - 無 undo 機制：deleteItemsCheck 直接從 vo.users / opt.rows 過濾，不保留 snapshot；反悔僅能重整 / 重拉 getUsersList。
  - 自我刪除保護：rows 內若**不**包含操作者本人（admin 把自己勾選刪除後 rows 移除自己 row），前端 saveUsers 與後端 checkTokenAndUpdateUsersList 皆以 `cannotDeleteSelf` 擋下；前後端兩道防線，訊息一致。
  - 級聯清理：procOrm 'users' 'del' 僅刪 users 表，不級聯清除被刪 user 名下既有 tokens / ips；須仰賴自然到期或另行清理。
- **契約**：
  - `updateUsersList` 走批次 upsert：整表 `ltdtDiffByKey` 一次同步 add / diff / del；若 admin 同時對其他列做過編輯，任一驗證錯誤即整批不落地（含本次刪除）。
  - 儲存成功後立即重拉 `getUsersList` 同步剩餘列與 resetOrder 後的 order。
  - API 回傳前剝除 password 欄位，避免 hash 從 API 流出。
