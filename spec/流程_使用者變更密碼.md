# 使用者變更帳密流程

## 觸發

使用者於 user view（`viewState='user'`，PageUser.vue）點擊「變更密碼 / Change Password」按鈕，展開變更表單，輸入舊密碼、新密碼、確認密碼後點擊「送出 / Submit」。

## 重要流程

- **E2E-001**
  - title: 點變更密碼展開三欄表單
  - description: 驗證使用者於 user view 點擊「變更密碼 / Change Password」按鈕後，畫面正確展開變更密碼表單（含舊密碼、新密碼、確認密碼三欄位與「送出」按鈕），且初始未顯示任何 inline 錯誤訊息。此案例為變更密碼流程的起點，後續 E2E-002 至 E2E-010 均以表單展開狀態為前置。
  - flow:
    - 測試資料：user `id-changepassword-{lang}`（帳號 `chpwuser-{lang}` / 原密碼 `Tk@246802` / `isActive='y'` / `timeVerified` 有值 / `timeExpired` 未來 / `timeBlocked` 空 / `redir` 帶 `?view=user&token={token}`），並建立對應 token 寫入 localStorage。
    - 操作：開乾淨頁面並寫入 token → 帶 `?view=user&lang={lang}` 進入 user view → 等待 autoLogin 完成 → 點「變更密碼」/「Change Password」按鈕。
    - 驗證：
      1. 語意：DOM 上出現「Send」/「送出」按鈕文字（表單已展開）。
      2. 視覺：與 baseline `test/pics/changepassword/changepassword-{eng,cht}-E2E-001-form-initial.png` byte-equal。
    - 雙語：eng / cht 各一輪。
    - 清理：移除本檔特化 user 與 token，保留 base seed。

- **E2E-002**
  - title: 三欄空送出舊密碼欄顯示提示

  - flow:
    - 測試資料：user `id-changepassword-{lang}`（帳號 `chpwuser-{lang}` / 原密碼 `Tk@246802`）+ 有效 token 寫入 localStorage。
    - 操作：進入 user view 並展開變更密碼表單 → 三欄保持空 → 點「Send」/「送出」按鈕。
    - 驗證：
      1. 語意：DOM 上出現「Please enter old password」/「尚未給予舊密碼」（位於舊密碼欄位下方）。
      2. 視覺：與 baseline `test/pics/changepassword/changepassword-{eng,cht}-E2E-002-old-empty.png` byte-equal。
    - 雙語：eng / cht 各一輪。
    - 清理：移除本檔特化 user 與 token，保留 base seed。

- **E2E-004**

- **E2E-005**
  - title: 新密碼與確認密碼不一致提示
  - description: 驗證使用者展開變更密碼表單後，三欄均填妥但新密碼與確認密碼不一致即點擊「送出」，前端依驗證順序通過三欄空檢、接著檢查兩次密碼一致性，於「確認密碼」欄位下方以紅字 inline 顯示不一致訊息（「New password and confirm password do not match」/「新密碼與確認密碼不一致」）。對應 spec 粒度規則：兩次密碼不一致為直接具體訊息。
  - flow:
    - 測試資料：user `id-changepassword-{lang}`（帳號 `chpwuser-{lang}` / 原密碼 `Tk@246802`）+ 有效 token 寫入 localStorage。

- **E2E-006**
  - title: 新密碼不符策略顯示具體策略名
  - description: 驗證使用者送出變更時，新密碼不符密碼策略（如長度過短、字元類不足、共用黑名單等），前端通過三欄空檢與一致性檢查後呼叫後端 `checkUserPassword`，於「新密碼」欄位下方以紅字 inline 顯示具體策略名（如「Password length must be at least 8 characters」/「密碼長度須大於等於8個字元」）。對應 spec 粒度規則：策略違反帶具體策略名（前端已知策略，逐項列出）。此案例以 `12345`（5 字元）觸發後端先回的長度錯誤（NumLenMin 優先於 RequireLetter）。
  - flow:
    - 測試資料：user `id-changepassword-{lang}`（帳號 `chpwuser-{lang}` / 原密碼 `Tk@246802`）+ 有效 token 寫入 localStorage。
    - 操作：進入 user view 並展開變更密碼表單 → 舊密碼欄輸入 `Tk@246802` → 新密碼欄與確認密碼欄均輸入 `12345`（5 字元、全數字、命中常見密碼黑名單）→ 點「Send」/「送出」按鈕 → 等待後端 `checkUserPassword` 回應。
    - 驗證：
      1. 語意：DOM 上出現「Password length must be at least 8 characters」/「密碼長度須大於等於8個字元」（位於新密碼欄位下方）。
      2. 視覺：與 baseline `test/pics/changepassword/changepassword-{eng,cht}-E2E-006-pw-policy-fail.png` byte-equal。
    - 雙語：eng / cht 各一輪。
    - 清理：移除本檔特化 user 與 token，保留 base seed。

- **E2E-007**
  - title: 舊密碼錯顯示統一變更失敗
  - description: 驗證使用者送出變更時，新密碼通過前端策略檢查但舊密碼填錯，後端 `changeUserPassword` 比對舊密碼雜湊不符而 reject，於「舊密碼」欄位下方以紅字 inline 顯示統一「變更失敗」訊息（「Password change failed」/「密碼變更失敗」），不洩露具體 reject 原因。對應 spec 粒度規則：後端任何 reject 統一訊息「變更失敗」，避免洩露細節。本案例之 baseline 同時被 E2E-010 共用。
  - flow:
    - 測試資料：user `id-changepassword-{lang}`（帳號 `chpwuser-{lang}` / 原密碼 `Tk@246802`）+ 有效 token 寫入 localStorage。
    - 操作：進入 user view 並展開變更密碼表單 → 舊密碼欄輸入 `Tk@246999`（與真實原密碼不同）→ 新密碼欄與確認密碼欄均輸入 `Tk@975310` → 點「Send」/「送出」按鈕 → 等待後端 `checkUserPassword` 與 `changeUserPassword` 完成。
    - 驗證：
      1. 語意：DOM 上出現「Password change failed」/「密碼變更失敗」（位於舊密碼欄位下方）。
      2. 視覺：與 baseline `test/pics/changepassword/changepassword-{eng,cht}-E2E-007-old-wrong.png` byte-equal（此 baseline 亦由 E2E-010 共用）。
    - 雙語：eng / cht 各一輪。
    - 清理：移除本檔特化 user 與 token，保留 base seed。

- **E2E-008**
  - title: 三欄填妥正確變更成功
  - description: 驗證使用者送出變更時，三欄均填妥、新密碼合規且舊密碼正確，後端完成 hash 寫入、`isForceChangePw` 設為 `'n'`、並寄送通知信，前端關閉變更表單並以 showCheckYes modal（System message）顯示成功訊息「Password change successful」/「密碼變更成功」。對應 spec 規則：寄信失敗不阻擋變更結果，成功後 token 不變、原 session 保留。
  - flow:
    - 測試資料：user `id-changepassword-{lang}`（帳號 `chpwuser-{lang}` / 原密碼 `Tk@246802` / 有效 email）+ 有效 token 寫入 localStorage。
    - 操作：進入 user view 並展開變更密碼表單 → 舊密碼欄輸入 `Tk@246802` → 新密碼欄與確認密碼欄均輸入 `Tk@975310` → 點「Send」/「送出」按鈕 → 等待 showCheckYes modal 出現。
    - 驗證：
      1. 語意：DOM 上出現「Password change successful」/「密碼變更成功」（成功訊息 modal）。
      2. 視覺：與 baseline `test/pics/changepassword/changepassword-{eng,cht}-E2E-008-success.png` byte-equal。
    - 雙語：eng / cht 各一輪。
    - 清理：點 modal 上的「OK」/「確認」收尾，移除本檔特化 user 與 token，保留 base seed。

- **E2E-009**
  - title: 前端策略檢查網路錯誤顯示提示
  - description: 驗證使用者送出變更時，前端呼叫後端 `checkUserPassword` 過程發生網路錯誤（攔截 `/api/main` POST 模擬斷線），於「新密碼」欄位下方以紅字 inline 顯示統一網路錯誤訊息「Password validation failed」/「密碼檢測失敗」，不進入後續 `changeUserPassword` 呼叫。對應 spec 粒度規則：前端策略檢查網路錯誤為統一訊息（與策略違反具體名分離）。
  - flow:
    - 測試資料：user `id-changepassword-{lang}`（帳號 `chpwuser-{lang}` / 原密碼 `Tk@246802`）+ 有效 token 寫入 localStorage。
    - 操作：進入 user view 並展開變更密碼表單 → 舊密碼欄輸入 `Tk@246802` → 新密碼欄與確認密碼欄均輸入 `Tk@975310` → 於送出前啟動 `/api/main` POST 攔截使其 abort → 點「Send」/「送出」按鈕 → 等待 inline 錯誤出現。
    - 驗證：
      1. 語意：DOM 上出現「Password validation failed」/「密碼檢測失敗」（位於新密碼欄位下方）。
      2. 視覺：與 baseline `test/pics/changepassword/changepassword-{eng,cht}-E2E-009-network-error.png` byte-equal。
    - 雙語：eng / cht 各一輪。
    - 清理：解除 `/api/main` 攔截，移除本檔特化 user 與 token，保留 base seed。

- **E2E-010**
  - title: token 失效顯示統一變更失敗
  - description: 驗證使用者於變更密碼流程進行至送出前 token 已失效（DB 中途刪除模擬過期/被清除），後端 `checkToken` reject，於「舊密碼」欄位下方以紅字 inline 顯示統一「變更失敗」訊息（「Password change failed」/「密碼變更失敗」），不洩露 token 失效細節。此案例與 E2E-007 視覺等同（後端任何 reject 統一訊息），故共用 E2E-007 baseline，spec 將其列為視覺等同案例。
  - flow:
    - 測試資料：user `id-changepassword-{lang}`（帳號 `chpwuser-{lang}` / 原密碼 `Tk@246802`）+ 有效 token 寫入 localStorage。
    - 操作：進入 user view 並展開變更密碼表單 → 三欄均輸入正確值（舊 `Tk@246802` / 新 `Tk@975310` / 確認 `Tk@975310`）→ 於送出前自 DB 刪除該 user 所有 token → 點「Send」/「送出」按鈕 → 等待 inline 錯誤出現。
    - 驗證：
      1. 語意：DOM 上出現「Password change failed」/「密碼變更失敗」（位於舊密碼欄位下方）。
      2. 視覺：與 E2E-007 共用 baseline `test/pics/changepassword/changepassword-{eng,cht}-E2E-007-old-wrong.png` byte-equal（視覺等同，避免維護多份等價 baseline）。
    - 雙語：eng / cht 各一輪。
    - 清理：移除本檔特化 user 與 token（token 流程內已刪除，user 由 cleanup 統一移除），保留 base seed。

## 執行流程

### 一、展開變更密碼表單

```
001  使用者點擊「變更密碼」按鈕  [PageUser.vue:382]
002  showChangePassword = true（展開表單）  [PageUser.vue:384]
003  清空 oldPassword / newPassword / confirmPassword 欄位  [PageUser.vue:385-387]
004  showOldPassword / showNewPassword / showConfirmPassword 預設 false（密碼遮罩）  [PageUser.vue:388-390]
005  清空 chPwOldError / chPwNewError / chPwConfirmError 三個 inline 錯誤訊息  [PageUser.vue:392-394]
```

### 二、取消變更

```
001  使用者點擊「取消」按鈕  [PageUser.vue:397]
002  showChangePassword = false（收起表單）  [PageUser.vue:399]
003  清空 chPwOldError / chPwNewError / chPwConfirmError  [PageUser.vue:401-403]
```

> 註：欄位內容不主動清空，使用者下次再點「變更密碼」時，clickChangePassword 會清空。

```
047      $ui.updateLoading(false) 隱藏 loading  [PageUser.vue:505]
```

### 四、變更成功後的後續

- 變更成功後使用者繼續處於 user view，**token 不變**（原有 session 保留，不需重新登入）
- 後端 save 時把 `isForceChangePw` 寫為 `'n'`（無論進入流程前是何值），代表變更密碼動作會解除強制變更狀態
- email 通知（若寄信成功）內容由 `server/template/changePasswordEmail-{lang}.html` 控制
- 下次以舊密碼登入會被擋下（密碼已改）；以新密碼登入正常通過
- 其他裝置既有 token 不受影響，仍可使用至 timeEnd（密碼變更**不**強制清除既有 token）

### 五、密碼策略多層檢查設計

策略檢查在前端送出前與後端寫入前各執行一次：

| 階段 | 檢查內容 |
|---|---|
| 前端 UI | 三欄是否填妥 + 兩次密碼一致 |
| 前端 → 後端 `checkUserPassword` API | 策略合規（長度 / 字元類 / 黑名單 / 與帳號連續字元等） |
| 後端 `changeUserPassword` 內部 | 再次呼叫 `checkUserPassword`（防 caller 跳過前端） |
| 後端 比對舊密碼 hash | 不符 reject |
| 後端 寫入 + 寄通知信 | 成功完成 |

兩層 `checkUserPassword`（前端送出前 + 後端 `changeUserPassword` 內）是有意設計：前者給使用者及時 UX 反饋，後者防止 caller 略過前端直接打 API。

## 參數來源

本流程涉及以下執行期參數，**測試讀取順序：`settings.json` 覆寫值 > `server/WWebSso.mjs` opt 預設**：

| 概念 | 來源（優先序）| 測試影響 |
|---|---|---|
| 密碼策略（長度上下限 / 字元類要求 / 禁用字元 / 共用黑名單 / 與帳號連續字元門檻）| `settings.json` `passwordPolicy` → `server/WWebSso.mjs` opt 預設 | 構造「不符策略」case 須避開所有規則才能進入下一階段；構造「合規」case 須繞開帳號連續字元、避開黑名單 |
| 鹽 salt | `settings.json` `salt` → `server/WWebSso.mjs` opt 預設 | 比對 DB password hash 須用同 salt |
| Email 寄信設定（SMTP）| `settings.json` `emSrc*` 系列 | 寄信失敗不影響流程結果，但測試時 SMTP 不通會等網路 timeout（~30s） |

實際數字 / 字元集 → 寫測試時讀 `settings.json` 對應 key，若無 → 讀 `server/WWebSso.mjs` opt 預設值。

## spec 規則摘要（粒度 / 邊界 / 順序 / 契約）

- **驗證順序**：前端空欄三檢查（舊 / 新 / 確認密碼）→ 兩次密碼一致 → 前端呼叫 `checkUserPassword` 策略檢查 → 後端 `checkToken` → 後端 `checkUserPassword`（防呆，防 caller 略過前端）→ 比對舊密碼雜湊 → 檢查 email 非空 → save 新 hash + 寄通知信。任一層 reject 即不寫入。
- **粒度**：
  - 空欄各別具體訊息（指明哪欄空），inline 紅字顯示於對應欄位下方。
  - 兩次密碼不一致 / 策略違反 / 網路錯誤 各自具體訊息。
  - 策略違反帶**具體策略名**（前端已知策略，可逐項列出）。
  - 後端任何 reject（舊密碼錯 / token 過期 / email 無效 / 後端 checkUserPassword 防呆 reject）**統一「變更失敗」訊息**，不洩露 reject 原因。
- **訊息呈現分工**（與全專案 A14 遷移後共識一致）：
  - **操作結果**（成功 / 已完成的可預期動作）→ `$dg.showCheckYes` 持久 modal，須使用者點 OK 確認；不自動消失，避免使用者錯過。
  - **非預期錯誤**（外層 `core().catch` 兜底的 throw / 漏接 reject）→ `$alert` toast，刻意低調，不放大未知例外造成可靠度感受下降。
  - **欄位驗證**（空欄 / 不一致 / 策略違反 / 統一變更失敗）→ inline 紅字顯示於對應欄位下方，貼近使用者輸入焦點。
- **邊界**：
  - 寄信失敗**不阻擋變更結果**（僅 `srLog.error`，使用者體驗為密碼已成功變更）。
  - 「取消」按鈕只清 inline errors，**不清欄位內容**（下次點「變更密碼」展開時才清）。
  - 變更後 `token 不變`（原 session 保留），**其他裝置既有 token 不清除**（trade-off：simplicity）。
- **契約**：
  - 兩層 `checkUserPassword`：前端送出前（UX 反饋） + 後端 `changeUserPassword` 內（防 caller 跳過前端）。
  - save 時 `isForceChangePw='n'` 無條件寫入（解除強制變更狀態，無論進入流程前是何值）。
  - password 加鹽雜湊後寫入 DB（salt 由 settings 提供）。
  - 舊密碼雜湊比對使用 `crypto.timingSafeEqual` 常數時間比對，防 timing side-channel attack（攻擊者依比對耗時差異推測雜湊前綴）。與登入路徑同款（詳 `spec/流程_使用者一般登入.md`），屬 defense-in-depth。
  - Email 模板路徑：`server/template/changePasswordEmail-{eng,cht}.html`。
