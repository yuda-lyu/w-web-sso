# 使用者變更帳密流程

## 觸發

使用者於 user view（`viewState='user'`，PageUser.vue）點擊「變更密碼 / Change Password」按鈕，展開變更表單，輸入舊密碼、新密碼、確認密碼後點擊「送出 / Submit」。

## 重要流程

- **E2E-001**
  - title: 點變更密碼展開三欄表單
  - description: 驗證使用者於 user view 點擊「變更密碼 / Change Password」按鈕後，畫面正確展開變更密碼表單（含舊密碼、新密碼、確認密碼三欄位與「送出」按鈕），且初始未顯示任何 inline 錯誤訊息。此案例為變更密碼流程的起點，後續 E2E-002 至 E2E-010 均以表單展開狀態為前置。

    - 測試資料：user `id-changepassword-{lang}`（帳號 `chpwuser-{lang}` / 原密碼 `Tk@246802` / `isActive='y'` / `timeVerified` 有值 / `timeExpired` 未來 / `timeBlocked` 空 / `redir` 帶 `?view=user&token={token}`），並建立對應 token 寫入 localStorage。
    - 操作：開乾淨頁面並寫入 token → 帶 `?view=user&lang={lang}` 進入 user view → 等待 autoLogin 完成 → 點「變更密碼」/「Change Password」按鈕。

      1. 語意：DOM 上出現「Send」/「送出」按鈕文字（表單已展開）。

## 執行流程

### 一、展開變更密碼表單

```
001  使用者點擊「變更密碼」按鈕，呼叫 clickChangePassword  [PageUser.vue:387]
002  showChangePassword = true（展開表單）  [PageUser.vue:389]
003  清空 oldPassword / newPassword / confirmPassword 欄位  [PageUser.vue:390-392]
004  showOldPassword / showNewPassword / showConfirmPassword 預設 false（密碼遮罩）  [PageUser.vue:393-395]
005  清空 chPwOldError / chPwNewError / chPwConfirmError 三個 inline 錯誤訊息  [PageUser.vue:397-399]
```

### 二、取消變更

```
001  使用者點擊「取消」按鈕，呼叫 cancelChangePassword  [PageUser.vue:402]
002  showChangePassword = false（收起表單）  [PageUser.vue:404]
003  清空 chPwOldError / chPwNewError / chPwConfirmError  [PageUser.vue:406-408]
```

> 註：欄位內容不主動清空，使用者下次再點「變更密碼」時，clickChangePassword 會清空。

### 三、送出變更

```

003      每次送出先清空 chPwOldError / chPwNewError / chPwConfirmError 三個 inline 錯誤訊息  [PageUser.vue:417-419]
004      檢查 oldPassword 為空  [PageUser.vue:422]
005          空:
006              chPwOldError = $t('userChangePasswordForNoOldPassword')（舊密碼欄下方紅字）, return  [PageUser.vue:423]
007      檢查 newPassword 為空  [PageUser.vue:428]
008          空:
009              chPwNewError = $t('userChangePasswordForNoNewPassword'), return  [PageUser.vue:429]
010      檢查 confirmPassword 為空  [PageUser.vue:434]
011          空:
012              chPwConfirmError = $t('userChangePasswordForNoConfirmPassword'), return  [PageUser.vue:435]
013      檢查 newPassword 與 confirmPassword 一致  [PageUser.vue:440]
014          不一致:
015              chPwConfirmError = $t('userChangePasswordNotSame'), return  [PageUser.vue:441]
016      同步驗證全通過、確定要打 API 才 $ui.updateLoading(true) 顯示 loading  [PageUser.vue:446]

018          state==='success': okCkPw=true 繼續  [PageUser.vue:452-453]
019          state==='error': chPwNewError = $tErr(res.key)（後端回 { state:'error', key }，前端以 key 翻譯+插值政策值）  [PageUser.vue:457]
```

### 四、變更成功後的後續

- 成功訊息以持久 modal 顯示 `userChangePasswordSuccess`，文案為「Password change successful, please log in again.」/「密碼變更成功，請使用新密碼重新登入。」，提示使用者改以新密碼重新登入
- 後端 save 僅寫 `{ id, password, isForceChangePw:'n' }`；同一組 `[tokens, users]` 表鎖內另撤銷該使用者**其他**session 權杖：**當前 token（送出變更之 session）在後端仍有效、未被清除**，使用者點 OK 後仍處於 user view（〔原載「不觸及 tokens 表，既有 session 在後端不被密碼變更牽動」不成立，2026-10-23 改為本句，第 117 項、ADR-093〕）
- 後端 save 時把 `isForceChangePw` 寫為 `'n'`（無論進入流程前是何值），代表變更密碼動作會解除強制變更狀態
- email 通知（若寄信成功）內容優先由 settings 之 `chpwEmTitle` / `chpwEmContent`（逐語系物件，各值可給文字或檔案路徑，`{sender}`/`{name}` 置換）客製，未給採內建語系文字（`server/procLang.mjs` 同名鍵）
- 下次以舊密碼登入會被擋下（密碼已改）；以新密碼登入正常通過
- 其他裝置之 session 權杖被撤銷（立即無效，`checkToken` 回 `tokenExpired`，該裝置下次呼叫即回登入頁），須以新密碼重新登入；app 權杖不受影響（〔原載「其他裝置既有 token 不受影響，仍可使用至 timeEnd（密碼變更不強制清除既有 token）」不成立，2026-10-23 改為本句，ADR-093〕）

### 五、密碼策略多層檢查設計

策略檢查在前端送出前與後端寫入前各執行一次：

| 階段 | 檢查內容 |
|---|---|
| 前端 UI | 三欄是否填妥 + 兩次密碼一致 |
| 前端 → 後端 `checkUserPassword` API | 策略合規（長度 / 字元類 / 黑名單 / 與帳號連續字元等） |
| 後端 `changeUserPassword` 內部 | 再次呼叫 `checkUserPassword`（防 caller 跳過前端） |
| 後端 比對舊密碼 hash | 不符 reject |
| 後端 寫入 + 寄通知信 | 成功完成 |

兩層 `checkUserPassword`（前端送出前 + 後端 `changeUserPassword` 內）是有意設計：前者給使用者及時 UX 反饋，後者防止 caller 略過前端直接打 API。

## 參數來源

本流程涉及以下執行期參數，**測試讀取順序：`settings.json` 覆寫值 > `server/WWebSso.mjs` opt 預設**：

| 概念 | 來源（優先序）| 測試影響 |
|---|---|---|
| 密碼策略（長度上下限 / 字元類要求 / 禁用字元 / 共用黑名單 / 與帳號連續字元門檻）| `settings.json` `passwordPolicy` → `server/WWebSso.mjs` opt 預設 | 構造「不符策略」case 須避開所有規則才能進入下一階段；構造「合規」case 須繞開帳號連續字元、避開黑名單 |
| 鹽 salt | `settings.json` `salt` → `server/WWebSso.mjs` opt 預設 | 比對 DB password hash 須用同 salt |
| Email 寄信設定（SMTP）| `settings.json` `emSrc*` 系列 | 寄信失敗不影響流程結果，但測試時 SMTP 不通會等網路 timeout（~30s） |

實際數字 / 字元集 → 寫測試時讀 `settings.json` 對應 key，若無 → 讀 `server/WWebSso.mjs` opt 預設值。

## spec 規則摘要（粒度 / 邊界 / 順序 / 契約）

- **改密碼後之 session 處置**（2026-10-23，第 117 項；帳本 R-SESS-01、ADR-093）：驗證（舊密碼、新密碼策略、email）全數通過後，**先撤銷其他 session 權杖、後寫新密碼**，同在 `[tokens, users]` 表鎖內；撤銷失敗則整體拒絕（`userChangePasswordFail`）且密碼不變；密碼寫入失敗時其他 session 已撤銷、目前 session 保留（fail closed）；驗證未過不撤銷任何權杖。使用者用途金鑰呼叫時（所綁使用者本人）無目前 session，該使用者全部 session 撤銷（2026-10-24 ADR-095：原載「app 權杖呼叫時（擁有者為該使用者）」；系統服務用途金鑰不可呼叫，回 `tokenUserOnly`）。鎖內另再驗呼叫權杖（見執行流程 025a）：同使用者兩個 session 並行改密碼時，先取得鎖者保留自己、撤銷對方，對方於鎖內被拒（`tokenExpired`），最終保留先到者之 session。測試：`unit-passwordSession`（PS-U-004～008、011、012、018～021）、`api-passwordsession`（PSA-003、004、005、006）。
- **多人同時編輯之表鎖**（2026-10-23，原則 10；帳本 R-CONC-01）：讀取使用者、驗舊密碼與寫入新密碼雜湊（`password`、`isForceChangePw='n'`）整段在 `[tokens, users]` 表鎖內（2026-10-23 sso-run04 起，原為 `users` 單表；同鎖撤銷其他 session）（`kmx` 在外層、表鎖在內層），經 w-serv-orm 且只改不增，更新者 `userIdUpdate` 記該使用者本人。`password` 為伺服器專有欄位，變更後載入在變更之前的後台清單頁存檔不會把密碼雜湊回寫成舊值（修正）。
- **驗證順序**：前端空欄三檢查（舊 / 新 / 確認密碼）→ 兩次密碼一致 → 前端呼叫 `checkUserPassword` 策略檢查 → 後端 `checkToken` → 後端 `checkUserPassword`（防呆，防 caller 略過前端）→ 比對舊密碼雜湊 → 檢查 email 非空 → save 新 hash + 寄通知信。任一層 reject 即不寫入。save 之結果逐筆檢查（w-orm 單筆失敗不 reject），寫入失敗即回 `userChangePasswordFail` 且不寄通知信，不以未生效之變更回報成功（ADR-080）。
- **粒度**：
  - 空欄各別具體訊息（指明哪欄空），inline 紅字顯示於對應欄位下方。
  - 兩次密碼不一致 / 策略違反 / 網路錯誤 各自具體訊息。
  - 策略違反帶**具體策略名**（前端已知策略，可逐項列出）。
  - 後端任何 reject（舊密碼錯 / token 過期 / email 無效 / 後端 checkUserPassword 防呆 reject）**統一「變更失敗」訊息**，不洩露 reject 原因。
- **訊息呈現分工**（與全專案 A14 遷移後共識一致）：
  - **操作結果**（成功 / 已完成的可預期動作）→ `$dg.showCheckYes` 持久 modal，須使用者點 OK 確認；不自動消失，避免使用者錯過。
  - **非預期錯誤**（外層 `core().catch` 兜底的 throw / 漏接 reject）→ `$alert` toast，刻意低調，不放大未知例外造成可靠度感受下降。
  - **欄位驗證**（空欄 / 不一致 / 策略違反 / 統一變更失敗）→ inline 紅字顯示於對應欄位下方，貼近使用者輸入焦點。
- **邊界**：
  - 寄信失敗**不阻擋變更結果**（僅 `srLog.error`，使用者體驗為密碼已成功變更）。
  - 「取消」按鈕只清 inline errors，**不清欄位內容**（下次點「變更密碼」展開時才清）。
  - 變更後後端**撤銷該使用者其他 session 權杖、保留目前 session**（2026-10-23 起，第 117 項；R-SESS-01、ADR-093 取代 ADR-009 之 Decision）：目前 token 仍可用至 timeEnd；其他裝置之 session 權杖立即無效；app 權杖（`isApp === 'y'`）不撤銷。成功訊息文案仍提示使用者改以新密碼重新登入。〔原載「變更後後端 save 不觸及 tokens 表：當前 token 與其他裝置既有 token 在後端皆不被清除（ADR-009）」不成立〕
- **契約**：
  - 兩層 `checkUserPassword`：前端送出前（UX 反饋） + 後端 `changeUserPassword` 內（防 caller 跳過前端）。
  - save 時 `isForceChangePw='n'` 無條件寫入（解除強制變更狀態，無論進入流程前是何值）。
  - password 加鹽雜湊後寫入 DB（salt 由 settings 提供）。
  - 舊密碼雜湊比對使用 `verifyPassword`（解析 DB 內 `scrypt:saltHex:hashHex` 自描述字串，取出 per-user salt 與雜湊值，以相同 salt + pepper 重新以 `crypto.scryptSync` 計算後，經長度檢查再以 `crypto.timingSafeEqual` 做常數時間比對），防 timing side-channel attack（攻擊者依比對耗時差異推測雜湊前綴），屬 defense-in-depth。
  - Email 文字來源：settings `chpwEmTitle` / `chpwEmContent`（各值可給文字或檔案路徑）優先；未給採內建語系文字（`server/procLang.mjs` 同名鍵）。

- **設計事實（記錄備查）— 事實更正（業主裁定 2026-10-23，第 117 項）**：本 spec 原載「變更後後端 save 不觸及 tokens 表，當前 token 與其他裝置既有 token 皆不被清除（ADR-009 設計取捨）」不成立。業主依 OWASP ASVS（改密碼後提供終止其他所有 session）裁定改為：使用者自行改密碼時保留目前 session、撤銷其他 session 權杖。改在 `server/procCore.mjs` `checkTokenAndChangePassword`（`revokeSessionTokensLocked`，`[tokens, users]` 同鎖）；受影響案例：無 UI 變更、無標準圖變更（成功訊息與流程不變，目前 session 保留故不強制登出；其他裝置之登出屬既有「權杖無效回登入頁」行為，見 `spec/流程_使用者自動登入.md`）。app 權杖不撤銷。證據：`test/unit-passwordSession.test.mjs`、`test/api-passwordsession.test.mjs`；修前紅、修後綠。
