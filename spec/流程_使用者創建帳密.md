# 使用者創建帳密流程

## 觸發

使用者在 PageLogin.vue 點擊「Register」進入註冊表單，填寫完成後點擊「Submit」。

## 重要流程

- **E2E-001**
  - title: 點 Register link 切入註冊表單
  - description: 驗證使用者於登入頁點擊「Register」/「申請帳號」link 後，PageLogin 由 login 模式切換至 register 模式：input 數從 2 增至 5（account / password / confirmPassword / name / email），並出現 Submit / 送出申請按鈕。本案例為自助註冊流程之入口，後續 E2E-002 至 E2E-005、E2E-009 至 E2E-016 皆以此 register 模式為前置狀態。終態為空表單，僅驗 Submit 按鈕文字以確認 register 模式成立。
  - flow:
    - 測試資料：使用 base seed，不另插入特化 user（本案例僅驗 UI 模式切換）。
    - 操作：開乾淨登入頁（localStorage 無 token）→ 切換語系 → 點「Register」/「申請帳號」link 進入註冊模式。
    - 驗證：
      1. 語意：頁面含「Submit」/「送出申請」按鈕文字（assertSpecForCase 比對 E2E-001-form-initial）。
      2. 視覺：與 baseline `test/pics/register/register-{eng,cht}-E2E-001-form-initial.png` 視覺一致（pixelmatch 容差）。
      3. 結構：.sb 元素須觸發 overflow-y 捲軸（assertSbOverflows）。
    - 雙語：eng / cht 各一輪。
    - 清理：移除本檔特化 user，保留 base seed。

- **E2E-002**
  - title: 註冊密碼過短跳 inline 紅字
  - description: 驗證使用者進入 register 模式後，於密碼欄填入長度小於 minLength（settings.json passwordPolicy.minLength=8）的字串時，前端密碼策略檢測立即於密碼欄下方顯示具體策略名「Password length must be at least 8 characters」/「密碼長度須大於等於8個字元」inline 紅字。對應 spec i18n 粒度規則「密碼策略違反帶具體策略名」。
  - flow:
    - 測試資料：使用 base seed，不另插入特化 user；測試密碼 `aB1@cd`（6 字元，含字母+數字+特殊符號但長度 < 8）。
    - 操作：開乾淨登入頁 → 點「Register」/「申請帳號」link → 於密碼欄輸入 `aB1@cd`。
    - 驗證：
      1. 語意：頁面含「Password length must be at least 8 characters」/「密碼長度須大於等於8個字元」inline 紅字。
      2. 視覺：與 baseline `test/pics/register/register-{eng,cht}-E2E-002-pw-too-short.png` 視覺一致（pixelmatch 容差）。
      3. 結構：.sb 元素須觸發 overflow-y 捲軸（assertSbOverflows）。
    - 雙語：eng / cht 各一輪。
    - 清理：移除本檔特化 user，保留 base seed。

- **E2E-003**

- **E2E-004**
  - title: 密碼多策略違反跳多條紅字
  - description: 驗證使用者於 register 模式輸入同時違反多項密碼策略的字串時，前端密碼策略檢測逐項列出多條 inline 紅字。本案例以 `12345` 觸發長度不足 + 純數字（須含字母）+ 常見密碼黑名單三項策略違反，spec 規定顯示「具體策略名」可同時顯示多條；測試以「Password must contain at least one letter」/「密碼須包含至少一個英文字母」為主要語意斷言錨點。
  - flow:
    - 測試資料：使用 base seed，不另插入特化 user；測試密碼 `12345`（觸發長度不足、純數字、常見黑名單多項違反）。

    - 驗證：
      1. 語意：頁面含「Password must contain at least one letter」/「密碼須包含至少一個英文字母」inline 紅字（多條紅字同時呈現）。
      2. 視覺：與 baseline `test/pics/register/register-{eng,cht}-E2E-004-pw-multi-errors.png` 視覺一致（pixelmatch 容差）。

    - 清理：移除本檔特化 user，保留 base seed。

- **E2E-005**

  - description: 驗證註冊流程所有檢測項（allowUserRegistration / account / email / 密碼策略 / 確認密碼一致 / name / 唯一性）皆通過後，呼叫後端 createUser 成功，使用者看到「Registration successful」/「帳號申請成功」訊息（showCheckYes 持久 modal），接著表單清空並切回 login 模式。此案例隱含涵蓋 E2E-018：測試環境 SMTP 為 placeholder pw 故寄信會失敗，但寄信失敗不阻擋註冊，仍走成功路徑。
  - flow:

    - 驗證（等待後端回傳並 modal 浮出後）：
      1. 語意：頁面含「Registration successful」/「帳號申請成功」訊息（System message modal）。
      2. 視覺：與 baseline `test/pics/register/register-{eng,cht}-E2E-005-success.png` 視覺一致（pixelmatch 容差）。

- **E2E-006**

    - 驗證（server-rendered HTML 載入後）：

> **架構備註**：驗證結果頁為 server-rendered HTML（白底簡潔），**不再 redirect 回 SPA 顯示彈窗**。
> - lang 端到端跟著驗證流程走（寄信時帶 ?lang=、API 收到後直接渲染對應語系），不依賴 SPA reload 後重新求 lang
> - 同時消除「任何人在網址列打 ?verified=ok 都會看到假驗證成功訊息」的 UX 缺陷
> - 使用者驗證後須自行回到登入頁登入（驗證連結可能在不同裝置開啟，無 auto-redirect 反而合理）

> **設計理由（lazy clear tokenVerify，F-053 fix / ADR-032）**：驗證成功時**只**寫 `timeVerified=now`，**不**清空 `tokenVerify`。
> - **race 情境**：使用者並行打 `verifyEmail`（舊 token）+ `resendVerifyEmail`（產生新 token 覆寫）時，若 `verifyEmail` 也清空 `tokenVerify`，會把 `resendVerifyEmail` 剛寫入的新 token 給覆蓋為空字串，導致新驗證信連結瞬間失效。
> - **修補**：改為 lazy clear——驗證成功僅更新 `timeVerified`，`tokenVerify` 留在欄位內當「歷史殘值」，不再參與正確性判定。
> - **舊 token 重用風險**：已驗證 user 點任何 verifyEmail 連結（含舊的、含 race 中倖存的），一律由 `isestr(timeVerified)` 判定攔截，reject `'verifyEmailAlreadyVerified'`，使用者得到友善訊息「This account has already been verified」/「此帳號已完成驗證」，不會誤觸發任何狀態變更。
> - **後果**：`users.tokenVerify` 欄位於已驗證帳號上可能非空（歷史殘值），但其值已無語意效果——所有後續查詢入口皆在 `timeVerified` 檢查處被攔下。新帳號狀態表內「點擊驗證連結後 tokenVerify=空」之欄位，因應 lazy clear 改記「不動（歷史殘值）」。

## 參數來源

本流程涉及以下執行期參數，**測試讀取順序：`settings.json` 覆寫值 > `server/WWebSso.mjs` opt 預設**：

| 概念 | 來源（優先序）| 測試影響 |
|---|---|---|
| 是否允許自助註冊 | `settings.json` `allowUserRegistration` → opt 預設 | 構造「系統不允許註冊」case 須設 false |
| 密碼策略（長度上下限 / 字元類要求 / 禁用字元 / 共用黑名單 / 與帳號連續字元門檻）| `settings.json` `passwordPolicy` → opt 預設 | 構造「密碼太短」case 須長度 < `minLength`；「黑名單」case 須挑 `commonPasswordBlacklist` 內值；「與帳號連續字元」case 須讓密碼與 account 有 ≥ `consecutiveCharsMinMatch` 字元連續子字串 |
| Email regex 格式 | hardcode `server/procCore.mjs` `createUser` 內 | 構造 invalid email 用無 `@` / 無 domain 字串 |
| 驗證信連結 base URL | `server/WWebSso.mjs` 計算為 `http://localhost:{serverPort}` | 測試環境連結 host 須對應 |
| 驗證信寄出 SMTP | `settings.json` `emSrc*` 系列 | SMTP 不通會等網路 timeout（測試須給寬鬆 timeout，~30s）|
| 鹽 salt | `settings.json` `salt` → opt 預設 | 比對 DB password hash 須用同 salt |
| Token 有效期 | `settings.json` `minExpired` → opt 預設 | 影響註冊後 login token / 驗證後 session 行為 |

實際數字 / 字元集 → 寫測試時讀 `settings.json` 對應 key，若無 → 讀 `server/WWebSso.mjs` opt 預設值。

## spec 規則摘要（粒度 / 邊界 / 順序 / 契約）

- **驗證順序**（註冊）：`allowUserRegistration` → account 非空 → email regex → 密碼 / 確認密碼一致 → `checkUserPassword` 策略 → name 非空 → cst.setWithFree 原子鎖（account / email 兩段獨立鎖）包覆 → 全表查唯一性（account / email）→ hash + 產生 tokenVerify → 寫入 users 表 → 寄驗證信。
- **驗證順序**（驗證信）：token 非空 → 對 `users.tokenVerify` 欄位查找對應使用者 → `timeVerified` 為空 → 寫入 `timeVerified=now`（**不動 `tokenVerify`**，lazy clear，F-053 fix；舊 token 重用由「已驗證 user 點任何 verifyEmail 連結一律 reject `'verifyEmailAlreadyVerified'`」攔截）→ 渲染 server HTML 結果頁。
- **驗證順序**（重寄）：account / email 非空 → kmx 序列化同帳號並行請求 → 30s throttle 檢查 → 查找 user → email 與帳號一致 → 未驗證 → 產生新 `tokenVerify` 覆寫 → 寄驗證信。
- **粒度**：
  - 註冊欄位驗證錯誤帶具體訊息（使用者已自填欄位，無列舉風險）。
  - 密碼策略違反帶**具體策略名**。
  - 重寄時帳號不存在 / email 與帳號不符 **共用同一 key 'userRegistrationResendInvalidEmail'**（防帳號列舉）；30s 內再寄 → 'userRegistrationResendThrottled'；已驗證 → 'userRegistrationAlreadyVerified'；寄信失敗 → 'userRegistrationResendFailed'；各自具體訊息。
- **訊息呈現方式**（全專案共識）：操作結果（註冊成功 / 重寄成功）一律走 `$dg.showCheckYes` 持久 System message modal（須點 OK 確認）；非預期錯誤（外層 `core().catch` 接住的例外 / 漏接 reject）才走 `$alert` toast（低調呈現，避免過度放大）；欄位驗證 / 後端可預期 reject 走 inline 紅字（`regError` / `resendError` / `loginError`），不彈窗。
- **邊界**：
  - 寄驗證信失敗**不阻擋註冊**（使用者可透過重寄機制補救）。
  - 唯一性檢查 + insert 被 `cst.setWithFree([createUser:account:<a>, createUser:email:<e>])` 兩段獨立原子鎖包覆，防同 account 不同 email 或不同 account 同 email 並行雙重 insert；`cst` 為 wsemi `cacheSt()` 實例（多 key 原子占位 + TTL auto-cleanup），衝突時 remap 回 `userRegistrationAccountExists` / `userRegistrationEmailExists`。
  - `tokenVerify` 存於 `users.tokenVerify` 欄位，**非獨立 tokens 表**；故無「刪除舊驗證 token」步驟，直接 overwrite 即視為失效。
  - 驗證結果頁為 **server-rendered HTML**（不 redirect 回 SPA），消除「網址列打 ?verified=ok 顯示假驗證」缺陷。
  - 自助註冊強制 `isAdmin='n'`、`timeVerified=''`、需驗證；後台建帳可指定 `isAdmin`、`timeVerified=now`、不寄驗證信。
- **契約**：
  - 驗證連結含 `?lang=` 參數，端到端不依賴 SPA reload 重新求 lang。
  - 自助 vs 後台建帳的狀態差異：自助 timeVerified 為空、isAdmin='n'、須驗證；後台建帳 timeVerified=now、isAdmin 可設、不寄驗證信。
  - 重寄驗證信 overwrite `tokenVerify`，舊連結立即失效（後端查 `tokenVerify` 落空 → reject 'verifyEmailInvalidToken'）。
  - password 加鹽雜湊後寫入；驗證信標題由 i18n key 控制、body 由 `server/template/regVerifyEmail-{eng,cht}.html` 控制。
