# 後台重設使用者密碼流程

> **設計策略**：管理員直接產生符合策略之隨機密碼塞給使用者，**不走 reset 連結機制**、**不限時**。改以 `users.isForceChangePw='y'` 旗標強制使用者下次登入後立即變更為自訂密碼。

## 觸發

管理員於 LayoutContentUsers.vue 後台 Users list 對某使用者點擊「Reset password」按鈕。

## 重要流程

- **E2E-001**
  - title: 管理員點 Reset password 開啟確認 modal
  - description: 驗證管理員登入後台、進入 Users list 並開啟 Edit mode 後，對某目標使用者列點擊「Reset password」按鈕，前端應彈出 CheckYesNo 二次確認 modal，內容顯示針對該目標 account 之確認句。此案例為「管理員觸發重設」流程鏈第 1 段，後續 E2E-002 點 No、E2E-003 點 Yes 共用本案例所建立之 admin / target user。modal 文字遵循 spec i18n 粒度規則，雙語顯示目標 account 名。
  - flow:
    - 測試資料：admin user `id-rp-admin`（`isAdmin='y'` / `redir` 指 `?view=backstage`）+ target user `id-rp-target-{lang}`（`isAdmin='n'` / `redir` 指 `?view=user`）+ 其他 base seed。
    - 操作：admin 開乾淨登入頁 → 輸入 admin 帳密 → 點「Log in」/「登入」→ 進後台 → 點「Users list」/「使用者清單」→ 開啟 Edit mode → 於 target 列點「Reset password」/「重設密碼」按鈕。
    - 驗證（等待 CheckYesNo modal 出現後）：
      1. 語意：DOM 含 eng「Confirm to reset password for」/ cht「確定對」。
      2. 視覺：與 baseline `test/pics/resetpassword/resetpassword-{eng,cht}-E2E-001-admin-ui-modal-opened.png` 視覺一致（pixelmatch 容差）。
    - 雙語：eng / cht 各一輪。
    - 清理：admin / target 等本檔特化 user 由本 describe block 結束後統一移除（admin UI 觸發鏈條 E2E-001 / E2E-002 / E2E-003 / E2E-004 共用同一 before/after 生命週期），保留 base seed。

- **E2E-002**
  - title: 點 No 取消後 modal 關閉且 DB 不變
  - description: 驗證接續 E2E-001 之 CheckYesNo modal 開啟態，使用者點擊「No」/「否」按鈕後，modal 應正常關閉、target user 之 password 與 isForceChangePw 在 DB 內維持不變，且 console 內無 unhandled rejection。本案例為「管理員觸發重設」流程鏈第 2 段，驗證取消路徑之完整 cleanup 行為，沿用 E2E-001 之 admin 登入態與目標 target user。
  - flow:
    - 測試資料：承接 E2E-001 之 admin user `id-rp-admin` + target user `id-rp-target-{lang}`（password / isForceChangePw 記錄為起點 snapshot）。
    - 操作：開啟未捕捉拒絕事件偵測 → 於 target 列再次點「Reset password」/「重設密碼」開啟 modal → 點「No」/「否」。
    - 驗證（等待 modal 關閉動畫完成後）：
      1. 語意：DOM 不再含 eng「Confirm to reset password for」/ cht「確定對」；window 內捕捉之 unhandled rejection 清單為空。
      2. DB：target 之 password 與 isForceChangePw 與 modal 開啟前 snapshot 相同。
      3. 視覺：與 baseline `test/pics/resetpassword/resetpassword-{eng,cht}-E2E-002-admin-ui-cancel-clean.png` 視覺一致（pixelmatch 容差）。
    - 雙語：eng / cht 各一輪。
    - 清理：由 admin UI 觸發鏈條 describe 結束後統一移除特化 user，保留 base seed。

### 一、管理員觸發重設

## 參數來源

本流程涉及以下執行期參數，**測試讀取順序：`settings.json` 覆寫值 > `server/WWebSso.mjs` opt 預設**：

| 概念 | 來源（優先序）| 測試影響 |
|---|---|---|
| 密碼策略（長度上下限 / 字元類要求 / 禁用字元 / 共用黑名單 / 與帳號連續字元門檻）| `settings.json` `passwordPolicy` → opt 預設 | `genRandomPassword` 依此產出符合策略密碼；構造強制變更失敗 case 須對應 |
| 隨機密碼目標長度公式 | hardcode `server/genRandomPassword.mjs` 內 | 測試驗 length 須讀該檔頂部變數 |
| 隨機密碼 special 字元池與排除字元 | hardcode `server/genRandomPassword.mjs` 內，並再依 `passwordPolicy.forbiddenChars` 過濾 | 測試驗 specials 須讀該檔頂部變數 |
| 隨機密碼生成嘗試上限 | hardcode `server/genRandomPassword.mjs` 內 | 測試「policy 設定不合理拋錯」case 用 |
| 鹽 salt | `settings.json` `salt` → opt 預設 | 比對 reset 後 password hash 須用同 salt |
| Email 寄信設定（SMTP）| `settings.json` `emSrc*` 系列 | SMTP 不通會等網路 timeout（測試須給寬鬆 timeout，~30s），且寄信失敗不阻擋 reset 結果 |

## 安全性考量

| 項目 | 規則（spec）|
|---|---|
| 信件含明文新密碼 | 採此設計取代 reset 連結；緩解措施為強制使用者首次登入後變更密碼 |
| 隨機密碼強度 | 由 `genRandomPassword` 產生符合 `passwordPolicy` 的密碼 |
| 不限時 | reset 流程無 token / 無連結，故無限時概念；`isForceChangePw='y'` 為常駐旗標直到使用者完成變更 |
| Admin 對自己重設 | 後端 reject i18n key `adminResetPasswordCannotResetSelf`，避免自我鎖死 |
| 一般使用者呼叫 API | 後端 reject i18n key `adminResetPasswordForbidden`，須 admin 權限 |
| 多裝置 token 不清除 | admin reset **不主動清** 該 user 所有 tokens（**已知 trade-off**：若疑似被盜需 admin 額外手動清除）|
| 密碼不記錄 log | srLog 僅記錄 event / userId，**不記錄 newPassword 明文** |
| 操作者不知道密碼 | 後端不回傳明文密碼給前端 API 回應 |
| 強制變更頁面不可繞過 | UX 設計「取消」按鈕**直接隱藏**，使用者要離開只能 logout；再次登入仍被拉回強制變更頁直到完成 |

## spec 規則摘要（粒度 / 邊界 / 順序 / 契約）

- **驗證順序**（admin 觸發）：WWebSso `_strictStr(token, targetUserId)` 前置檢查（空即 reject `tokenExpired`）→ `checkToken` → `isAdmin='y'`（非 admin reject `adminResetPasswordForbidden`）→ 操作者 ≠ 目標（reject `adminResetPasswordCannotResetSelf`）→ **進入 `kmx(adminResetUserPassword:${targetUserId})` 序列化** → **mutex 內第一檢 30s throttle**（命中即 reject `adminResetPasswordAlreadyTriggered`，不走完整 reset）→ user 存在（查無 reject `adminResetPasswordUserNotFound`）→ 產生符合策略隨機密碼 → hash → save（含 `isForceChangePw='y'`）→ 寫入 throttle 時間戳 → 寄信。
- **驗證順序**（使用者收信並登入後）：正常登入路徑 → 前端檢查 `userSelf.isForceChangePw='y'` → 不執行 redir → CheckYes 提示 → 進入 user view → PageUser mounted 自動展開變更密碼表單。
- **粒度**：
  - API 拒絕訊息（`adminResetPasswordForbidden` / `adminResetPasswordUserNotFound` / `adminResetPasswordCannotResetSelf`）**各自具體 i18n key**（後台對 admin 顯示，前端 `$tErr` 翻譯，不需混淆統一訊息）。
  - 強制變更模式下變更密碼錯誤訊息**沿用變更密碼流程的 i18n 規則**（後端 reject 統一「變更失敗」）。
- **邊界**：
  - 信件**不含任何連結**、**僅含明文新密碼 + 帳號**（避免 phishing 與 reset 連結攻擊面）。
  - 寄信失敗**不阻擋 reset 結果**（密碼已 save，由 admin 另外通知使用者）。
  - **不限時**：reset 流程無 token / 無連結，`isForceChangePw='y'` 為常駐旗標直到使用者完成變更。
  - **多裝置既有 token 不清除**（trade-off：simplicity；若疑似被盜需 admin 另外手動清）。
  - 強制變更頁「取消」按鈕**直接隱藏**，使用者要離開只能 logout；再次登入仍被拉回強制變更頁。
- **契約**：
  - 後端**不回傳明文新密碼**給前端 API（操作者不知道密碼）。
  - `srLog` 僅記錄 event / userId，**不記錄 newPassword 明文**。
  - 強制變更完成後後端清 `isForceChangePw='n'`（與變更密碼流程共用 save 路徑）。
  - 隨機密碼產生器（`server/genRandomPassword.mjs`）依 `passwordPolicy` 產出符合策略密碼；嘗試上限內仍失敗則 throw。
  - Email 文字來源：settings `resetPwEmTitle` / `resetPwEmContent`（各值可給文字或檔案路徑）優先；未給採內建語系文字（`server/procLang.mjs` 同名鍵），placeholder 由 `procCore.renderEmailText` 代入。
- **ADR-033 雙擊防護分層**（對齊 ADR-033 / ADR-031 此流程之 race 修補 ADR / ADR-030 單機假設）：本流程之 reset 觸發具元件層與後端層分層防護，缺一不可：
  - **元件層**（前端 UI）：`LayoutContentUsers.vue` Reset password 按鈕（`WButtonChip`）用 `:promiseUnlock="true"`，使用者快速雙擊時第二次點擊在第一次 promise 解決前不再觸發 handler，防 modal-before-loading 空窗。  [src/components/LayoutContentUsers.vue:221-238]
  - **後端層**（API 序列化 + throttle）：`procCore.mjs` `adminResetUserPassword` 以 `kmx(adminResetUserPassword:${targetUserId})` 序列化同 user 之並行請求，並於 mutex 內第一行做 30s throttle（`lastResetTime` Map），防 API 直打繞過元件層、雙 admin 同時觸發、單 admin 30s 內第 2 次觸發。  [server/procCore.mjs:1248-1255]
  - **race 防護後果**：同 targetUserId 30s 內第 2 次（不論單一 admin 雙擊或兩 admin 並行）一律 reject `adminResetPasswordAlreadyTriggered`（i18n key，前端 `$tErr` 翻譯），不寫第二份隨機密碼、不寄第二封信。並行 race 之 e2e 驗證見 `test/api-doubleclick.test.mjs` `E2E-DC-01`（對應雙擊調研 DC-01 議題）。
