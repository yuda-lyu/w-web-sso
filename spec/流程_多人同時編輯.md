# 後台多人同時編輯流程(使用者清單 / 金鑰清單 / IP 清單)

## 觸發

多位管理員同時開啟後台「Users list」、「Tokens list」、「Ips list」,其中一位在別人載入之後已改了資料(另一位管理員存檔、app 權杖直呼、使用者自助註冊 / 登入 / 登出、系統自動封鎖、計時器登錄新 IP 等),持有舊畫面者再按 Save。上位原則 `C:\opensrcOper\sgud\proc\process_principle.md` 第 10 條,跨套件規格 `C:\opensrcOper\dspec\多人同時編輯之寫入契約.md`;本套件規則帳本 `sgud/rule/rulebook_concurrency.md`(R-CONC-01~05)、設計決策 `spec/設計要點與取捨.md` ADR-091。

本檔描述三個清單頁共通之「舊畫面存檔」使用者可見行為;各清單之儲存主流程見 `流程_後台IP清單.md`、`流程_後台金鑰清單.md`、`流程_後台新增使用者.md`、`流程_後台變更使用者資訊.md`、`流程_後台刪除使用者.md`。無推播 / 輪詢重建(`tableNamesSync: []`),故不需草稿凍結,不適用規格 V11。

## 重要流程

- **E2E-CC-001**
  - title: 管理員以舊畫面儲存使用者清單被整次拒收
  - description: 驗證兩位管理員同時開著使用者清單時,其中一位在另一人更動資料之後才按 Save:後端於表鎖內重新讀取並比對載入時的基準,資料已被更動即整次拒收、不寫入任何變更,前端彈出 System message 持久 modal,內容為儲存失敗前綴(`userSaveUsersFail`)後接「資料自您載入後已被其他使用者或系統更動…請重新載入頁面後再操作」(`saveStale`);管理員點 OK 後草稿仍保留(改過的格仍在、Save 按鈕仍在),重新載入清單後可見他人之更動,重改同一格即可儲存成功,且不重新載入、再改另一格也能連續儲存成功(存檔成功後新基準取自伺服端)。
  - flow:
    - 測試資料:admin user + 其有效 admin token;另 seed 兩位使用者(`cc-ua`、`cc-ub`);審計時間欄固定(避免全頁截圖含浮動時間)。
    - 操作:以預填之 admin token 自動登入後台 → 點「Users list」/「使用者清單」→ 確認編輯模式 → 雙擊 `cc-ua` 列之 `name` 欄改為 `CC UserA Edited` → Enter(Save 出現)→ (他人於此時直接更動庫內 `cc-ub` 之 `name`)→ 點 Save。
    - 驗證:
      1. 語意:出現含「Failed to save users」/「儲存使用者數據失敗」與 `saveStale` 文字之 System message modal;庫內 `cc-ua` 之 `name` 維持原值、`cc-ub` 之更動維持(零寫入)。
      2. 視覺:與 baseline `test/pics/concurrency/concurrency-{eng,cht}-E2E-CC-001-1-stale-save-rejected-modal.png` 視覺一致(pixelmatch 容差);觀看區為 modal panel 紅框標注。
      3. 關閉 modal 後:改過的 `name` 格仍顯示 `CC UserA Edited`、Save 按鈕仍在(草稿保留)。
      4. 重新載入清單(再進一次後台)後見到 `Changed By Other Admin`;重改 `cc-ua` 之 `name` 並 Save → 出現「Save users successfully」/「儲存使用者數據成功」,庫內已更新。
      5. 不重新載入,改 `cc-ub` 之 `name` 再 Save → 再次成功(驗證瀏覽器端 `buildBaseline` 與伺服端所算相同,V10)。
    - 雙語:eng / cht 各一輪。
    - 清理:移除本檔特化資料,保留 base seed。

- **E2E-CC-002**
  - title: 管理員以舊畫面儲存金鑰清單被整次拒收
  - description: 同 E2E-CC-001,對象為金鑰清單(應用系統金鑰列採嚴格整表比對、session 列採逐列寬鬆比對);失敗前綴為 `tokenSaveTokensFail`,成功訊息為 `tokenSaveTokensSuccess`。
  - flow:
    - 測試資料:admin user + token;另 seed 兩支應用系統金鑰(`cc-token-app1`、`cc-token-app2`)與一支 session 金鑰。
    - 操作:自動登入 → 點「Tokens list」/「金鑰清單」→ 雙擊 `cc-token-app1` 列之 `token` 欄改為 `cc-token-app1-edited` → Enter → (他人直接把庫內 `cc-token-app2` 之 `token` 改為 `cc-token-app2-ext`)→ 點 Save。
    - 驗證:同 E2E-CC-001(語意、視覺、草稿保留、重新載入後見 `cc-token-app2-ext`、重改成功、不重載連續第二次成功)。視覺 baseline `concurrency-{eng,cht}-E2E-CC-002-1-stale-save-rejected-modal.png`。
    - 雙語:eng / cht 各一輪。
    - 清理:同 E2E-CC-001。

- **E2E-CC-003**
  - title: 管理員以舊畫面儲存 IP 清單被整次拒收
  - description: 同 E2E-CC-001,對象為 IP 清單;失敗前綴為 `ipSaveIpsFail`,成功訊息為 `ipSaveIpsSuccess`。
  - flow:
    - 測試資料:admin user + token;另 seed 三筆 IP(`10.1.0.1`~`10.1.0.3`,固定 `timeBlocked`)。
    - 操作:自動登入 → 點「Ips list」/「IP清單」→ 雙擊 `10.1.0.1` 列之 `ip` 欄改為 `10.1.0.91` → Enter → (他人直接把庫內 `id-cc-ip2` 之 `ip` 改為 `10.1.0.92`)→ 點 Save。
    - 驗證:同 E2E-CC-001。視覺 baseline `concurrency-{eng,cht}-E2E-CC-003-1-stale-save-rejected-modal.png`。
    - 雙語:eng / cht 各一輪。
    - 清理:同 E2E-CC-001。

## 執行流程

```
001  管理員載入清單: getUsersList / getTokensList / getIpsList  [LayoutContent{Users,Tokens,Ips}.vue mounted]
002      前端以畫面所見之同一份回傳列自算基準 buildBaseline(rows, 契約)  [src/baselineOf.mjs; 契約 src/writeContracts/{users,tokens,tokensSession,ips}.mjs]
003          users / ips: 有序 [[id, 列摘要]]; tokens: baseline(app 列)與 baselineSession(session 列)兩份
004  管理員按 Save → 呼叫 updateUsersList / updateTokensList / updateIpsList(token, lang, rows, 基準物件)  [kpfun, WWebSso.mjs]
005      checkToken(權限閘) → lockSave(同操作者雙擊防護, 外層)  [procCore.mjs checkTokenAndUpdate*List]
006          parseSaveOpt: 第 4 參數須為純物件且只含白名單鍵、格式 / 版本合法, 否則 reject saveBaselineFormat(不降級為不帶基準)  [procCore.mjs parseSaveOpt]
007          取表鎖(users 為 [tokens, users]; tokens; ips)並新鮮讀取  [procCore.mjs updateTabItems → w-serv-orm guardWrite]
008              比對基準: 相符才往下; 不符整次 reject → saveStale / saveRowNotFound(零寫入, 記 warn)
009              tokens 另對 session 列做逐列寬鬆比對(只比管理員有改或刪之列; 管理員有動而庫內已變 → saveStale)
010              驗證依賴庫內之項(帳號唯一、新增列已存在、perms 合法)→ 算 diff(刪除集合 = 基準內 − 送出; 修改 = 摘要 ≠ 庫內) → 只寫契約欄位 → 撤銷 token → 清快取  [同一把鎖內]
011  前端: 有 reject → 失敗 modal(前綴 + 語系鍵文字), 草稿保留; 成功 → 重新取清單作為新基準  [LayoutContent*.vue saveXxx]
```

## i18n 訊息粒度規則

| 觸發情境 | i18n 鍵(grep `server/procLang.mjs`) | 顯示元件 | 規則 |
|---|---|---|---|
| 載入後資料已被他人或系統更動(基準不符) | 各清單失敗前綴(`userSaveUsersFail` / `tokenSaveTokensFail` / `ipSaveIpsFail`)接 `saveStale`(「The data has been changed by another user or the system since you loaded this page. Nothing was saved. Please reload the page and make your changes again.」/「資料自您載入後已被其他使用者或系統更動，本次未儲存任何變更，請重新載入頁面後再操作」) | `showCheckYes` 持久 modal | 整次拒收、零寫入、草稿保留、提示重新載入 |
| 要修改或刪除之資料已不存在 | 同前綴接 `saveRowNotFound`(「Some of the data no longer exists (it may have been deleted by another user). Nothing was saved. …」/「部分資料已不存在（可能已被其他使用者刪除），本次未儲存任何變更，請重新載入頁面後再操作」) | 同上 | 現行 UI 路徑多由 `saveStale` 先行涵蓋(整表比對); 本鍵為契約拒收鍵之對應 |
| 基準格式或版本不識(含算不出基準送 null) | 同前綴接 `saveBaselineFormat`(「The page data version is not recognized. Nothing was saved. …」/「頁面資料版本無法辨識，本次未儲存任何變更，請重新載入頁面後再操作」) | 同上 | 不降級為不帶基準; 前端重新讀取失敗時基準置 null 即走此訊息 |
| 庫內讀出之列主鍵重複或缺漏(`rowsInvalid`, 伺服端資料錯誤) | 同前綴接 `anUnexpectedErrorOccurred` | 同上 | 重新載入無法解決; srLog 記 error |
| 儲存成功 | `userSaveUsersSuccess` / `tokenSaveTokensSuccess` / `ipSaveIpsSuccess` | `showCheckYes` 持久 modal | 成功後前端重新讀取清單作為新基準 |

## spec 規則摘要

- **先動先贏、不部分變更**:基準比對於表鎖內以新鮮讀取進行,不符整次拒收(零寫入); 不逐列判斷哪些可蓋。
- **刪除集合 = 基準內(且在範圍內)− 送出**; 載入後他人新增之使用者 / IP / session 金鑰不被刪。
- **雙方欄位入基準**(`timeVerified`、`timeBlocked`、`isForceChangePw`、金鑰 `timeEnd`、IP `timeBlocked`): 系統於載入後改動它們,持舊畫面者存檔即被拒; 伺服器專有欄位(`password`、`tokenVerify`、`userId`、`timeCreate`、稽核欄、金鑰 `timeUpdate`)不入基準、存檔取庫內值。
- **使用者清單之列序**: 以名次入基準(他人重排被偵測; 系統重編號而名次不變不誤擋); 自助註冊之使用者 `order` 為空字串,排在有數值者之後。
- **金鑰清單(選項 P)**: 應用系統金鑰列嚴格整表比對; session 列逐列寬鬆比對——載入後新登入者不刪、已登出或被封鎖撤銷者不復活、系統續期而管理員未動者不寫、管理員刪除或修改一個剛被續期之 session 時整次拒收(重新載入後再操作)。
- **不帶基準**(app 權杖直呼、升級前已開啟之舊版頁面)本 major 允許,後者蓋前者,但仍取表鎖、只改不增、伺服器專有欄位不採用客戶端值; 金鑰清單只刪 / 改應用系統金鑰列。下一個 major 起後台必帶基準。
- **前端**: 基準以畫面所見之同一快照自算,不另向後端取雜湊; 存檔成功後以重新讀取之列為新基準(送出列與伺服端列契約摘要相同者保留現畫面,不同者改以伺服端列取代)。
- **IP 清單之特性**: 自動偵測計時器每 2 秒登錄新 IP、自動封鎖寫 `timeBlocked`,繁忙系統上舊畫面存檔較常被拒——符合先動先贏,使用者重新載入後再存。

## 已知落差

- **設計事實(記錄備查,2026-10-23)**: 金鑰清單不帶基準時,session 列不刪、不以送入值覆蓋(主控 2026-10-22 採選項 P 配套, D3): 直打 API 以 app 權杖強制登出某 session 不再可行(後台頁帶基準之路徑不受影響)。依據 `sgud/rule/rulebook_concurrency.md` R-CONC-03; 證據 `test/unit-saveBaseline.test.mjs` SB-T10。
- **設計事實(記錄備查,2026-10-23)**: 金鑰清單帶基準、管理員刪除或修改一個於載入後被續期之 session 列時整次拒收(「管理員有動且庫內已變者拒收」),需重新載入後再操作; 現行前端不自動續期(Layout 之 refreshToken 呼叫已註解),僅 API 端續期會觸發。證據 SB-T05 / SB-T06。
- **待實測回填**: 無。
