# 後台變更使用者資訊流程

## 觸發

管理員於 LayoutContentUsers.vue 後台 Users list 對既有列就地修改 account / name / email / description / from / redir 等文字欄位，切換 isAdmin / isActive 勾選，調整 timeVerified / timeExpired / timeBlocked 時間欄位，或拖拉列改變順序，再點「儲存」批次提交至後端。

## 重要流程

- **E2E-001**
  - title: 管理員修改既有列欄位儲存成功
  - description: 驗證管理員於後台 Users list 對既有列（target）就地修改 name 欄位後點儲存，後端正確處理 audit 欄位與 password hash 保留之契約：既有 password hash 由後端在 ltdtDiffByKey 前還原回 row 不被前端送回的空字串洗掉；userIdUpdate 與 timeUpdate 由 procOrm save 自動覆寫為操作者 id 與 now；userId 與 timeCreate 保留原值；儲存成功後前端緊接重拉 getUsersList 同步表格。本案例為流程主成功路徑之 baseline 案例，target 使用者於本檔範圍內保留供後續欄位驗證案例使用。
  - flow:
    - 測試資料：admin user `id-mu-admin`（帳號 `mu-admin` / 密碼 `Pw@muadmin1` / `isAdmin='y'` / `isActive='y'`）+ target user `id-mu-target`（帳號 `mu-target` / `name='Modify Target'` / `email='mu-target@test.com'` / `isAdmin='n'` / 預先設定 `timeBlocked='2030-06-01...'` 視為封鎖中 / 持有效未來 60 分鐘 admin token）。
    - 操作：以 admin token 進入後台 Users list 並切到編輯模式 → 於 target 列 name cell 雙擊啟動 editor → 改值為 `Modified Target` → 點「Save」/「儲存」按鈕。
    - 驗證（等待 Save 後 success modal 出現）：
      1. 語意：DB target user `name` 已變為 `Modified Target`；`userIdUpdate` 等於 admin.id；`timeUpdate` 非空字串（被後端覆寫為 now）；`password` 欄位仍為原 hash（未被前端空字串洗掉）。
      2. 視覺（多階段，數字前綴使檔名排序即階段順序）：
         - stage1 與 baseline `test/pics/modifyuser/modifyuser-{eng,cht}-E2E-001-1-save-success-modal.png` 視覺一致（pixelmatch 容差）——觀察點為儲存成功 modal（綠勾）畫面，於按確認鈕關閉之前截取。
         - stage2 與 baseline `test/pics/modifyuser/modifyuser-{eng,cht}-E2E-001-2-after-save-modify-name.png` 視覺一致（pixelmatch 容差）——觀察點為關閉 modal、表格重拉後 target 那一列，name 已顯示為 `Modified Target`。
    - 雙語：eng / cht 各一輪。
    - 清理：移除本檔特化 admin/target user 與 admin token，保留 base seed。

## 執行流程

### 一、就地編輯欄位（資料表 cell-render）

```
account / email / redir / name / description / from
    aggrid 內建 cell editor 直接輸入文字 (kpCellEditable 定義);
    cell 顯示警告 icon 表示有 errItemsBy* 偵測到錯誤;
    輸入完成 → rowsChange → vo.isModified=true

password
    顯示為「重設密碼」按鈕, 不接受就地輸入

isAdmin / isActive
    checkbox 形式; click 走 $dg.toggleItemIsAdminById / toggleItemIsActiveById
        → toggleItemByKeyAndId(key, id) 切 'y' / 'n', set 至 opt.rows[kr].<key>
        → vo.refresh() 觸發 cell 重渲染, vo.isModified=true

timeVerified / timeExpired / timeBlocked
    左側狀態指示器顯示 isVerified / isExpired / isBlocked (綠勾 / 紅叉) 反映目前 row 狀態;
    右側 WTimeminute 日期時間選擇器 @input → handleCellTimeInput(key, id, timeNew)
        → 解析後以 timemsTZ 格式寫回 row 對應欄位
        → vo.refresh(), vo.isModified=true

順序
    account 欄啟用 kpRowDrag.account=true, 可拖拉列調整 opt.rows 順序;
    觸發 rowsChange → vo.isModified=true
```

### 二、即時前端驗證（computed）

前端 computed 對每列做粒度驗證，產生 cell 警告 icon + tooltip，並聚合為 `isError` 字串供 saveUsers 攔截。粒度規則詳「i18n 訊息粒度規則」章節。

```
errItemsByAccount   每列檢查 account 空值與同表重複, 寫入 kpErr[<value>] = 對應錯誤訊息
errItemsByEmail     每列檢查 email 空值 / isEmail 格式 / 同表重複
errItemsByRedir     只檢查「管理員本次新增之列」與「redir 由非空改為空之既有列」, 鍵為列主鍵 id (cellRedirErr(id));
                    載入時 redir 即為空之既有列(自助註冊者)不檢查、不標警示 (2026-10-23, R-VAL-02 / ADR-094;
                    〔原載「每列檢查 redir 空值, 寫入 kpErr[<value>]」: 載入時即為空之列會擋住整份清單存檔, 且空值為鍵使所有空 redir 儲存格同時標警示〕)

isError computed（整體錯誤訊息, 第一層攔截）
    依序取 errItemsByAccount → errItemsByPassword → errItemsByEmail → errItemsByRedir
    第一條具體錯誤訊息 (cell tooltip 級訊息, 非 category title);
    cellFieldErr 在 cell 顯示警告 icon + tooltip 細節錯誤
```

## spec 規則摘要（粒度 / 邊界 / 順序 / 契約）

- **多人同時編輯**（2026-10-23，原則 10；共通規則與案例見 `流程_多人同時編輯.md`）：後者蓋前者僅限「看著最新資料改」者；持舊畫面存檔整次拒收。系統於載入後改動之雙方欄位（`timeVerified` 驗證信、`timeBlocked` 自動封鎖、`isForceChangePw` 重設密碼）使持舊畫面者存檔被拒，不再被舊值蓋回（修正）；系統寫入之伺服器專有欄位（密碼雜湊、`tokenVerify`）不被客戶端舊值回寫（修正）；拖曳重排以名次入基準（他人重排被偵測，系統重編號而名次不變不誤擋）。
- **驗證順序**：前端 computed `errItemsBy*` → 前端 `isError` 聚合攔截 → 前端自我鎖死保護 → 後端 `checkToken`（含 funCheckAdmin）→ 後端 `checkTokenAndUpdateUsersList` 自我鎖死保護 → 列格式（rows 為陣列；id 非空、不重複、不超過鍵長上限 → `invalidRows`）→ email 非空、不重複（`userEmailEmpty` / `userEmailDuplicate`）→ account 必填 + 全域唯一性驗證（reject `accountRequired` / `accountDuplicate`）→ 新增 / 修改列之欄位值會被 clearXSS 改寫（`htmlMarkupNotAllowed`）→ procOrm save 寫入。任一層 reject 即整批不落地（ADR-021 / ADR-081）。
- **粒度**：account / email 「空」與「重複」分開告知；token 失效與身分不足共用同一訊息（不洩露身分檢查）；前後端攔截訊息一致。
- **一列之既有資料問題不得擋住整份清單之存檔**（2026-10-23，原則 3；R-VAL-02、ADR-094）：redir 檢查只攔管理員本次輸入造成之空值（新增列、非空改為空），不攔載入時即存在之空值（自助註冊者）；比對基準取自與畫面同一快照（載入、存檔成功後重讀），基準算不出或列不在基準內者一律嚴格檢查。
- **邊界**：
  - password 不可由本流程修改（顯示為「重設密碼」按鈕，不接受就地輸入）。後端 saveUsers 在 ltdtDiffByKey 前以 DB 既有 hash 還原 row.password，避免前端送回空字串把 DB hash 洗掉。
  - 自我鎖死保護：rows 內若包含操作者本人，不可將自己 `isAdmin` 或 `isActive` 改為非 'y'（前端 + 後端兩道）。
  - userId / timeCreate 保留原值，不被覆寫；userIdUpdate / timeUpdate 由 procOrm save 自動覆寫為操作者 id 與 now（audit 不接受前端送來的值）。
- **契約**：
  - `updateUsersList` 走批次 upsert：整表 `ltdtDiffByKey` 一次同步 add / diff / del，任一驗證錯誤即整批不落地。即使 admin 只改一列，ckKey 仍對全表掃描。
  - 拖拉列順序變動 → 後端 `resetOrder=true` 依陣列順序重指派 order=k+1，前端送回的 order 值被覆寫；一次拖拉可能讓多列同時進入 diff 群組。
  - 儲存成功後立即重拉 `getUsersList` 同步 audit fields 與 order。
  - API 回傳前剝除 password 欄位，避免 hash 從 API 流出。
  - token 不因 user 資料更新而失效（token 表獨立，不級聯）；唯停用（isActive 改為 'n'）時即撤銷其名下全部令牌，被停用者之既有登入隨即失效，寫入失敗亦撤（ADR-037 / ADR-080，`test/api-deleteuser.test.mjs` API-003）。**撤銷範圍（2026-10-24，ADR-095）**：登入權杖與綁定該使用者之使用者用途金鑰（刪列，重新啟用不恢復，須重新核發）；系統服務用途金鑰不撤銷；使用者被封鎖、帳號到期、未驗證時金鑰不刪列，僅即時不可用、恢復後可用。另：使用者清單新增列之主鍵不得以 `app:` 開頭（保留給應用系統身分，`invalidRows`）。
  - 寫入階段（驗證全過後）失敗即回 `saveWriteFail`，已寫入之列不回滾；撤銷與清除清單快取不論寫入成敗皆執行（ADR-080）。
- **送出入口與連按**（ADR-074）：「儲存」鈕（WButtonCircle，`:promiseUnlock="true"`）之按鈕鎖交給 `runSubmit('saveUsers')`，於請求結束時釋放；流程自觸發至結果訊息框關閉，期間滑鼠或焦點在鈕上之鍵盤 Enter 再觸發即略過。後端以「updateUsersList:操作者 id」占位，同一操作者處理中再送出回 `saveInProgress`、不寫入。

## 已知落差

每條帶分類標籤（缺陷（待修）／設計事實（記錄備查）／待裁示（業主決定）／已修復（附修復紀錄））；修復後不刪、改標已修復。
