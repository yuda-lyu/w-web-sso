# 後台新增使用者流程

## 觸發

管理員於 LayoutContentUsers.vue 後台 Users list 點擊「新增」按鈕，於資料表中插入一筆空白列就地填寫帳號 / 密碼 / 姓名 / Email / Redir 等欄位，再點「儲存」批次提交至後端。

## 重要流程

> 編號規則:
> - `**E2E-NNN**`: UI baseline 測試, 對應 `test/e2e-adduser.test.mjs` + `test/pics/adduser/adduser-{lang}-E2E-NNN-*.png`
> - `**API-NNN**`: 後端契約測試, 對應 `test/api-adduser.test.mjs` (含 password-* / self-lockout-* / happy-path / existing-row-password-preserved)
> - `**API-NNN(待補)**`: 編號預留, 尚無 e2e 待未來補

- **E2E-001** 管理員於後台點新增, 填妥帳號/密碼/姓名/email/redir, 儲存成功（timeVerified 自動填 now, password 經 hash 寫入 DB; 儲存成功後前端緊接重拉 getUsersList, 表格刷新顯示後端寫入的 timeVerified=now、userId/userIdUpdate=操作者 id、order 重排等）
- **E2E-002** 管理員於後台點新增, 但點「儲存」前帳號為空, 前端 isError 攔下無法儲存
- **E2E-003** 管理員於後台點新增, 但點「儲存」前帳號與表中其他列重複, 前端 isError 攔下無法儲存
- **E2E-004** 管理員於後台點新增, 但點「儲存」前密碼為空, 前端 isError 攔下無法儲存
- **E2E-005** 管理員於後台點新增, 但點「儲存」前 email 為空, 前端 isError 攔下無法儲存
- **E2E-006** 管理員於後台點新增, 但點「儲存」前 email 格式錯, 前端 isError 攔下無法儲存
- **E2E-007** 管理員於後台點新增, 但點「儲存」前 email 同表內重複, 前端 isError 攔下無法儲存
- **E2E-008** 管理員於後台點新增, 但點「儲存」前 redir 為空, 前端 isError 攔下無法儲存
- **E2E-009** 管理員於後台點新增, 但 rows 整張表為空（極少見：刪光所有列再儲存）, 前端以 CheckYes modal 顯示對應訊息後不送出
- **E2E-010** 管理員於後台儲存時, 把自己列的 isAdmin 由 'y' 改為 'n', 前端以 CheckYes modal 顯示「不可解除自己 admin 權限」之語系化訊息並不送出（後端為第二道防線同條訊息 reject）
- **E2E-011** 管理員於後台儲存時, 把自己列的 isActive 由 'y' 改為 'n', 前端以 CheckYes modal 顯示「不可停用自己帳號」之語系化訊息並不送出（後端為第二道防線同條訊息 reject）
- **E2E-012** 管理員於後台點新增, 但點「儲存」前密碼不符策略（過短 / 缺字母 / 缺數字 / 缺特殊符號 / 黑名單等）, 前端只擋空值, 其他策略違反由後端 checkUserPassword reject 後以 CheckYes modal 顯示語系化訊息要 admin 點擊確認
- **E2E-013** 管理員於後台點新增, 帳號與 DB 既有 row 衝突（同表內無重複但 ltdtDiffByKey 後重複）, 後端 ckKey reject (E2E-013-account-conflict-backend)
- **E2E-014** 管理員於後台點新增, email 與 DB 既有 row 衝突（同表內無重複但 ltdtDiffByKey 後重複）, 後端 ckKey reject (E2E-014-email-conflict-backend)
- **API-010(待補)** 管理員於後台點新增, 點儲存時 token 已過期 / 已被刪, 後端 reject (modifyuser-011 有對應 baseline 可參考)
- **API-011(待補)** 管理員以非 admin token 呼叫 updateUsersList API, 後端 funCheckAdmin 判否, 與「真過期」共用同一 reject 訊息（不洩露身分檢查細節）

## 執行流程

### 一、新增空白列（addItem）

```
001  管理員點「+」新增按鈕（僅 isEditable 顯示）  [LayoutContentUsers.vue:122]
002  addItem 取既有 vo.opt.rows 並 cloneDeep
003  vo.$ds.users.funNew() 產生新 row（id 用 genIDSeq, timeCreate=now,
        其餘欄位依 schema 預設; 實際預設值見 src/schema/users.mjs 之 funNew）
004  填入暫時佔位字串:
        name = $s.getNameNew(rows, 'name', '', $t('userAddNameNew'))   //如「new user N」, 確保不撞名
        userId / timeCreate / userIdUpdate / timeUpdate = `{${$t('userAddIdNew')}}`
            （送至後端時由 procOrm 以實際操作者 id 與 nowms2str 覆寫,
              詳見「四、儲存」）
        _isNew = true   //transient flag, 標示此列為「未儲存的新列」, 用於 password 欄位顯示
                            為輸入框（非按鈕）並啟用密碼空值檢查; 送後端前由 saveUsers 剝除
005  將新 row 插入 rows 最首
006  vo.users = cloneDeep(rows) → 連帶驅動 computed 重算 items / opt.rows
007  isModified=true → 顯示紅底「儲存」按鈕
```

### 二、就地編輯欄位（資料表 cell-render）

```
account / email / redir / name / description / from / order
    可直接輸入文字; cell 顯示警告 icon 表示有 errItemsBy* 偵測到錯誤

password (新增列, _isNew=true)
    cellRenderer: 顯示密碼值文字 + 警告 icon (若 cellPasswordErr 非空)
    編輯: 走 ag-grid 標準 cell editor (dblclick 進入), Enter 或 blur commit
    (歷史: 原本走 custom WText 就地輸入. @input 每字 keystroke 觸發 vo.refresh() 重建 input DOM
     導致鍵盤連續輸入漏字; 改 @change 又讓警告 icon 無法即時刷新.
     改用 ag-grid 編輯模式, 沿用其他欄位 [account/email/redir/name/description] 同款機制, 一致且穩定.)

password (既有列, _isNew=false 或 undefined)
    顯示為「重設密碼」按鈕 (本流程不負責設定既有使用者密碼)

isAdmin / isActive
    checkbox 形式; click 走 $dg.toggleItemIsAdminById / toggleItemIsActiveById, 切 'y' / 'n'

timeVerified / timeExpired / timeBlocked
    WTimeminute 日期時間選擇器, 解析後以 timemsTZ 格式寫回 row
```

### 三、即時前端驗證（computed）

前端 computed 對每列做粒度驗證，產生 cell 警告 icon + tooltip，並聚合為 `isError` 字串供 saveUsers 攔截。粒度規則詳「i18n 訊息粒度規則」章節。

```
errItemsByAccount   每列檢查 account 空值與同表重複, 寫入 kpErr[<value>] = 對應錯誤訊息
errItemsByEmail     每列檢查 email 空值 / isEmail 格式 / 同表重複
errItemsByRedir     每列檢查 redir 空值
errItemsByPassword  僅檢查 _isNew=true 之列的 password 是否為空
                    (其他 policy 違反不在前端檢查, 由後端 checkUserPassword 把關)

isError computed（整體錯誤訊息, 第一層攔截）
    上述任一 errItemsBy* 非空 → 取對應 category title 字串
    saveUsers 以此字串為入口判斷是否送後端;
    cellFieldErr 在 cell 顯示警告 icon + tooltip 細節錯誤;
    cellPasswordErr 同樣機制但 lookup 鍵為 row.id（password 不適合做 key）
```

### 四、儲存（saveUsers）

```
001  管理員點紅底「儲存」按鈕（僅 isEditable && isModified 顯示）
002  $ui.updateLoading(true)
003  檢查 isError
004      非空字串:
005          hideLoading + await showCheckYes(isError) 後 return（不送後端）
006  rows = vo.opt.rows
007  檢查 rows 是否為空 → 為空 hideLoading + await showCheckYes(對應訊息) return
008  自我鎖死保護（前端第一道）:
009      尋找 rows 內 row.id === userSelf.id
010      若該列 isAdmin !== 'y' → hideLoading + await showCheckYes(cannotDemoteSelf) return
011      若該列 isActive !== 'y' → hideLoading + await showCheckYes(cannotDisableSelf) return
012  剝除 transient flag _isNew (不送後端)
013  vo.$fapi.updateUsersList(token, lang, rows) 批次提交
014      handler 帶入 funCheckAdmin 後呼叫 p.checkTokenAndUpdateUsersList(token, lang, rows, opt)
015          checkToken({ fun: funCheckAdmin })
016              token 為空 / 過期 / 無效 → reject
017              token 有效但 funCheckAdmin 回 false（非 admin）→ b2=false → reject
018                  （注意: 此路徑不分歧錯誤訊息, 與真過期共用同一字串）
019          getUserByToken 取操作者 → operatorId
020          自我鎖死保護（後端第二道, 與前端同條訊息）:
021              rows 內找操作者 row, 若 isAdmin !== 'y' → reject(cannotDemoteSelf)
022                                     若 isActive !== 'y' → reject(cannotDisableSelf)
023          updateUsersList(rows, { lang, operatorId }) 委派
024              updateTabItems('users', rows, 'id', { resetOrder: true, lang, operatorId })
025                  ltdtmapping(rows, ds.users.keys) 補齊缺失欄位
026                  resetOrder: rows 依陣列順序重指派 order = k+1
027                  ckKey('id'): 表內 id 不可為空或重複 → reject
028                  ckKey('email'): 表內 email 不可為空或重複 → reject
029                  ltdtOld = woItems.users.select() 取 DB 既有資料
030                  既有 row password 保留: 將 ltdtOld 內對應 id 的 password (hash) 寫回 rows 該列
031                      （getUsersList 已 strip password, 前端送回的 password 是 '', 此步避免覆蓋既有 hash）
032                  ltdtDiffByKey(ltdtOld, rows, 'id') 拆 add / diff / del 三組
033                  add 群組（新增列）:
034                      checkUserPassword(lang, row.password, { account: row.account })
035                          state==='error' → reject 對應語系化錯誤訊息 (空、過短、缺字母、黑名單等)
036                      row.password = hashPassword(明文, salt)
037                      若 timeVerified 為空 → row.timeVerified = now2str()
038                      procOrm(operatorId, 'users', 'insert', r.add) 寫入 DB
039                          procOrm 內部對 add 群組自動覆寫:
040                              userId = operatorId
041                              timeCreate = now
042                              userIdUpdate = operatorId
043                              timeUpdate = now
044                  diff 群組（既有 row 有變動）:
045                      procOrm(operatorId, 'users', 'save', r.diff)
046                          procOrm 內部對 save 群組自動覆寫:
047                              userIdUpdate = operatorId
048                              timeUpdate = now
049                          （password 已在步驟 030 還原為 DB hash, save 時 merge 不會覆蓋）
050                  del 群組:
051                      procOrm(operatorId, 'users', 'del', r.del)
052                  return ltdtNew (剝除 password 欄位避免 hash 經 API 洩漏)
053  .catch err → errTemp = err
054  errTemp 非 null:
055      hideLoading + await $dg.showCheckYes(`<userSaveUsersFail>: ${errTemp}`) 後 return
            （改用 modal 強制 admin 點擊確認, 避免 transient toast 漏看後端錯誤訊息）
056  $fapi.getUsersList(token) 重拉同步, 覆寫 vo.users
057      （讓 timeVerified=now、userId/userIdUpdate=operatorId、order 重排等後端寫入結果立即顯示）
058  isModified = false（紅底儲存按鈕收起）
059  hideLoading + await showCheckYes(<userSaveUsersSuccess>)
```

### 五、衍生操作（同一表共用 saveUsers 路徑）

```
copyItem
    UI 觸發: 勾選表內單一列時 copy 按鈕始出現（hasItemCheckOne）;
            未勾選或勾選多於一列, copy 按鈕不顯示.
    對勾選的單一列 cloneDeep, 換新 id（funNew 產的）, 占位 userId/time*,
    清空 password, 標記 _isNew=true, 插入最首
    其他欄位（name / email / isAdmin / isActive / redir / description 等）保留自源頭列;
        admin 須於新列至少改動 account 與 email 以避開同表重複, 並重新輸入 password
        （清空後該列 password 走前端 errItemsByPassword 攔截直到輸入）
    儲存路徑與 addItem 完全相同（走 add 群組: checkUserPassword → hashPassword
        → procOrm insert 覆寫 audit fields）; 源頭列不受影響, DB 兩列共存

toggleItemIsAdminById / toggleItemIsActiveById
    checkbox click → 切 'y'/'n'，isModified=true
    儲存時走 diff 群組（procOrm save）;
    若被切的列 id === userSelf.id 且新值非 'y', 儲存階段會被自我鎖死保護擋下
```

### 六、新增使用者欄位邊界（純 spec 規則）

| 欄位 | 邊界規則 | 後端處理 |
|---|---|---|
| id | 前端 `genIDSeq()` 產生 | procOrm insert 不覆寫 |
| password | 必填; 由 admin 就地輸入明文 | add 群組做 `checkUserPassword` + `hashPassword(salt)` 後寫入 |
| timeCreate / timeUpdate / userId / userIdUpdate | 前端佔位字串送出 | procOrm 在 add 群組覆寫為操作者 id 與 now (audit fields) |
| isActive / isForceChangePw / isAdmin | 預設值依 schema funNew; checkbox 可變更 | — |
| timeVerified | 前端空字串 | insert 階段填 now（後台建帳即已驗證，不寄驗證信） |
| order | 前端不指定 | 後端 resetOrder 重排為陣列順序 +1 |
| timeExpired / timeBlocked | 可選輸入 | merge 寫入 |
| tokenVerify | 後台建帳不產生 | — |
| _isNew (transient) | addItem 設 `true`, saveUsers 送出前剝除 | — |

實際欄位預設值 → 見 `src/schema/users.mjs` 之 `funNew`。

## 參數來源

本流程涉及以下執行期參數，**測試讀取順序：settings.json 覆寫值 > WWebSso.mjs opt 預設**：

| 概念 | 來源（優先序）| 測試影響 |
|---|---|---|
| 密碼策略（最小 / 最大長度、字元類型限制、是否禁空白、是否禁非 ASCII、是否禁常見密碼、是否禁與 account 相連字元、自訂黑名單等）| `settings.json` 對應 key → `server/WWebSso.mjs` opt 預設 | 觸發策略違反 case 須以具體值構造（grep `keyLim*`、`checkUserPassword`、`opt.password*`）|
| salt（hashPassword 加鹽）| `settings.json` 對應 key → 預設值 | 比對 DB 已 hash password 時須一致 |
| 使用者欄位 schema 預設（id 產生器、isActive / isForceChangePw / isAdmin 預設、其他欄位空字串等）| `src/schema/users.mjs` 的 `funNew`（不可從 settings 改）| test setup 建 user 的初始狀態源頭 |
| token 有效期 | `settings.json` 對應 key | 測試 token 構造時的 `timeEnd` 計算 |

實際數字 / 預設值 → 寫測試時讀 `settings.json` 對應 key 或 `src/schema/users.mjs` 的 funNew。

## spec 規則摘要（粒度 / 邊界 / 順序 / 契約）

- **驗證順序**：前端 computed `errItemsBy*` → 前端 `isError` 聚合攔截 → 前端自我鎖死保護 → 後端 `checkToken`（含 funCheckAdmin）→ 後端 `checkTokenAndUpdateUsersList` 自我鎖死保護 → `ckKey('id')` / `ckKey('email')` → add 群組逐筆 `checkUserPassword` → procOrm 寫入。任一層 reject 即整批不落地。
- **粒度**：帳號 / email 「空」與「重複」分開告知；具體策略違反由後端帶具體訊息；token 失效與身分不足共用同一訊息（不洩露身分檢查）。
- **邊界**：
  - 前端只擋 password 空值；其他密碼策略由後端 `checkUserPassword` 把關。
  - 既有 user password 不可由本流程改寫：後端 saveUsers 在 ltdtDiffByKey 前以 DB 既有 hash 還原 row.password，避免前端送回空字串把 DB hash 洗掉。
  - 自我鎖死保護：rows 內若包含操作者本人，不可將自己 `isAdmin` 或 `isActive` 改為非 'y'（前端 + 後端兩道）。
  - 後台建帳不寄驗證信，timeVerified 由後端 add 群組自動填 now；不產生 tokenVerify。
- **契約**：
  - `updateUsersList` 走批次 upsert：整表 `ltdtDiffByKey` 一次同步 add / diff / del，任一驗證錯誤即整批不落地。
  - 儲存成功後立即重拉 `getUsersList` 同步 audit fields 與 order。
  - audit fields（userId / timeCreate / userIdUpdate / timeUpdate）由 procOrm 在伺服端寫入，不接受前端送來的值。
  - API 回傳前剝除 password 欄位，避免 hash 從 API 流出。
