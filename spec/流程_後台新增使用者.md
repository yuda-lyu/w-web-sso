# 後台新增使用者流程

## 觸發

管理員於 LayoutContentUsers.vue 後台 Users list 點擊「新增」按鈕，於資料表中插入一筆空白列就地填寫帳號 / 密碼 / 姓名 / Email / Redir 等欄位，再點「儲存」批次提交至後端。

## 重要流程

- **E2E-001**
  - title: 管理員填妥新使用者欄位後儲存成功
  - description: 驗證管理員於後台 Users list 點「新增」插入空白列，依序填妥帳號、密碼、email、redir 等必要欄位後點「儲存」，前端 isError 為空通過攔截，後端 add 群組執行 checkUserPassword、hashPassword、procOrm insert 寫入 DB（timeVerified 自動填 now、password 經 hash），儲存成功後前端立即重拉 getUsersList 並於 CheckYes 成功 modal 顯示語系化訊息；表格刷新後新帳號可被使用者於畫面上觀察到。
  - flow:
    - 測試資料：admin user `id-au-admin`（帳號 `au-admin` / 密碼 `Pw@auadmin1` / `isAdmin='y'`）與 admin token（有效 60 分鐘）；existing user `id-au-existing` 作為表內基底列。
    - 操作：以 admin 登入並進入 Users list → 開啟「Edit mode」/「編輯模式」→ 點「+」新增按鈕 → 於首列依序填入帳號 `au-newuser-{lang}-baseline`、密碼 `Pw@KLMN5678`、email `au-newuser-{lang}-baseline@test.com`、redir `{baseUrl}/?view=user&token={token}` → 點「儲存」按鈕 → 於 CheckYes 成功 modal 點「OK」/「確認」。
    - 驗證（共 3 階段截圖，涵蓋完整流程）：
      - **階段 1（按「+」後空白列出現）**：
        1. 語意：表格首列（row-index=0）出現新的空白可編輯列，帳號、密碼、email、redir 等欄位尚未填入。
        2. 視覺：與 baseline `test/pics/adduser/adduser-{eng,cht}-E2E-001-1-new-blank-row.png` 視覺一致（pixelmatch 容差）；標注區為首列跨 pinned-left 與 center 容器的整列寬。
      - **階段 2（填妥欄位後點「儲存」—— CheckYes 成功 modal 出現）**：
        1. 語意：CheckYes modal 顯示儲存成功語系化訊息（對應 spec `userSaveUsersSuccess`），畫面仍停留在 Users list；admin 尚未點「OK」/「確認」。
        2. 視覺：與 baseline `test/pics/adduser/adduser-{eng,cht}-E2E-001-2-save-success-modal.png` 視覺一致（pixelmatch 容差）；標注區為 CheckYes modal 內層 panel（綠勾確認框）。
      - **階段 3（點「OK」/「確認」後，表格刷新含新帳號）**：
        1. 語意：Users list 表格 DOM 上出現新帳號 `au-newuser-{lang}-baseline`（後端寫入後重拉 getUsersList 同步）；新列排在表格首列（row-index=0）。
        2. 視覺：與 baseline `test/pics/adduser/adduser-{eng,cht}-E2E-001-3-after-save-with-new-user.png` 視覺一致（pixelmatch 容差）；標注區為新使用者那一列（row-index=0，聚焦驗證標的為新帳號已出現於清單）。
    - 雙語:eng / cht 各一輪。
    - 清理：移除動態建立的 `au-newuser-{lang}-baseline` 使用者；afterEach 統一刪除 admin / existing 等非 base seed 資料，保留 base seed。

## 執行流程

### 一、新增空白列（addItem）

```
001  管理員點「+」新增按鈕（僅 isEditable 顯示）  [LayoutContentUsers.vue:122]
002  addItem 取既有 vo.opt.rows 並 cloneDeep
003  vo.$ds.users.funNew() 產生新 row（id 用 genIDSeq, timeCreate=now,
        其餘欄位依 schema 預設; 實際預設值見 src/schema/users.mjs 之 funNew）
004  填入暫時佔位字串:
        name = $s.getNameNew(rows, 'name', '', $t('userAddNameNew'))   //如「new user N」, 確保不撞名
        userId / timeCreate / userIdUpdate / timeUpdate = `{${$t('userAddIdNew')}}`
            （送至後端時由 procOrm 以實際操作者 id 與 nowms2str 覆寫,
              詳見「四、儲存」）
        _isNew = true   //transient flag, 標示此列為「未儲存的新列」, 用於 password 欄位顯示
                            為輸入框（非按鈕）並啟用密碼空值檢查; 送後端前由 saveUsers 剝除
005  將新 row 插入 rows 最首
006  vo.users = cloneDeep(rows) → 連帶驅動 computed 重算 items / opt.rows
007  isModified=true → 顯示紅底「儲存」按鈕
```

### 二、就地編輯欄位（資料表 cell-render）

```
account / email / redir / name / description / from / order
    可直接輸入文字; cell 顯示警告 icon 表示有 errItemsBy* 偵測到錯誤

password (新增列, _isNew=true)
    cellRenderer: 顯示密碼值文字 + 警告 icon (若 cellPasswordErr 非空)
    編輯: 走 ag-grid 標準 cell editor (dblclick 進入), Enter 或 blur commit
    (歷史: 原本走 custom WText 就地輸入. @input 每字 keystroke 觸發 vo.refresh() 重建 input DOM
     導致鍵盤連續輸入漏字; 改 @change 又讓警告 icon 無法即時刷新.
     改用 ag-grid 編輯模式, 沿用其他欄位 [account/email/redir/name/description] 同款機制, 一致且穩定.)

password (既有列, _isNew=false 或 undefined)
    顯示為「重設密碼」按鈕 (本流程不負責設定既有使用者密碼)

isAdmin / isActive
    checkbox 形式; click 走 $dg.toggleItemIsAdminById / toggleItemIsActiveById, 切 'y' / 'n'

timeVerified / timeExpired / timeBlocked
    WTimeminute 日期時間選擇器, 解析後以 timemsTZ 格式寫回 row
```

### 三、即時前端驗證（computed）

前端 computed 對每列做粒度驗證，產生 cell 警告 icon + tooltip，並聚合為 `isError` 字串供 saveUsers 攔截。粒度規則詳「i18n 訊息粒度規則」章節。

```
errItemsByAccount   每列檢查 account 空值與同表重複, 寫入 kpErr[<value>] = 對應錯誤訊息
errItemsByEmail     每列檢查 email 空值 / isEmail 格式 / 同表重複
errItemsByRedir     新增列(_isNew) redir 空值即攔下(本流程 E2E-008); 既有列僅「由非空改為空」才攔, 載入時即為空之既有列
                    (自助註冊者)不攔、不標警示, 鍵為列主鍵 (2026-10-23, R-VAL-02 / ADR-094; 見 流程_後台變更使用者資訊.md E2E-016;
                    〔原載「每列檢查 redir 空值」: 載入時即為空之既有列會擋住整份清單存檔; 本流程新增列之攔截行為與標準圖不變〕)
errItemsByPassword  僅檢查 _isNew=true 之列的 password 是否為空
                    (其他 policy 違反不在前端檢查, 由後端 checkUserPassword 把關)

isError computed（整體錯誤訊息, 第一層攔截）
    上述任一 errItemsBy* 非空 → 按 account→password→email→redir 優先序,
        取 kpErr 內的第一條具體欄位訊息（如 $t('userAccountDuplicate')）直接回傳;
        非 category title（errInAccounts 等 category key 不在此路徑）
    saveUsers 以此字串為入口判斷是否送後端;
    cellFieldErr 在 cell 顯示警告 icon + tooltip 細節錯誤;
    cellPasswordErr 同樣機制但 lookup 鍵為 row.id（password 不適合做 key）
```

### 四、儲存（saveUsers）

```
001  管理員點紅底「儲存」按鈕（僅 isEditable && isModified 顯示）
002  $ui.updateLoading(true)
003  檢查 isError
004      非空字串:
005          hideLoading + await showCheckYes(isError) 後 return（不送後端）
006  rows = vo.opt.rows
007  檢查 rows 是否為空 → 為空 hideLoading + await showCheckYes(對應訊息) return
008  自我鎖死保護（前端第一道）:
009      尋找 rows 內 row.id === userSelf.id（mySelfRow）
010      若 mySelfRow 為 null（admin 把自己勾選刪除） → hideLoading + await showCheckYes(cannotDeleteSelf) return
011      若 mySelfRow.isAdmin !== 'y' → hideLoading + await showCheckYes(cannotDemoteSelf) return
012      若 mySelfRow.isActive !== 'y' → hideLoading + await showCheckYes(cannotDisableSelf) return
013  transient flag _isNew 隨列送後端（後端據以判定 saveNewRowExists 後於 ltdtmapping 剝除，不入庫；ADR-074 起前端不再剝除）
014  vo.$fapi.updateUsersList(token, lang, rows) 批次提交
015          handler 帶入 funCheckAdmin 後呼叫 p.checkTokenAndUpdateUsersList(token, lang, rows, opt)
016              checkToken({ fun: funCheckAdmin })
017                  token 為空 / 過期 / 無效 → reject
018                  token 有效但 funCheckAdmin 回 false（非 admin）→ b2=false → reject
019                      （注意: 此路徑不分歧錯誤訊息, 與真過期共用同一字串）
020              getUserByToken 取操作者 → operatorId
021              自我鎖死保護（後端第二道, 與前端同條訊息）:
022                  rows 內找操作者 row, 若自己列已移除 → reject(cannotDeleteSelf)
023                                         若 isAdmin !== 'y' → reject(cannotDemoteSelf)
024                                         若 isActive !== 'y' → reject(cannotDisableSelf)
025              updateUsersList(rows, { lang, operatorId }) 委派
026                  updateTabItems('users', rows, 'id', { resetOrder: true, lang, operatorId, optClient, ocList: 使用者清單快取 })
                         (2026-10-23 多人同時編輯: 取 [tokens, users] 表鎖, 鎖內新鮮讀取並比對基準 { baseline }; 帳號唯一性、新增列已存在〔_isNew〕檢查亦在鎖內,
```

## spec 規則摘要（粒度 / 邊界 / 順序 / 契約）

- **多人同時編輯**（2026-10-23，原則 10；共通規則與案例見 `流程_多人同時編輯.md`）：新增之使用者與他人同時新增看似相同之資料時各自保存（不去重、由管理員協調），但帳號全域唯一仍依既有規則擋（改於表鎖內檢查，自助註冊與後台清單新增同帳號並行時恰一方成功，修正）；載入後資料已被更動者整次拒收。新增列之伺服器專有欄位（`tokenVerify`、`userId`、`timeCreate`、稽核欄）不採客戶端值。
- **驗證順序**：前端 computed `errItemsBy*` → 前端 `isError` 聚合攔截 → 前端自我鎖死保護 → 後端 `checkToken`（含 funCheckAdmin）→ 後端 `checkTokenAndUpdateUsersList` 自我鎖死保護 → 列格式（rows 為陣列；id 非空、不重複、不超過鍵長上限 → `invalidRows`）→ email 非空、不重複（`userEmailEmpty` / `userEmailDuplicate`）→ 新增列已存在（`saveNewRowExists`）→ account 必填 + 全域唯一性（`accountRequired` / `accountDuplicate`）→ 新增 / 修改列之欄位值會被 clearXSS 改寫（`htmlMarkupNotAllowed`）→ add 群組逐筆 `checkUserPassword` → procOrm 寫入。任一層 reject 即整批不落地（ADR-021 / ADR-081：凡可於寫入前判定、寫入時才會被拒或被改寫之輸入，一律於驗證階段拒絕）。
- **粒度**：帳號 / email 「空」與「重複」分開告知；具體策略違反由後端帶具體訊息；token 失效與身分不足共用同一訊息（不洩露身分檢查）。
- **邊界**：
  - 前端只擋 password 空值；其他密碼策略由後端 `checkUserPassword` 把關。
  - 既有 user password 不可由本流程改寫：後端 saveUsers 在 ltdtDiffByKey 前以 DB 既有 hash 還原 row.password，避免前端送回空字串把 DB hash 洗掉。
  - 自我鎖死保護：admin 不可將自己列從 rows 刪除（`cannotDeleteSelf`）、不可將自己 `isAdmin` 或 `isActive` 改為非 'y'（前端 + 後端兩道）。
  - 後台建帳不寄驗證信，timeVerified 由後端 add 群組自動填 now（timemsTZ 格式，與其他時間欄一致，後台清單之「已驗證」與管理權限閘皆以此格式認定）；不產生 tokenVerify。
- **契約**：
  - `updateUsersList` 走批次 upsert：整表 `ltdtDiffByKey` 一次同步，實際寫入序為 del → add → diff，任一驗證錯誤即整批不落地。
  - 寫入階段（驗證全過後）任一步失敗即停止後續步驟、回 `saveWriteFail`，其前已寫入者不回滾；撤銷本批欲刪除 / 停用者之令牌與清除清單快取不論寫入成敗皆執行（ADR-080）。
  - 儲存成功後立即重拉 `getUsersList` 同步 audit fields 與 order。
  - audit fields：新增列之 userId / timeCreate / userIdUpdate / timeUpdate 由 procOrm 於新增時寫入；既有列儲存時 procOrm 只覆寫 userIdUpdate / timeUpdate，userId / timeCreate 以送入值為準（後台畫面送回原值）。原載「audit fields 不接受前端送來的值」對既有列不成立（2026-09-29 讀 `node_modules/w-serv-orm/src/getMapOrm.mjs` 之 `adjustData` 更正；2026-10-11 引用由行號改為函數名：w-serv-orm 1.1.7 重構該檔，原行號 71-88 已移位）。
  - 同一包重送（ADR-074）：同一操作者處理中再送出 → reject `saveInProgress`；新增列帶 `_isNew` 送出，其 id 已存在（第 2 次於第 1 次完成後才到）→ reject `saveNewRowExists`，不把剛建立之列當修改覆寫。
  - API 回傳前剝除 password 欄位，避免 hash 從 API 流出。
- **送出入口與連按**（ADR-074）：「儲存」鈕為 promiseUnlock，鎖於請求結束時釋放；儲存流程以 `$ui.runSubmit('saveUsers')` 包覆，至結果訊息框關閉前再觸發（滑鼠、鍵盤 Enter）一律略過。
