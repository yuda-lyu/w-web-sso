# 後台新增使用者流程

## 觸發

管理員於 LayoutContentUsers.vue 後台 Users list 點擊「新增」按鈕，於資料表中插入一筆空白列就地填寫帳號 / 密碼 / 姓名 / Email / Redir 等欄位，再點「儲存」批次提交至後端。

## 重要流程

- **E2E-001**
  - title: 管理員填妥新使用者欄位後儲存成功
  - description: 驗證管理員於後台 Users list 點「新增」插入空白列，依序填妥帳號、密碼、email、redir 等必要欄位後點「儲存」，前端 isError 為空通過攔截，後端 add 群組執行 checkUserPassword、hashPassword、procOrm insert 寫入 DB（timeVerified 自動填 now、password 經 hash），儲存成功後前端立即重拉 getUsersList 並於 CheckYes 成功 modal 顯示語系化訊息；表格刷新後新帳號可被使用者於畫面上觀察到。
  - flow:
    - 測試資料：admin user `id-au-admin`（帳號 `au-admin` / 密碼 `Pw@auadmin1` / `isAdmin='y'`）與 admin token（有效 60 分鐘）；existing user `id-au-existing` 作為表內基底列。
    - 操作：以 admin 登入並進入 Users list → 開啟「Edit mode」/「編輯模式」→ 點「+」新增按鈕 → 於首列依序填入帳號 `au-newuser-{lang}-baseline`、密碼 `Pw@KLMN5678`、email `au-newuser-{lang}-baseline@test.com`、redir `{baseUrl}/?view=user&token={token}` → 點「儲存」按鈕 → 於 CheckYes 成功 modal 點「OK」/「確認」。
    - 驗證（等待 modal dismiss 與表格重拉完成後）：
      1. 語意：Users list 表格 DOM 上出現新帳號 `au-newuser-{lang}-baseline`（後端寫入後重拉 getUsersList 同步）。
      2. 視覺：與 baseline `test/pics/adduser/adduser-{eng,cht}-E2E-001-after-save-with-new-user.png` byte-equal。
    - 雙語:eng / cht 各一輪。
    - 清理：移除動態建立的 `au-newuser-{lang}-baseline` 使用者；afterEach 統一刪除 admin / existing 等非 base seed 資料，保留 base seed。

- **E2E-002**
  - title: 新增列帳號為空時前端攔下無法儲存
  - description: 驗證管理員點「新增」插入空白列後，於密碼、email、redir 都填妥但帳號欄位故意留空時，前端 errItemsByAccount 偵測到空值並聚合至 isError，saveUsers 於送後端前以 CheckYes modal 顯示語系化「無效帳號」訊息（spec 粒度規則：帳號空與帳號重複分開告知，不洩露具體列）。整批不送後端，DB 不落地。
  - flow:
    - 測試資料：admin user `id-au-admin`（同 E2E-001），admin token 有效。
    - 操作：以 admin 登入並進入 Users list → 開啟編輯模式 → 點「+」新增按鈕 → 首列只填密碼 `Pw@KLMN5678`、email `au-newuser-002@test.com`、redir `{baseUrl}/?view=user&token={token}`（account 故意不填）→ 點「儲存」按鈕。
    - 驗證（等待 CheckYes modal 出現並穩定後）：
      1. 語意：modal 顯示 `Invalid account of user` / `尚未給予有效使用者帳號`（對應 spec i18n 鍵 `userAccountEmpty` 之聚合 category 訊息）。
      2. 視覺：與 baseline `test/pics/adduser/adduser-{eng,cht}-E2E-002-account-empty.png` byte-equal。
    - 雙語:eng / cht 各一輪。
    - 清理：afterEach 統一刪除非 base seed 資料；本案例 DB 未落地，無須清新使用者。

### 四、儲存（saveUsers）

```
001  管理員點紅底「儲存」按鈕（僅 isEditable && isModified 顯示）
002  $ui.updateLoading(true)
003  檢查 isError
004      非空字串:
005          hideLoading + await showCheckYes(isError) 後 return（不送後端）
006  rows = vo.opt.rows
007  檢查 rows 是否為空 → 為空 hideLoading + await showCheckYes(對應訊息) return
008  自我鎖死保護（前端第一道）:
009      尋找 rows 內 row.id === userSelf.id
010      若該列 isAdmin !== 'y' → hideLoading + await showCheckYes(cannotDemoteSelf) return
011      若該列 isActive !== 'y' → hideLoading + await showCheckYes(cannotDisableSelf) return
012  剝除 transient flag _isNew (不送後端)
013  vo.$fapi.updateUsersList(token, lang, rows) 批次提交
014      handler 帶入 funCheckAdmin 後呼叫 p.checkTokenAndUpdateUsersList(token, lang, rows, opt)
015          checkToken({ fun: funCheckAdmin })
016              token 為空 / 過期 / 無效 → reject
017              token 有效但 funCheckAdmin 回 false（非 admin）→ b2=false → reject
018                  （注意: 此路徑不分歧錯誤訊息, 與真過期共用同一字串）
019          getUserByToken 取操作者 → operatorId
020          自我鎖死保護（後端第二道, 與前端同條訊息）:
021              rows 內找操作者 row, 若 isAdmin !== 'y' → reject(cannotDemoteSelf)
022                                     若 isActive !== 'y' → reject(cannotDisableSelf)
023          updateUsersList(rows, { lang, operatorId }) 委派
024              updateTabItems('users', rows, 'id', { resetOrder: true, lang, operatorId })
025                  ltdtmapping(rows, ds.users.keys) 補齊缺失欄位
026                  resetOrder: rows 依陣列順序重指派 order = k+1
027                  ckKey('id'): 表內 id 不可為空或重複 → reject
028                  ckKey('email'): 表內 email 不可為空或重複 → reject
029                  ltdtOld = woItems.users.select() 取 DB 既有資料
030                  既有 row password 保留: 將 ltdtOld 內對應 id 的 password (hash) 寫回 rows 該列
031                      （getUsersList 已 strip password, 前端送回的 password 是 '', 此步避免覆蓋既有 hash）
032                  ltdtDiffByKey(ltdtOld, rows, 'id') 拆 add / diff / del 三組
033                  add 群組（新增列）:
034                      checkUserPassword(lang, row.password, { account: row.account })
035                          state==='error' → reject 對應語系化錯誤訊息 (空、過短、缺字母、黑名單等)
036                      row.password = hashPassword(明文, salt)
037                      若 timeVerified 為空 → row.timeVerified = now2str()
038                      procOrm(operatorId, 'users', 'insert', r.add) 寫入 DB
039                          procOrm 內部對 add 群組自動覆寫:
040                              userId = operatorId
041                              timeCreate = now
042                              userIdUpdate = operatorId
043                              timeUpdate = now
044                  diff 群組（既有 row 有變動）:
045                      procOrm(operatorId, 'users', 'save', r.diff)
046                          procOrm 內部對 save 群組自動覆寫:
047                              userIdUpdate = operatorId
048                              timeUpdate = now
049                          （password 已在步驟 030 還原為 DB hash, save 時 merge 不會覆蓋）
050                  del 群組:
051                      procOrm(operatorId, 'users', 'del', r.del)
052                  return ltdtNew (剝除 password 欄位避免 hash 經 API 洩漏)
053  .catch err → errTemp = err
054  errTemp 非 null:
055      hideLoading + await $dg.showCheckYes(`<userSaveUsersFail>: ${errTemp}`) 後 return
            （改用 modal 強制 admin 點擊確認, 避免 transient toast 漏看後端錯誤訊息）
056  $fapi.getUsersList(token) 重拉同步, 覆寫 vo.users
057      （讓 timeVerified=now、userId/userIdUpdate=operatorId、order 重排等後端寫入結果立即顯示）
058  isModified = false（紅底儲存按鈕收起）
```

## spec 規則摘要（粒度 / 邊界 / 順序 / 契約）

- **驗證順序**：前端 computed `errItemsBy*` → 前端 `isError` 聚合攔截 → 前端自我鎖死保護 → 後端 `checkToken`（含 funCheckAdmin）→ 後端 `checkTokenAndUpdateUsersList` 自我鎖死保護 → `ckKey('id')` / `ckKey('email')` → add 群組逐筆 `checkUserPassword` → procOrm 寫入。任一層 reject 即整批不落地。
- **粒度**：帳號 / email 「空」與「重複」分開告知；具體策略違反由後端帶具體訊息；token 失效與身分不足共用同一訊息（不洩露身分檢查）。
- **邊界**：
  - 前端只擋 password 空值；其他密碼策略由後端 `checkUserPassword` 把關。
  - 既有 user password 不可由本流程改寫：後端 saveUsers 在 ltdtDiffByKey 前以 DB 既有 hash 還原 row.password，避免前端送回空字串把 DB hash 洗掉。
  - 自我鎖死保護：rows 內若包含操作者本人，不可將自己 `isAdmin` 或 `isActive` 改為非 'y'（前端 + 後端兩道）。
  - 後台建帳不寄驗證信，timeVerified 由後端 add 群組自動填 now；不產生 tokenVerify。
- **契約**：
  - `updateUsersList` 走批次 upsert：整表 `ltdtDiffByKey` 一次同步 add / diff / del，任一驗證錯誤即整批不落地。
  - 儲存成功後立即重拉 `getUsersList` 同步 audit fields 與 order。
  - audit fields（userId / timeCreate / userIdUpdate / timeUpdate）由 procOrm 在伺服端寫入，不接受前端送來的值。
  - API 回傳前剝除 password 欄位，避免 hash 從 API 流出。
- **訊息呈現分工**：操作結果（成功 `userSaveUsersSuccess` / 預期失敗 `userSaveUsersFail` / 前端攔截 `isError` 聚合 / 自我鎖死 / rows 空）一律走 `$dg.showCheckYes` 持久 modal，admin 須點「OK」/「確認」才繼續；僅外層 `core().catch` 接住的非預期錯誤 (`anUnexpectedErrorOccurred`) 走 `$alert` toast；欄位粒度錯誤（帳號 / email / redir / password 空、格式、重複）走 cell 警告 icon + tooltip 的 inline 紅字呈現，不走 modal 也不走 toast。
